# Маршрут — backend

Backend системы планирования выездных работ. Сервис хранит заявки и данные
инженеров, строит маршруты на несколько дней, проверяет ограничения и публикует
готовый план для владельца, диспетчера и инженера.

## Локальный запуск всей системы

Ниже описан рекомендуемый сценарий для первого запуска: инфраструктура и backend
работают в Docker, frontend — через Vite на хосте. Команды выполняются из корня
соответствующего репозитория.

### 1. Что понадобится

- Git;
- Docker с плагином Docker Compose (`docker compose version`);
- Node.js 22+ и npm — для frontend;
- свободные порты `5173`, `8000`, `8002`, `8080` и `5432`;
- доступ в интернет для загрузки Docker-образов, npm-пакетов и OSM-экстракта.

Первый запуск Valhalla и Nominatim скачивает и индексирует данные OpenStreetMap.
Это самая долгая часть запуска и требует заметного объёма диска. Последующие
старты используют Docker volumes и проходят значительно быстрее.

### 2. Клонируйте оба репозитория рядом

```bash
git clone https://github.com/Ship-it-easy/backend.git ship-it-backend
git clone https://github.com/Ship-it-easy/frontend.git ship-it-frontend
```

Ожидаемая структура каталогов:

```text
workspace/
├── ship-it-backend/
└── ship-it-frontend/
```

Если репозитории уже скачаны, этот шаг можно пропустить.

### 3. Подготовьте переменные backend

```bash
cd ship-it-backend
cp .env.docker.example .env.docker
```

Для обычного локального запуска шаблон уже содержит рабочие адреса сервисов.
Перед запуском откройте `.env.docker` и как минимум задайте собственный пароль
PostgreSQL:

```dotenv
POSTGRES_HOST=postgres
POSTGRES_PORT=5432
POSTGRES_DB=app_db
POSTGRES_USER=postgres
POSTGRES_PASS=change_me_to_a_local_password

BACKEND_PORT=8000
SESSION_EXPIRATION_MINUTES=60
SESSION_COOKIE_SECURE=false
```

Важно:

- для локального HTTP оставьте `SESSION_COOKIE_SECURE=false`, иначе браузер не
  будет отправлять сессионную cookie;
- `.env.docker` не должен попадать в Git;
- `USE_YANDEX_GEOCODER=false` не требует внешнего API-ключа: адреса обрабатывает
  локальный Nominatim;
- шаблон использует экстракт Центрального федерального округа. Для более
  компактного московского демо можно до первого запуска заменить значение на:

  ```dotenv
  OSM_PBF_URL=https://download.openstreetmap.fr/extracts/russia/central_federal_district/moscow-latest.osm.pbf
  ```

Не меняйте OSM-экстракт после его импорта без пересоздания томов Valhalla и
Nominatim: старые индексы не обновляются простой перезагрузкой контейнеров.

### 4. Соберите и запустите backend

```bash
docker compose --env-file .env.docker up -d --build
```

Compose поднимет четыре сервиса:

- `postgres` — основная база данных;
- `valhalla` — дорожные маршруты, время и расстояния;
- `nominatim` — локальный поиск и геокодирование адресов;
- `backend` — FastAPI-приложение.

Контейнер backend ждёт, пока все инфраструктурные сервисы станут `healthy`,
затем автоматически выполняет `alembic upgrade head` и запускает Gunicorn.
Поэтому при первом импорте OSM backend некоторое время может оставаться в
состоянии `Created` — это ожидаемо.

Следить за подготовкой геосервисов:

```bash
docker compose --env-file .env.docker logs -f valhalla nominatim
```

Проверить состояние всех контейнеров:

```bash
docker compose --env-file .env.docker ps
```

Посмотреть логи приложения:

```bash
docker compose --env-file .env.docker logs -f backend
```

Запуск завершён, когда `postgres`, `valhalla` и `nominatim` имеют статус
`healthy`, а в логах backend нет ошибки миграций. API после этого доступен на
<http://localhost:8000>, Swagger — на <http://localhost:8000/docs>.

### 5. Задайте пароль начального владельца

Миграции создают активного пользователя `owner`. Исходный bootstrap-пароль не
хранится в открытом виде, поэтому для локальной установки сразу задайте свой:

```bash
docker compose --env-file .env.docker exec backend \
  python scripts/set_owner_password.py
```

Скрипт дважды запросит пароль длиной не менее 12 символов. После этого для входа
используйте логин `owner` и введённый пароль.

### 6. При необходимости создайте готовое демо

Для быстрой проверки интерфейса можно создать изолированный проект с инженерами,
заявками и тремя способами передвижения: автомобиль, пешком и велосипед.

```bash
docker compose --env-file .env.docker exec backend \
  python scripts/prepare_transport_demo.py
```

Команда выведет JSON с `project_id`, логином и сгенерированным паролем
диспетчера. Сохраните эти данные: пароль печатается для локального оператора.
Сам расчёт запускается в интерфейсе в разделе «Планирование».

Этот шаг необязателен. Можно войти как `owner` и вручную создать район,
диспетчера, справочники, инженеров, смены и заявки.

### 7. Запустите frontend

Откройте второй терминал:

```bash
cd ../ship-it-frontend
npm ci
npm run dev
```

В режиме разработки frontend сам использует API на порту `8000` того же
hostname. Для стандартного запуска создавать env-файл frontend не нужно.

Откройте <http://localhost:5173> и войдите одним из способов:

- `owner` + пароль из шага 5;
- демо-диспетчер + пароль из JSON шага 6.

### 8. Быстрая проверка

После входа владельцем:

1. Создайте район и укажите его часовой пояс.
2. Создайте диспетчера и назначьте ему район.
3. Добавьте типы работ, квалификации и оборудование.
4. Добавьте инженеров и рабочие смены.
5. Создайте или импортируйте заявки.
6. Откройте «Планирование» и запустите расчёт.

Проверка API без интерфейса:

```bash
curl -fsS -o /dev/null http://localhost:8000/docs
```

### 9. Остановка и повторный запуск

Остановить backend и инфраструктуру, сохранив базу и OSM-индексы:

```bash
docker compose --env-file .env.docker down
```

Повторный запуск:

```bash
docker compose --env-file .env.docker up -d
```

Frontend останавливается сочетанием `Ctrl+C` в его терминале.

Полностью удалить локальную базу, маршруты и геокодирующий индекс:

```bash
docker compose --env-file .env.docker down -v
```

`down -v` необратимо удаляет все данные из Docker volumes. Используйте команду
только для полного чистого старта, например после смены OSM-экстракта.

### Частые проблемы

**Backend долго не запускается.** Проверьте `docker compose ps` и логи
`valhalla`/`nominatim`. На первом старте импорт OSM может занимать значительное
время; backend запустится только после обеих healthcheck-проверок.

**Порт уже занят.** Освободите конфликтующий порт. Текущая конфигурация Gunicorn
внутри контейнера слушает `8000`, поэтому `BACKEND_PORT` должен оставаться
равным `8000`. Чтобы опубликовать API, например, на `8010`, замените в
`docker-compose.yml` левую часть mapping с `8000:${BACKEND_PORT}` на
`8010:${BACKEND_PORT}`, а frontend запустите с соответствующим URL:

```bash
VITE_API_URL=http://localhost:8010 npm run dev
```

**Вход успешен, но интерфейс снова показывает форму входа.** Для локального HTTP
проверьте `SESSION_COOKIE_SECURE=false` и используйте один hostname во всех URL,
например везде `localhost`, а не смесь `localhost` и `127.0.0.1`.

**После изменения логина/пароля БД backend не подключается.** Значения
`POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASS` фиксируются при первом создании
тома PostgreSQL. Верните первоначальные значения либо выполните полный чистый
старт с `down -v`, если локальные данные больше не нужны.

**После смены региона находятся старые адреса или дороги.** Переменная
`OSM_PBF_URL` применяется при создании геоданных. Для другого региона требуется
чистый старт геосервисов; самый простой локальный вариант — `down -v` с потерей
локальной БД.

## Альтернативный запуск backend из исходников

Этот режим удобен для разработки backend на Linux/macOS: PostgreSQL, Valhalla и
Nominatim остаются в Docker, а FastAPI запускается на хосте.

Понадобятся Python 3.12 и [uv](https://docs.astral.sh/uv/).

1. Подготовьте оба env-файла:

   ```bash
   cp .env.docker.example .env.docker
   cp .env.example .env
   ```

2. В `.env.docker` задайте пароль БД. В `.env` укажите те же имя базы,
   пользователя и пароль, но используйте адреса хоста:

   ```dotenv
   POSTGRES_HOST=localhost
   POSTGRES_PORT=5432
   POSTGRES_DB=app_db
   POSTGRES_USER=postgres
   POSTGRES_PASS=change_me_to_a_local_password
   BACKEND_PORT=8000
   SESSION_EXPIRATION_MINUTES=60
   SESSION_COOKIE_SECURE=false
   VALHALLA_URL=http://localhost:8002
   NOMINATIM_URL=http://localhost:8080
   ```

3. Поднимите только инфраструктуру:

   ```bash
   docker compose --env-file .env.docker up -d postgres valhalla nominatim
   ```

4. Установите зависимости и примените миграции:

   ```bash
   uv sync --all-groups
   uv run alembic upgrade head
   ```

5. Запустите приложение с автоперезагрузкой:

   ```bash
   uv run gunicorn -c conf/gunicorn.conf.py 'auth.run:make_app()' --reload
   ```

Команды `make app`, `make migrate`, `make test`, `make up` и `make down` служат
короткими алиасами основных операций. Текущий Gunicorn-конфиг слушает порт
`8000`.

## Основные переменные окружения

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_HOST`, `POSTGRES_PORT` | Адрес PostgreSQL из backend: `postgres:5432` в Docker или `localhost:5432` при локальном запуске. |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASS` | База, пользователь и пароль PostgreSQL. |
| `BACKEND_PORT` | Внутренний порт backend; для текущего Gunicorn-конфига должен быть `8000`. Внешний порт задаётся левой частью mapping в Compose. |
| `SESSION_EXPIRATION_MINUTES` | Время жизни сессии в минутах. |
| `SESSION_COOKIE_SECURE` | `false` для локального HTTP, `true` за HTTPS. |
| `VALHALLA_URL` | URL сервиса дорожных маршрутов. |
| `NOMINATIM_URL` | URL локального геокодера. |
| `NOMINATIM_VIEWBOX` | Область поиска адресов: `left,top,right,bottom`. |
| `OSM_PBF_URL` | OSM PBF-экстракт, из которого строятся Valhalla и Nominatim. |
| `USE_YANDEX_GEOCODER` | Переключает геокодирование на API Яндекса. |
| `YANDEX_GEOCODER_API_KEY` | Ключ Яндекс Геокодера; нужен только при включённом флаге выше. |
| `GEOSERVICE_TIMEOUT_SEC` | Тайм-аут HTTP-запросов к геосервисам. |
| `MATRIX_BLOCK_SIZE` | Размер блока при построении матрицы времени и расстояний. |
| `MATRIX_CANDIDATE_LIMIT` | Необязательный лимит кандидатов матрицы; `0` в env означает отсутствие лимита. |
| `TRAFFIC_MODEL_ENABLED` | Включает сценарную модель пробок. |
| `BASELINE_COMPARISON_ENABLED` | Включает фоновый расчёт сравнения с FIFO. |

Полные шаблоны находятся в `.env.example` и `.env.docker.example`.

## Что делает проект

- аутентификация по серверной сессии и разграничение доступа по ролям;
- управление районами, диспетчерами, инженерами и их доступами;
- справочники типов работ, квалификаций и оборудования;
- создание, отмена и атомарный CSV-импорт заявок;
- многодневное планирование и динамический перерасчёт при изменениях;
- построение дорожных матриц через Valhalla;
- геокодирование через Nominatim или Яндекс;
- оптимизация распределения и порядка заявок через OR-Tools;
- отдельная валидация результата перед публикацией;
- сравнение оптимизированного плана с базовым FIFO;
- история версий, объяснение назначений и восстановление фоновых задач после
  перезапуска приложения.

## Роли

- **owner** — создаёт районы и пользователей, управляет доступами и может
  работать с данными и планами любого района;
- **dispatcher** — ведёт заявки, инженеров, справочники и планирование только в
  назначенных ему районах;
- **engineer** — видит собственные текущие, будущие и завершённые назначения.

Данные каждого района изолированы по `project_id`. Перед выполнением операции
backend проверяет, что пользователь имеет доступ к выбранному району.

## Как устроено приложение

Код разделён на два функциональных модуля:

- `src/auth` — пользователи, роли, сессии и аутентификация;
- `src/planning` — заявки, инженеры, справочники, импорт и планирование.

Оба модуля следуют слоистой архитектуре:

```text
domain          бизнес-сущности и правила
application     сценарии использования и интерфейсы портов
infrastructure  PostgreSQL, геосервисы, OR-Tools и другие адаптеры
presentation    HTTP-схемы, роутеры и обработка ошибок
entrypoint      конфигурация, dependency injection и сборка приложения
```

Dishka связывает зависимости, SQLAlchemy работает с PostgreSQL, Alembic ведёт
схему БД. Фоновые расчёты сохраняют состояние в PostgreSQL и восстанавливаются
при рестарте процесса.

## Как строится план

1. Backend фиксирует согласованный снимок заявок, инженеров, смен и настроек.
2. Отбрасывает заведомо несовместимые назначения по квалификации, транспорту,
   оборудованию и доступности.
3. Получает дорожное время и расстояния через Valhalla.
4. OR-Tools подбирает исполнителей и последовательность посещений с учётом SLA,
   окон работ, смен и бизнес-приоритетов.
5. Независимый валидатор проверяет полученное расписание.
6. Допустимые дни публикуются как единая версия плана; неназначенные заявки
   получают безопасную причину, а FIFO-сравнение считается в фоне.

Поиск ограничен временем, поэтому корректная трактовка результата — «найден
допустимый маршрут с оптимизацией по заданным приоритетам», а не гарантия
глобального математического оптимума.

## API

- интерактивная документация: `GET /docs`;
- аутентификация: `/api/auth/*`;
- управление пользователями и районами: `/api/admin/*`;
- рабочее пространство района: `/api/projects/{project_id}/workspace/*`;
- заявки и CSV-импорт: `/api/projects/{project_id}/jobs` и
  `/api/projects/{project_id}/job-imports`;
- запуски и пакеты планирования: `/api/projects/{project_id}/planning/*`;
- кабинет инженера: `/api/engineer/*`.

Точный и актуальный контракт запросов удобнее смотреть в Swagger после запуска.
