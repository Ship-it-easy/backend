**3. Текущий статус проекта и место OR-Tools**

Это уже функциональный MVP с достаточно широкой прикладной оболочкой. В backend присутствуют FastAPI, PostgreSQL/SQLAlchemy, RBAC, справочники, импорт, расписания, очередь событий, многодневный каскад, защита текущих маршрутов, версии плана и проверки перед публикацией. Во frontend есть кабинеты, семидневная доска, объяснения решений и карта. Такое наличие кода ещё не подтверждает полную приёмку каждого сценария.

OR-Tools — вычислительное ядро дневного распределения, но результат зависит от всей цепочки:

```text
Заявки, инженеры, графики, оборудование, конфигурация
  → snapshot
  → нормализация и совместимость
  → дневные штрафы, SLA-группы, FutureOpportunityBonus
  → дорожные время и расстояние Valhalla
  → RoutingModel OR-Tools
  → извлечение последовательности и расписания
  → дневной Validator
  → следующий день каскада / сравнение срочных кандидатов
  → проверка составного плана и актуальности
  → публикация новой версии
```

Сам OR-Tools не знает, что такое аварийная заявка, SLA или защищённая остановка. Он получает числовые стоимости и ограничения. Ошибка подготовки этих чисел будет выглядеть как осмысленный результат solver, хотя бизнес-задача окажется другой.

**4. Что в математической модели сделано правильно**

Используется `RoutingModel`, то есть специализированная модель маршрутизации, а не отдельная CP-SAT-модель. Инженер представлен vehicle, заявка — job node, старт у каждого инженера собственный, конец — фиктивная точка без возвращения домой.

Существенные корректные решения:

1. **Время работы включено в переход.** `transit(A,B) = duration(A) + travel(A,B)`. В переход к dummy end включена длительность последней заявки. Возвратного пути нет, но последняя работа обязана закончиться до конца смены. Это важная деталь: обнулить весь последний transit было бы ошибкой.
2. **Окно ограничивает начало.** `CumulVar(job)` ограничен окном начала. Завершение отдельно ограничено сменой конкретного инженера. Работа может закончиться после конца клиентского окна, как и требует ТЗ.
3. **Ожидание разрешено.** Slack временного измерения допускает ожидание открытия окна. Ожидание не входит в обычную objective.
4. **Профиль индивидуален.** CAR использует `auto`, NONE — `pedestrian`. Callback замыкает соответствующую матрицу через аргументы по умолчанию; типичной ошибки позднего связывания разных профилей в этом месте нет.
5. **Optional и mandatory разделены.** Обычные заявки имеют disjunction; в домене vehicle есть `-1` для пропуска. Срочная заявка внутри проверочной модели не имеет disjunction и должна быть назначена.
6. **Квалификации работают по AND.** Требуемое множество должно быть подмножеством квалификаций инженера. CAR исключает пешехода. Привязка сегодняшней старой заявки к прежнему инженеру дополнительно задаётся через allowed IDs.
7. **Оборудование моделируется на инженера и день.** Одна единица может обслуживать несколько работ одного инженера; двум инженерам одновременно она не выдаётся. Индикаторы `VehicleVar(job) == vehicle` связаны с `UsesEquipment`, а общая сумма ограничена запасом.
8. **Уже занятое оборудование учитывается.** Предварительно выделенные единицы вычитаются из доступного остатка, а инженер-владелец может продолжать использовать свою единицу.
9. **Стоимость подключения инженера реализована штатным механизмом.** `SetFixedCostOfVehicle` начисляется за непустой маршрут. Для инженера с защищённой активной остановкой используется нулевая дополнительная стоимость.
10. **Минимакс пробега полного будущего дня смоделирован разумно.** При нулевых начальных значениях Distance и отсутствии slack глобальный span равен максимальной длине маршрута в единицах модели. Для пересчёта хвостов есть отдельная оговорка ниже.
11. **Каскад переносит неназначенные заявки.** Дата меняется, возможности и штрафы пересчитываются. Назначенные ранее заявки исключаются из остатка; ограничение дневного набора применяется после расчёта каскадных приоритетов.
12. **Внешний рейтинг срочных кандидатов отделён от ObjectiveValue.** `_candidate_score` действительно строит общий сегодняшний вектор с SLA-потерями, числом инженеров, стабильностью, временем новой заявки и дорожными показателями.

Положительные эксперименты подтвердили: последняя работа, не помещающаяся в смену, не назначается; одна единица оборудования не выдаётся двум разным инженерам. Это проверки конкретных свойств, не исчерпывающий набор.

**5. Подтверждённые проблемы — в порядке исправления**

**F1. Невыполнимый первый кандидат прерывает перебор остальных инженеров. Приоритет: высокий.**

В [обработчике срочной вставки](/Users/pavelepanov/ship-it-backend/src/planning/application/services/dynamic_today_planning.py:529) невозможность маршрута распознаётся точным сравнением с текстом `OR-Tools did not return a feasible solution`. Однако [основная ветка solver](/Users/pavelepanov/ship-it-backend/src/planning/infrastructure/adapters/planning_solver_ortools.py:452) дописывает `for objective phase SINGLE` либо название другой фазы.

В результате ожидаемый отказ одного кандидата становится необработанным RuntimeError и выходит из перебора. Сценарий из разделов 7.3 и 8.3 ТЗ динамического добавления нарушается.

Воспроизведение через настоящий `DynamicTodayPlanningService._insert_one` и настоящий OR-Tools, с подменой только внешнего хранилища/матрицы:

- два инженера, смены 08:00–10:00;
- новая работа длится 60 минут, окно начала 08:00–08:20;
- первому ехать 30 минут: он не успевает;
- второму ехать 5 минут: он может начать в 08:05 и закончить в 09:05;
- общий перебор прекращается на инженере №1; сохранено 0 оценок кандидатов;
- отдельный solve инженера №2 успешно назначает заявку и проходит Validator.

Нужно вернуть типизированный результат/исключение с причиной: доказанная невыполнимость, отсутствие решения в лимите, невалидная модель, ошибка провайдера. Нельзя просто ловить все RuntimeError и продолжать: это скроет технические ошибки и неполную оценку кандидатов. Особый сценарий таймаута должен сохранять требуемую ТЗ семантику неполного сравнения.

**F2. Дорожный кеш формирует SQL, превышающий предел PostgreSQL уже на ожидаемом объёме. Приоритет: высокий.**

[Провайдер](/Users/pavelepanov/ship-it-backend/src/planning/infrastructure/adapters/travel_matrix_provider_valhalla.py:155) записывает все отсутствующие пары одним `insert(...).values(values)`. Это одна многострочная команда, а не пакет небольших вставок.

В эксперименте реальный код провайдера получил 110 различных точек — например, 100 заявок + 10 стартов инженеров. HTTP и сессия были заменены локальными заглушками, сформированные SQL-команды скомпилированы PostgreSQL-диалектом:

| Команда | Число параметров |
| --- | ---: |
| SELECT кеша | 12 101 |
| INSERT/UPSERT нового кеша | 121 000 |

PostgreSQL допускает максимум 65 535 параметров запроса. Приложение использует асинхронный psycopg без изменения стандартного server-side binding. Таким образом, для такого холодного кеша есть конкретный механизм отказа ещё до запуска OR-Tools. Проверена структура реального SQL; выполнение на PostgreSQL в рамках аудита не проводилось. [Предел PostgreSQL](https://www.postgresql.org/docs/current/limits.html), [передача параметров psycopg](https://www.psycopg.org/psycopg3/docs/basic/from_pg2.html#server-side-binding).

При 10 параметрах на пару полный холодный набор уже из 81 различной точки даёт 65 610 параметров вставки. На больших матрицах предел превысит и SELECT с развернутым `IN`: в текущем коде все ключи передаются одним списком.

Исправление: отдельное пакетирование чтения и UPSERT по числу параметров, например по 1 000–2 000 строк записи; дедупликация координат и ключей до запросов; интеграционный тест холодного кеша на 100 заявках. Автоматическую нарезку именно этого `.values(list)` предполагать нельзя.

**F3. Поиск останавливается в локальном минимуме и теряет выполнимые заявки. Приоритет: высокий.**

ТЗ дневного планирования, §4.13, задаёт `PARALLEL_CHEAPEST_INSERTION + GUIDED_LOCAL_SEARCH`. В [коде](/Users/pavelepanov/ship-it-backend/src/planning/infrastructure/adapters/planning_solver_ortools.py:419) стоит `GREEDY_DESCENT`. Комментарий объясняет это желанием оставить время на исправление недопустимых маршрутов.

Различие существенное: Greedy Descent прекращает улучшения в локальном минимуме, а GLS предназначен для выхода из таких состояний. Это соответствует [описанию стратегий OR-Tools](https://developers.google.com/optimization/routing/routing_options).

Получен точный контрпример: один инженер, шесть работ, симметричная метрическая матрица на прямоугольной сетке, без оборудования и сложной совместимости. Перебраны все подмножества и перестановки — 1 957 вариантов, включая пустой маршрут.

| Метод | Порядок заявок | Назначено | Дорога | Неназначенные |
| --- | --- | ---: | ---: | --- |
| Текущие настройки | 1 → 6 → 2 → 5 → 3 | 5 | 65 мин | №4 |
| Полный перебор | 6 → 2 → 1 → 5 → 4 → 3 | 6 | 89 мин | нет |
| Изолированная копия solver с заменой только Greedy на GLS, лимит 2 секунды | 6 → 2 → 1 → 5 → 4 → 3 | 6 | 89 мин | нет |

У маршрута на шесть работ начала: 08:19, 08:57, 10:01, 10:43, 11:39, 12:44. Последняя работа заканчивается в 12:59 при конце смены в 13:00. Все окна и длительности соблюдены.

Здесь 89 минут дороги лучше 65 по вашей целевой функции: выполнена дополнительная заявка, а дорожная экономия — нижестоящая цель. Контрпример также повторён с одинаковыми исходными штрафами 9 000 и действующим `_enforce_sla_hierarchy`; проблема сохраняется.

Это доказательство существования потери качества, а не оценка процента потерь на реальных данных. Настройка одного лишь `solver_time_limit_sec` не устраняет раннюю остановку Greedy. Рекомендация: вернуть конфигурируемый GLS, прогнать репрезентативную регрессию и подобрать бюджет. Не обещать, что одна смена стратегии исправит остальные ошибки.

**F4. Переполнение общей стоимости обрабатывается вопреки прямому требованию ТЗ. Приоритет: высокий для соответствия контракту.**

§8.4.2 ТЗ отмены/недоступности требует `OBJECTIVE_RANGE_OVERFLOW`, если точный objective не помещается в int64. [Код](/Users/pavelepanov/ship-it-backend/src/planning/infrastructure/adapters/planning_solver_ortools.py:1017) выдаёт эту ошибку только для отдельных границ, а при переполнении полной суммы включает `PHASED_DROP_THEN_ROUTE`.

Фактически выполняются две модели:

1. Минимизируется только бизнес-стоимость пропусков; дорожные и vehicle costs обнуляются.
2. Найденная стоимость пропусков фиксируется равенством; оптимизируются число инженеров, пробег и время.

Такой подход в принципе может быть разумным вариантом разработки, но это другое правило, которое не соответствует текущему тексту ТЗ. Кроме того, первая фаза — эвристическая: она не доказывает оптимум по пропускам. Ошибку первой фазы вторая исправить не сможет из-за равенства. При двух фазах `result.objective` уже обозначает только нижестоящую часть, что необходимо явно учитывать в мониторинге и истории.

Это не только экстремальные тестовые штрафы. В синтетическом наборе 100 работ / 10 инженеров / шесть SLA-групп получены:

- `Pmax = 6 249 918 419`;
- верхняя граница нижней части ≈ `1,081 × 10^15`;
- верхняя граница общей суммы ≈ `6,757 × 10^24`;
- предел int64 ≈ `9,223 × 10^18`;
- автоматически выбрана двухфазная ветка.

Единственный существующий прямой тест OR-Tools как раз закрепляет такое переключение, а не требуемый ТЗ отказ. Это показывает, что зелёные тесты в данном месте не означают соответствие спецификации.

Необходимо выбрать и записать один контракт: либо требуемый сейчас отказ и ограничение допустимого масштаба, либо согласованная фазовая оптимизация с сохранением статусов каждой фазы, найденных значений и признака отсутствия доказанного оптимума. Простое уменьшение весов разрушит строгую иерархию и не является исправлением.

**F5. Для разрешённых настроек времени неверно рассчитывается Tmax. Приоритет: средний, воспроизводимый отказ расчёта.**

[Формула](/Users/pavelepanov/ship-it-backend/src/planning/infrastructure/adapters/planning_solver_ortools.py:976) ограничивает сумму округлённых времен дуг округлённой длительностью смены. Но в общем случае сумма округлений вверх больше округления суммы.

Воспроизведение:

- `time_unit_seconds = 3600` — значение разрешено [API](/Users/pavelepanov/ship-it-backend/src/planning/presentation/http/project/schemas.py:176);
- смена 60 минут;
- две работы по 10 минут;
- две дорожные дуги по 60 секунд;
- маршрут занимает 22 минуты и физически допустим;
- каждая дуга стоит `ceil(60 / 3600) = 1`, вместе 2;
- граница по смене равна `ceil(3600 / 3600) = 1`, поэтому Tmax = 1;
- Validator возвращает `actual travel time exceeds Tmax`.

При стандартных 60 секундах этот конкретный пример не возникает: Time Dimension тоже округляет дорогу до минут. Но открытый диапазон настройки делает общую формулу неверной. Причём эта формула перенесена из самого ТЗ: необходимо исправить и спецификацию, и код.

Безопасный простой вариант — использовать границу `Nmax × ATmax`. Более тесная граница по сменам должна учитывать добавку от поарочного округления. Нужны проверки нескольких единиц, включая значения, не согласованные с минутной сеткой. Ограничение настройки проверенным набором значений допустимо только как явно описанный временный контракт.

**F6. Одна отсутствующая ненужная дуга блокирует весь расчёт. Приоритет: средний/высокий для доступности сервиса.**

В [предварительной проверке матрицы](/Users/pavelepanov/ship-it-backend/src/planning/infrastructure/adapters/planning_solver_ortools.py:166) обязательными считаются все пары совместимых заявок инженера. Их реальная совместимость по порядку окон не учитывается. При одном `None` возбуждается `DISTANCE_DATA_NOT_READY`, и до механизма запрета отдельных дуг управление не доходит.

Контрпример: A должна начаться до 08:20, B — после 09:00; известны старт → A, A → B и остальные нужные значения, но B → A отсутствует. Порядок B → A заведомо не нужен. Маршрут A в 08:05, B в 09:00 допустим, однако публичный `solve` завершается ошибкой.

Это расходится с §4.10 и §4.19 дневного ТЗ и планом реализации, где отказ отдельной дуги означает запрет дуги. Поздний §8.3 требует отказа при нехватке данных для необходимых вариантов; он не требует наличия заведомо ненужной обратной дуги.

В интерфейсе провайдера также стоит различать «маршрута физически нет» и «время/расстояние пока не удалось получить». Сейчас оба состояния представлены `None`. Для первого нужен запрет, для второго — контролируемый отказ/повтор, если данные действительно необходимы.

**F7. Независимый Validator не проверяет начало маршрута относительно смены. Приоритет: средний.**

Валидатор [начинает цепочку с `route.planned_start`](/Users/pavelepanov/ship-it-backend/src/planning/application/validators/planning_result.py:55), но не проверяет сам выезд. Эксперимент: смена с 08:00, маршрут искусственно сдвинут на 10 минут назад, выезд 07:50, дорога 20 минут, первая работа 08:10. Возвращается пустой список ошибок.

Найден не случай, когда текущий solver сам выпустил такой маршрут: в модели его старт фиксирован корректно. Найден пробел в обещанной независимой защите от ошибок solver/извлечения/композиции.

Дополнительно по коду отсутствует явный запрет нескольких Route для одного инженера; матрицы могут отсутствовать, и соответствующие проверки пропускаются. Дневные Job/Engineer не несут project_id, поэтому принадлежность проекту проверяется за пределами этого валидатора. Эти границы ответственности нужно явно зафиксировать и проверить на составном плане.

Добавить проверки начала и даты маршрута, уникальности route на инженера, обязательного наличия матричных данных в обычном успешном результате и связи результата с исходным snapshot. Разделять hard-constraint validation и оценку качества: даже полностью валидный маршрут может быть неоптимальным.

**6. Дополнительные риски, подтверждённые устройством кода**

Здесь выводы основаны на чтении реализации и математике; полное воспроизведение через публикацию в PostgreSQL не выполнялось.

**F8. У последовательных кандидатов различается «текущее время».** ТЗ динамического добавления §8.1 требует общий T0. Но [normalizer](/Users/pavelepanov/ship-it-backend/src/planning/application/services/planning_input_normalizer.py:41) читает `datetime.now()` при каждом вызове и заново подрезает начало смены. Кандидаты считаются последовательно. При переходе минуты поздний кандидат получит меньше доступного времени на тех же данных. Общие penalty также рассчитаны раньше этих отдельных нормализаций. Нужно передавать единый момент snapshot/общую временную границу и отличать её от deadline вычисления.

Матрица тоже не передаётся кандидатам единым неизменяемым объектом: каждый solve обращается к провайдеру. Кеш уменьшает повторные запросы, но не является полноценным контрактом единого snapshot матрицы. Желательно собирать общую версионированную матрицу и выдавать кандидатам подматрицы.

**F9. Минимакс пробега текущего дня считает изменяемые хвосты, а не полные маршруты.** [Distance начинается с нуля](/Users/pavelepanov/ship-it-backend/src/planning/infrastructure/adapters/planning_solver_ortools.py:322), а PlanningInput не содержит длины защищённых префиксов. Сумма неизменных префиксов — константа, её можно удалить из цели total distance. Но для `max(prefix_e + tail_e)` индивидуальные префиксы удалить нельзя.

Пример: защищённые части двух инженеров — 100 км и 1 км. Добавить 10 км первому или второму даёт одинаковую сумму, но максимумы полного дня будут 110 км и 100 км. Модель хвостов видит одинаковый максимум 10 км. Для обычного полного будущего дня этой проблемы нет. Для текущего многомашинного пересчёта нужно передавать исходные расстояния и формулировать максимум по полным учитываемым маршрутам.

**F10. Исправление невалидного расписания запретом одной дуги может удалить допустимые маршруты.** При `_InvalidSolverTimetable` [код](/Users/pavelepanov/ship-it-backend/src/planning/infrastructure/adapters/planning_solver_ortools.py:506) запрещает найденную пару from → to для инженера и повторяет solve. Но опоздание в B после A могло быть вызвано более ранними остановками; дуга A → B в другом префиксе может быть допустимой. Ветка не сработала в сохранённых экспериментах, поэтому это латентный риск, а не доказанный текущий инцидент. Правильнее устранить расхождение модели и извлечения либо отвергать конкретную недопустимую последовательность, не объявляя её последнюю дугу глобально невозможной.

**F11. Лимит solver не ограничивает всё время подготовки.** Матрицы получаются до старта таймера `_solve_sync`. Запросы блоков Valhalla и восстановление отдельных пустых ячеек идут последовательно. Общий deadline кандидатов проверяется между этапами, но не прерывает весь длинный вызов провайдера. После таймаута `asyncio.to_thread` также нельзя считать гарантированно остановленным без отдельного механизма. Нужно измерять и ограничивать весь путь события отдельно от времени поиска.

**7. Бизнес-неоднозначности, которые нужно закрыть в ТЗ**

**Количество заявок и аварийность внутри одной SLA-группы.** `_enforce_sla_hierarchy` не только разводит SLA-группы, но и добавляет каждой заявке одной группы большую общую базу. Это делает число выполненных заявок важнее любой суммы вторичных штрафов внутри группы.

Такое поведение опирается на приоритет количества из каскадного ТЗ §11. Однако поздние §7.2 и §8.4.2 задают additive EmergencyBonus и требуют нормализации BusinessDropCost без изменения порядка возможных сумм.

Конкретный пример одинаковой SLA-группы:

| Заявка | Исходный штраф | После `_enforce_sla_hierarchy` |
| --- | ---: | ---: |
| Одна аварийная, 100 минут | 1 009 000 | 2 037 |
| Обычная A, 50 минут | 9 000 | 1 037 |
| Обычная B, 50 минут | 9 000 | 1 037 |

В смену помещается либо аварийная, либо две обычные. По исходной сумме пропустить две обычные стоит 18 000, пропустить аварийную — 1 009 000: выбирается аварийная. По преобразованной сумме 2 037 < 2 074: выгоднее выполнить две обычные. Независимый перебор подтвердил предпочтение новой модели. Текущий Greedy в этом маленьком примере остался на аварийной — это локальный результат, а не сохранение исходного порядка моделью.

Нужно выбрать: «максимальное число заявок одной SLA-группы, аварийность — tie-break» или «аварийная заявка может перевесить несколько обычных той же группы». Это нельзя решить технической настройкой, не определив продуктовое правило. После решения требуются отдельные acceptance cases.

**Округление и обещание сохранить порядок расстояний.** Позднее ТЗ одновременно требует не менять порядок вариантов и округлять каждую дугу вверх до 10 метров. В общем случае эти требования несовместимы. Путь из дуг 1 м + 11 м имеет 12 м, но 3 единицы; путь 9 м + 9 м имеет 18 м, но 2 единицы. Модель предпочтёт второй. Код выполняет указанное поарочное округление, поэтому это прежде всего противоречие формулировки ТЗ. Нужно определить допустимую точность: единицы метрики считаются бизнес-целью, либо сравнение должно идти в исходных метрах.

**Стабильность динамического маршрута.** Внешний рейтинг кандидатов учитывает инверсии и сдвиги, но внутренняя дневная модель их не минимизирует, а расписание извлекается как самое раннее. Это соответствует описанной двухступенчатой архитектуре: сравниваются готовые варианты инженеров. Однако это не гарантирует наиболее стабильный из всех допустимых маршрутов каждого инженера. Если продукт обещает именно это, нужны дополнительные критерии внутренней модели/выбор нескольких решений и обновлённое ТЗ. Простая смена solver не добавит отсутствующую цель.

**Свободный выезд и фиксированный старт.** Первое ТЗ требует не фиксировать start в начале смены; код фиксирует и строит раннее расписание. При статической матрице и свободном ожидании это обычно не уменьшает множество допустимых последовательностей: более поздний выезд можно заменить ранним выездом и ожиданием. Это формальное расхождение, но оно не равнозначно ошибке маршрута. Если ранний выезд/ожидание неприемлемы операционно, нужно определить отдельную цель расписания.

**8. Эффективность и пределы текущей реализации**

Проведены небольшие локальные замеры без PostgreSQL и Valhalla. Матрицы синтетические, время solver в конфигурации — 2 секунды; это не нагрузочный тест production и не измерение default-бюджета 30 секунд. Значения времени немного меняются между запусками.

| Работ | Инженеров | Стратегия | Назначено | Использовано инженеров | Время всего локального solve, примерно |
| ---: | ---: | --- | ---: | ---: | ---: |
| 10 | 3 | Один weighted solve | 10 | 1 | 0,01 с |
| 100 | 10 | Две фазы после переполнения | 100 | 7 | 2,2 с |
| 100 | 30 | Две фазы после переполнения | 100 | 8 | 2,9 с |

Эти числа показывают, что вычислительное ядро работает на ста работах, но не доказывают оптимальное число инженеров, устойчивость к узким окнам/оборудованию и полную длительность события. Превышение заданных 2 секунд показывает, что это не строгий wall-clock предел всего Python-вызова.

Основные места роста затрат:

- Полная квадратная матрица `(jobs + engineers)²` на каждый профиль. Получаются и пары, которые solver никогда не использует: обратные поездки к стартам, пары стартов и несовместимые назначения.
- Повторные проходы по `engineer × job × job`: диапазоны objective, проверка полноты, запреты отсутствующих и временно невозможных дуг.
- `_objective_ranges` накапливает список всех допустимых дуг, повторяя одинаковые пары для инженеров одного профиля. Для максимумов достаточно потокового расчёта; хранить весь список не нужно.
- Временные запреты добавляют множество отдельных reified CP-ограничений, хотя Time Dimension уже кодирует последовательность. Нужен замер, какие дополнительные запреты реально окупаются.
- Оборудование добавляет связи job × engineer × equipment. Это ожидаемо, но такие ограничения требуют отдельных стресс-наборов.
- Python callbacks вызываются во время поиска. Возможны предварительная подготовка целочисленных cost matrices и переиспользование callback по одинаковым профилям; эффект нужно измерить.
- Фазы повторно строят модель. При включении overflow-ветки это не бесплатное масштабирование.
- Кандидаты сейчас идут последовательно; `max_parallel_candidate_models` в цикле не используется. Значение 1 соответствует умолчанию, но увеличение настройки не даёт заявленного параллелизма.
- Valhalla `/route` fallback может превратить множество пропусков матрицы в большое число последовательных HTTP-запросов. Ошибки кеширования усугубят повторную работу.

Не следует считать `max_jobs_per_run = 1000` доказанной поддерживаемой нагрузкой. Это только порог входного набора. Внешний кеш уже требует исправления на существенно меньшем числе точек.

Отдельно: Valhalla в текущей интеграции даёт статическую дорожную оценку. Пробки в конкретное время отправления не моделируются; это предусмотрено локальной заменой Yandex. Оптимальный по такой матрице маршрут не обязательно самый быстрый в реальном трафике. `STATIC_TEST` использует географическое расстояние и фиксированную скорость; он подходит для тестов, но не подтверждает качество реального дорожного плана.

**9. Как настраивать после исправления корректности**

Рекомендуемая последовательность:

1. Исправить типизированную обработку результатов solver и перебор кандидатов. Отдельно проверить «первый невыполним, второй выполним», «все невыполнимы», «один не оценён из-за таймаута», «сбой матрицы».
2. Пакетировать SQL дорожного кеша и закрепить тест 100 заявок / 10 инженеров на холодном и тёплом кеше.
3. Исправить Tmax и различение недоступных/неполных дуг. Расширить Validator.
4. Согласовать политику int64 и аварийности. Зафиксировать явный objective contract с номером версии.
5. Сделать поисковую стратегию конфигурацией; базовый кандидат — уже предусмотренный ТЗ GLS. `PARALLEL_CHEAPEST_INSERTION` можно оставить отправной точкой.
6. Проверять разные first-solution strategies на ваших данных, особенно при equipment constraints. Не выбирать стратегию по одному красивому маршруту.
7. Для полной даты сравнить бюджеты 1/5/15/30 секунд; для срочной вставки — отдельные бюджеты с учётом числа кандидатов и общего deadline. Важна дополнительная польза каждой секунды.
8. `use_full_propagation=True` сначала сохранить. После регрессии сравнить с light propagation по времени, памяти и валидности; отключать только по измерениям.
9. Если фазовая схема согласована, сохранять отдельно каждую фазу, её бюджет, статус, incumbent и вектор бизнес-метрик. Не выдавать оптимальность последней фазы за доказанный общий оптимум.
10. Сделать единый snapshot времени/матрицы для срочных кандидатов, затем добавить ограниченный параллелизм. У параллельных веток должны быть отдельные сессии и никакой записи активного плана.

Для многодневного каскада не нужно сразу строить огромную общую CP-SAT-модель. По текущему ТЗ независимые дни — сознательный выбор. Если позже появится требование глобальной оптимальности недели, это будет отдельная продуктовая и математическая задача.

Для задач на 4–8 заявок полезен независимый полный перебор: он проверяет смысл целевой функции, а не повторяет реализацию. Для больших наборов нужны фиксированные эталоны и сравнение стратегий по вектору: SLA-потери, аварийные потери, пропуски, число инженеров, пробег, время, стабильность. Единственный скаляр ObjectiveValue неудобен для сравнения разных моделей, масштабов и фаз.

Измерять отдельно: нормализацию, геокодирование, чтение/запись кеша, внешнюю матрицу, построение модели, первый допустимый результат, улучшение, валидацию, сохранение и весь event. Для эксплуатации важны p50/p95 и доля технических отказов, а не только средний `solver_time_ms`.
