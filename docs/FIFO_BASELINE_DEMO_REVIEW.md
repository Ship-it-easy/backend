# Преддемонстрационное ревью FIFO-сравнения

Дата проверки: 26 сентября 2026. Это инженерная проверка локального стенда, не
формальная приёмка PROD.

Обновление после удаления общественного транспорта: отдельный backend на порту
`8001` удалён при пересоздании Docker Compose. Текущий контейнер `backend`
обслуживает порт `8000`; сохранённый проект `8`, версия `14`, прошёл тот же
read-only smoke на этом порту. Frontend сейчас доступен по
`http://localhost:5173` и обращается к `8000`. Приведённые ниже сведения о
прежнем контейнере `8001` относятся к первоначальной проверке.

## Итог для показа

Локальный проект `8`, версия плана `14`, дневной запуск `41`, дата сравнения
27 сентября. Первая попытка FIFO завершилась `READY`; оба плана назначили
одинаковые 8 из 8 заявок, использовали двух инженеров и попали во все окна.
Пробег FIFO `123 381 м`, опубликованного оптимизатора `4 520 м` (меньше на
`118 861 м`, или `96,3%`). Значения получены из одной сохранённой дорожной
матрицы. Сценарий синтетический и специально чередует два удалённых кластера;
на других данных такой эффект не гарантирован. Solver вернул
`FEASIBLE_TIME_LIMIT`, поэтому доказан только выигрыш относительно FIFO на этом
входе, а не глобальная математическая оптимальность.

Безопасная проверка перед встречей, не создающая новую версию плана:

```sh
.venv/bin/python scripts/smoke_local_demo.py /private/tmp/routes-demo-20260926-customer-final-fifo.json \
  --base-url http://127.0.0.1:8000 --verify-only
```

Войти тестовым диспетчером из manifest, открыть `http://localhost:5173`,
выбрать проект `8` и дату 27 сентября. После начала смены 27 сентября не
нажимать «Рассчитать маршруты»: новая версия законно получит
`NOT_APPLICABLE_SHIFT_STARTED`, хотя уже сохранённое сравнение останется
доступным в версии `14` до её замены.

### Если локальный стенд выключился до встречи

После перезагрузки компьютера запустить Docker Desktop, затем текущий
Compose-стек, не пересчитывая маршруты:

```sh
docker compose --env-file .env.docker up -d
docker compose --env-file .env.docker ps
```

Если `http://localhost:5173` не отвечает, запустить frontend из
`/Users/pavelepanov/ship-it-frontend` в отдельном терминале:

```sh
npm run dev -- --host localhost --strictPort
```

Затем выполнить read-only smoke выше и открыть доску. Наличие `READY` и
версии `14` важнее статуса процесса: именно эти сохранённые результаты
показываются заказчику. Пароль из manifest не публиковать и не вкладывать в
слайды или скриншоты.

## Что обнаружено и исправлено при ревью

1. FIFO запрашивал всю дорожную матрицу даже при наличии всех реально нужных
   дуг в snapshot. Теперь он читает только дуги назначенных маршрутов; при
   недоступном провайдере и полном snapshot сравнение остаётся `READY`.
2. Параллельное сохранение baseline и публикация версии давали PostgreSQL
   deadlock. Порядок блокировок исправлен; тест воспроизводит конкурирующую
   публикацию, а финальный проект прошёл с первой попытки при четырёх workers.
3. Старт второго worker мог сбросить живой `RUNNING` в `FAILED`. Восстановление
   касается только попыток старше пяти минут и повторяется фоновым сканером.
4. Браузерное событие раскрытия инженерной детализации не попадало в серверный
   аудит. Добавлен авторизованный endpoint и JSON-лог без адресов и имён.
5. Клиент не восстанавливался после `BASELINE_VERSION_CHANGED`. Теперь он
   перечитывает доску и не показывает ответ старой версии.
6. Уточнены состояния и читаемость блока: скелетон, отказ от кнопки после
   исчерпания попыток, подсветка несопоставимого покрытия, горизонтальная
   прокрутка детализации и размер текста.
7. При быстром переключении дат поздний ответ старого запроса мог заменить
   доску выбранного дня. Теперь ответы проверяются по дате, версии плана и
   поколению запроса; сравнение не показывает метрики предыдущей вкладки.
   Параллельный опрос активного расчёта не прерывает уже начатую загрузку дня.
8. Ошибка первичного сохранения аналитики могла оставить успешный дневной запуск
   вообще без baseline-строки, недоступной автоматическому повтору. Теперь после
   отката частичной записи сохраняется минимальный `FAILED`-маркер с тем же
   `input_hash` и временем следующей попытки; рабочий план остаётся успешным.
   Исключения хранения логируются без SQL-параметров и адресов.
9. Мониторинг считал p50/p95/p99 только по CPU-времени FIFO-перебора и на
   реальном проекте показывал `0 мс`. Теперь он берёт полный интервал попытки
   `started_at`…`finished_at` (для исторических строк — старое поле); на
   проекте `8` получено `32 мс`, а не ноль.
10. Действие «Как считается базовый план» было под таблицей, хотя §6.2 ТЗ
    требует его справа от заголовка. Оно перенесено в шапку. Раскрытое
    описание проверено на синтетическом UI при ширине 1280, 1024, 768 и
    390 px; горизонтального переполнения нет.
11. Read-only smoke запрашивал доску с датой подготовки. После полуночи API
    отклонил бы такой диапазон как устаревший. Теперь `--verify-only` берёт
    текущие семь дней, но проверяет уже опубликованное сравнение за 27 сентября;
    отдельный тест фиксирует это поведение. Новая версия плана не создаётся.
12. В демо все 8 FIFO-переездов совпали с дугами сохранённого дорожного
    snapshot оптимизатора. В более широком QA-сценарии 7 из 35 дуг пришлось
    получить дополнительно. Теперь worker атомарно сохраняет эти дуги в
    snapshot того же `planning_run` до состояния `READY`, чтобы повтор не
    зависел от изменившихся ответов дорожного сервиса. PostgreSQL-тест
    проверяет сохранение и отсутствие deadlock при одновременной публикации.
    Уже завершённые QA-запуски не переписывались.
13. На авторизованной доске длинный логин диспетчера налезал на поля версии
    плана. Строка контекста исправлена; статус «оптимальность не доказана»
    теперь виден полностью. В детализации исправлено склонение «4 заявки».

Проверки: `297` backend-тестов с PostgreSQL, `44` frontend-теста (включая рендер
состояний сравнения, разное покрытие, длинные имена и 20 инженеров), сборка Vite,
линтер изменённых файлов, повторный read-only smoke локального проекта. В браузере
проверен тот же UI-компонент на синтетической QA-странице: список из 20
инженеров и длинное имя видны, при ширине 1024 px страница не получает
горизонтальную прокрутку. Отдельная синтетическая QA-страница прошла переключение
всех семи дат, гонку поздних ответов и загрузку дня медленнее интервала опроса
активного расчёта. QA-страницы не включаются в production build. Мониторинг
доступен командой `scripts/baseline_monitor.py`: для проекта `8` ошибок и
alert-сигналов нет.
При первоначальной проверке backend-образ сначала прошёл read-only smoke на
отдельном порту `8003`, затем занял демо-порт `8001` и повторно прошёл тот же
smoke. Старый контейнер `ship-it-backend-fifo-demo-ready-20260926` впоследствии
удалён при пересоздании Compose-стека. Текущий backend на порту `8000` прошёл
read-only smoke для той же версии плана.

В QA-проекте `10` лимит `max_jobs_per_run=1` намеренно даёт разное покрытие:
FIFO назначает от 8 до 2 заявок на последовательных датах, оптимизатор — по
одной. На всех семи датах API возвращает `coverage_comparable=false`; этот
проект подтверждает независимость дневных результатов и запрет ложного вывода
об экономии, но не используется для клиентского показа выигрыша. Для каждого
из семи дней размер сохранённого DayInput одинаков у solver и FIFO: `8, 7, 6,
5, 4, 3, 2`; у обеих сторон сумма назначенных и неназначенных равна входу.
В отдельном FIFO-аудите семи дней сохранены `35` маршрутных строк, но рабочая
версия `15` содержит ровно `8` уникальных заявок без дублирования — базовые
назначения не меняют опубликованный план. Первая
попытка QA на отдельном проекте `9` завершилась до solver с
`TRAVEL_PROVIDER_UNAVAILABLE`: пермские адреса не покрывает локальная дорожная
карта. Демо-проект `8` не менялся.

На настоящей авторизованной доске локального проекта `8` подтверждены метрики
8/8, 123,4/4,5 км, пояснение метода, раскрытие двух инженеров, переход между
26 и 27 сентября и отсутствие ошибок браузера. До утверждения 100%
соответствия для релиза остаются формальный QA-прогон всех сценариев §9 и
подключение read-only мониторинга к расписанию/оповещениям DEV и PROD.
Конфигураций развёртывания DEV/PROD в двух локальных репозиториях нет.

## Уточнение после ревью ТЗ от 26 сентября

Новый расчёт FIFO отделяет отсутствие нужной дорожной дуги в сохранённом
снимке (`BASELINE_ROUTE_UNAVAILABLE`) от временной неполноты матрицы и ошибки
провайдера. Для первого случая автоматические повторы не назначаются; экран
показывает проверку адреса и покрытия карты. Мониторинг отдельно считает такие
случаи и долю `READY` среди расчётов с доступными дугами. Исторические строки
с прежним кодом ошибки не переписываются. Сравнение проекта №8 остаётся
подготовленным сценарием показа; отсутствие дороги на проекте №11 не превращается
в искусственное расстояние или ложный вывод об экономии.
