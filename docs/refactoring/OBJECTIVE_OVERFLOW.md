# Переполнение objective: причина и текущее решение

Актуально на 21 сентября 2026 года для алгоритма `objective-range-v5`.

## Что именно переполнялось

OR-Tools RoutingModel принимает целочисленные стоимости в диапазоне знакового
`int64`. Приложение раньше упаковывало все бизнес-цели в одно число:

```text
DropCost * W_drop
+ NewEngineers * W_engineer
+ TotalDistance * W_total_distance
+ MaxEngineerDistance * W_max_distance
+ TravelTime
```

Каждый старший вес больше всей возможной суммы младших целей. Это точно сохраняет
лексикографический порядок, но произведение верхних границ быстро растёт.

На сохранённом обезличенном наборе из 16 заявок и трёх инженеров:

| Показатель | Значение |
| --- | ---: |
| Общий делитель штрафов | 1 |
| `Pmax` | 31 687 199 |
| `Dmax / Mmax` | 102 208 |
| `Tmax` | 1 264 |
| `W_drop` | 52 860 199 185 860 |
| Максимальная составная оценка | 1 674 991 703 642 182 991 999 |
| Предел `int64` | 9 223 372 036 854 775 807 |

Граница превышала предел примерно в 182 раза. Ошибка возникала до поиска и не
зависела от памяти или длительности работы solver.

## Почему уменьшение пользовательских весов не решает задачу

Числа `2500`, `25` и подобные бизнес-штрафы — только один слой оценки. После них
приложение строит веса пробега, инженеров и пропусков из доказанных верхних
границ. Простое деление с округлением может сделать два разных плана равными или
позволить младшей цели компенсировать старшую. Увеличение единицы расстояния также
снижает точность сравнения маршрутов.

Общий делитель применяется автоматически и является точным преобразованием.
На сохранённом наборе он равен единице, поэтому больше сократить числа этим
способом нельзя.

## Текущее решение

Когда единая оценка помещается в `int64`, продолжает работать прежний режим
`WEIGHTED_SINGLE_PASS`. Его формулы и результат не менялись.

Когда переполняется только общая оценка, используется
`LEXICOGRAPHIC_STAGES`. Прикладной слой заранее создаёт уровни в том же порядке,
который раньше кодировался большими штрафными диапазонами:

1. SLA-группы от просроченных до резерва;
2. аварийные заявки перед обычными внутри одной SLA-группы;
3. число пропущенных заявок внутри категории;
4. вторичный penalty внутри категории;
5. число новых инженеров;
6. общий пробег;
7. максимальный пробег одного инженера;
8. время дороги.

Для каждой пары «SLA-группа и тип приоритета» строится отдельная стоимость:

```text
Secondary(j) = точное нормализованное отличие penalty заявки от минимума группы
CountWeight = sum Secondary(j) + 1
StageDropCost(j) = CountWeight + Secondary(j)
```

`CountWeight` больше любой возможной разницы вторичных сумм. Поэтому дополнительный
пропуск всегда хуже, а при одинаковом числе пропусков сравнивается вторичный
penalty. После решения этапа его значение фиксируется равенством в следующей
модели. Финальный этап включает прежние веса инженеров, расстояния и времени.

## Почему бизнес-результат не меняется

Прежняя функция `_enforce_sla_hierarchy` строила доминирующие числовые диапазоны
для тех же категорий. Последовательное решение сравнивает тот же вектор напрямую.
Для любых двух допустимых планов отношения «лучше», «равно» и «хуже» совпадают.

Это проверяется исчерпывающим тестом: для восьми заявок с несколькими SLA-группами
и аварийными подкатегориями перебираются все 256 наборов пропусков и все 65 536
пар наборов. Знак сравнения прежней составной стоимости совпадает со сравнением
вектора этапов для каждой пары.

Hard constraints не делятся между этапами и не ослабляются. Каждая модель заново
содержит те же смены, окна, квалификации, транспорт, оборудование, доступность
дорог, обязательные заявки и защищённые назначения. Меняется только представление
целевой функции.

## Ограничение по времени

Все этапы делят прежний общий лимит дня. Результат этапа используется как стартовый
маршрут следующего. Если OR-Tools нашёл допустимое значение, но не доказал его
оптимальность, это значение разрешено зафиксировать; итог получает
`FEASIBLE_TIME_LIMIT`.

Поэтому множество математически оптимальных решений и бизнес-порядок совпадают с
однопроходной функцией, но конкретный маршрут при ограниченном времени не обязан
побитово совпасть. Это ограничение существовало и раньше: эвристический Routing
solver не обещал глобальный оптимум при истечении лимита.

## Когда расчёт всё ещё останавливается

`OBJECTIVE_RANGE_OVERFLOW` сохраняется и выдаётся до поиска, если:

- вход вызвал solver напрямую без подготовленных бизнес-этапов;
- описание этапов отсутствует или не согласовано со snapshot;
- отдельный этап либо финальная маршрутная оценка достигает предела `int64`.

В этих случаях коэффициенты и точность не уменьшаются, новый план не публикуется.

## Что сохраняется для аудита и проверяет Validator

В `objective_metrics` записываются стратегия, исходная составная граница,
границы каждого этапа, определения категорий, результаты этапов, признаки
доказанной оптимальности и зафиксированные значения. Validator независимо:

- сверяет определения со входным snapshot;
- проверяет уникальный порядок и полное однократное покрытие optional-заявок;
- пересчитывает стоимости этапов по фактически неназначенным заявкам;
- сверяет верхние границы, равенства предыдущих этапов и текущую objective;
- продолжает проверять ограничения маршрута, времена, расстояния и оборудование.

Рабочие тесты находятся в
[test_objective_overflow.py](../../tests/unit/infrastructure/test_objective_overflow.py).
Отменённый ранний двухэтапный эксперимент сохранён только как историческая запись
в [STAGED_ROUTING_FIX.md](STAGED_ROUTING_FIX.md); текущий алгоритм использует
полную последовательность бизнес-категорий.
