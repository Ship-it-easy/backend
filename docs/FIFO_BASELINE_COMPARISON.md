# Сравнение оптимального плана с FIFO

Реализация следует ТЗ из
`analytics/ТЗ_сравнение_оптимального_плана_с_базовым_FIFO_планом.docx`.
После успешного дневного Validator вместе с неизменяемым `planning_run`
атомарно создаётся задача `PENDING`. Фоновый worker стартует до переключения
актуальной версии, но публикация оптимального плана не ждёт его завершения.
Worker читает только сохранённый snapshot запуска и не восстанавливает вход по
текущим, возможно уже изменившимся заявкам и инженерам.

Полный JSON результата дополняется нормализованными строками
`planning_baseline_routes`, `planning_baseline_route_jobs` и
`planning_baseline_unassigned_jobs`. Перед сохранением отдельный валидатор
повторно проверяет порядок FIFO, выбор первого совместимого инженера, ёмкость
смен, плановые времена, дорожные дуги и агрегаты.

## Что сравнивается

Обе стороны используют один снимок дневного входа и один snapshot дорожных
расстояний. FIFO:

1. сортирует заявки по `received_at`, `ingest_sequence`, `job_id`;
2. для каждой заявки заново перебирает инженеров по `created_at`, `engineer_id`;
3. проверяет квалификацию, транспорт и остаток смены;
4. резервирует ровно 20 минут перед каждой заявкой, включая первую;
5. не использует фактическое время дороги, оборудование и окно как запрет;
6. считает попадание в окно отдельно, по плановому началу включительно;
7. считает расстояние от старта до первой заявки и между заявками, без возврата.

Основные метрики: назначенные заявки, попадание в окна, активные инженеры и
общий пробег. Экономия или победитель показываются только при
`coverage_comparable=true`, то есть когда множества назначенных заявок
совпадают. При разном покрытии UI показывает числа и явное предупреждение, но
не делает маркетинговый вывод.

Ошибка baseline не отменяет оптимальный результат. Для неё сохраняется
`FAILED`, а для текущего дня после старта первой смены —
`NOT_APPLICABLE_SHIFT_STARTED`. Старые версии без расчёта возвращают
`NOT_AVAILABLE_LEGACY_PLAN`. Для `FAILED` сохраняются номер попытки и время
следующего допустимого повтора. Повтор использует неизменяемый snapshot
исходного `planning_run`, обновляет ту же строку результата и не запускает
оптимальный solver повторно. Всего допускается три попытки, включая первую.
После рестарта действительно зависший `RUNNING` (старше пяти минут) возвращается
в retry-очередь; живой расчёт другого Gunicorn worker не сбрасывается.
Полученные оптимизатором дорожные дуги сохраняются на запуске и повторно
используются worker; провайдер вызывается только при отсутствии дуги,
фактически пройденной контрольным FIFO-маршрутом. Смена представления дорожного
аудита зафиксирована версией алгоритма `FIFO_V2`. Дополнительно полученные
FIFO-дуги сохраняются в дорожном snapshot того же дневного запуска атомарно с
`READY`, поэтому следующий повтор использует зафиксированные значения.

## API

Для владельца или диспетчера выбранного района:

```http
GET /api/projects/{project_id}/planning/current/days/{date}/comparison
```

Клиент передаёт `plan_version_id` query-параметром. Если за время запроса
опубликована другая версия, API отвечает `BASELINE_VERSION_CHANGED`, и клиент
перечитывает актуальную доску.

Для ручного повтора результата в состоянии `FAILED`:

```http
POST /api/projects/{project_id}/planning/runs/{planning_run_id}/baseline/retry
```

Операция доступна владельцу и диспетчеру, идемпотентна для уже выполняющегося
или завершённого результата и не создаёт дубликаты маршрутов или сравнений.

Поэтапное включение управляется флагами
`BASELINE_COMPARISON_ENABLED` на backend и
`VITE_BASELINE_COMPARISON_ENABLED` на frontend. Оба включены по умолчанию;
значение `false` отключает соответственно расчёт и отображение, не затрагивая
публикацию оптимального плана.

Совместимый однопроектный маршрут:

```http
GET /api/project/planning/current/days/{date}/comparison
```

В ответе нет внутренних ID инженеров. Поля `baseline`, `optimized`, `delta` и
`engineers` берутся из сохранённого сравнения конкретного запуска.

## Подготовка демонстрации на 27 сентября 2026

Сначала применить миграцию и пересобрать backend/frontend. Затем создать
отдельный безопасный проект, не меняющий существующие демо:

```sh
.venv/bin/python scripts/prepare_local_demo.py \
  --date 2026-09-26 \
  --suffix=-customer-final \
  --baseline-showcase
```

Сценарий создаёт восемь автомобильных заявок в двух разнесённых кластерах на
следующий день. Короткая уже завершённая смена текущего дня нужна только для
readiness; полноценные смены начинаются со следующего дня. Поэтому сравнение
можно честно рассчитать в любое время дня подготовки и показать на вкладке
даты из `comparison_date` в manifest.
Порядок поступления чередует кластеры, поэтому честный FIFO возит обе машины
через город, а оптимизатор группирует точки географически. В смену помещаются
по четыре заявки на машину у обоих алгоритмов: покрытие должно совпасть, и
разница пробега будет корректно показана как экономия.

Подготовить демонстрацию **26 сентября**, до начала смены 27 сентября:

1. войти диспетчером из напечатанного manifest;
2. убедиться, что Valhalla готова и readiness зелёный;
3. один раз нажать «Рассчитать маршруты» и дождаться публикации и состояния
   `READY` для `comparison_date`;
4. выбрать дату `comparison_date` из manifest и открыть блок «Сравнение с
   базовым планом»;
5. показать одинаковое число назначений, меньший пробег и раскрыть
   «Пробег по инженерам»;
6. открыть карту: FIFO-метрики объясняют контрольный сценарий, опубликованные
   колонки показывают географически сгруппированный оптимальный маршрут.

Для обычных данных расчёт текущего дня после начала смены по ТЗ не сравнивается;
демо-сценарий намеренно показывает следующий день и не обходит это правило.
На показе **27 сентября** используйте уже опубликованную версию и не нажимайте
«Рассчитать маршруты» повторно: после начала смены новый снимок текущего дня
законно даст `NOT_APPLICABLE_SHIFT_STARTED`. Безопасная проверка без пересчёта:

```sh
.venv/bin/python scripts/smoke_local_demo.py /private/tmp/routes-demo-20260926-customer-final-fifo.json \
  --base-url http://127.0.0.1:8001 --verify-only
```

Если стенд перезапускался, точный порядок восстановления существующих
контейнеров и frontend без нового расчёта указан в
`docs/FIFO_BASELINE_DEMO_REVIEW.md`. Для Vite на демо обязательно
`VITE_API_URL=http://127.0.0.1:8001`: без переменной dev-клиент обращается к
другому backend на порту `8000`.

Локальный финальный пример: проект `8`, версия `14`, запуск `41`, 27 сентября;
оба плана назначили одинаковые `8/8` заявок и задействовали двух инженеров.
Контрольный FIFO — `123,381 км`, оптимизатор — `4,520 км`, разница —
`118,861 км` (`96,3%`). Это иллюстрация на синтетическом сценарии с
чередующимися удалёнными кластерами, а не обещание такого эффекта на любых
данных. Обе величины взяты из одной сохранённой дорожной матрицы. Оптимальный
solver пометил результат как `FEASIBLE_TIME_LIMIT`: найденный план лучше FIFO
по пробегу при равном покрытии, но математическая глобальная оптимальность не
доказана. На демо не следует утверждать обратное.

## Эксплуатационный контроль

Состояние и диагностические поля каждой попытки хранятся в
`planning_baseline_results`; сопоставимость — в
`planning_plan_comparisons`. Для дашборда доступны JSON-события
`baseline_calculation_*`, `baseline_retry_scheduled`,
`planning_comparison_viewed` и `planning_comparison_engineers_expanded`.
В них есть проект, запуск, дата, версия плана и
алгоритма, hash входа, размер входа и длительность. Поэтому из журналов можно
строить p50/p95/p99, задержку появления сравнения, частоты retry и ошибок
матрицы, а из БД — доли `READY`/`FAILED`/`NOT_APPLICABLE`, исчерпанные повторы и
долю разного покрытия. Только агрегированные показатели без адресов и имён
выдаёт read-only команда:

```sh
.venv/bin/python scripts/baseline_monitor.py --window-hours 24
```

Её нужно запускать по расписанию на DEV и PROD; код выхода `2` означает
alert и содержит JSON-коды при росте `FAILED`, несовпадении `input_hash` или
разных `result_hash` для одинаковых `input_hash + algorithm_version +
travel_matrix_hash`. Команда также отдаёт размеры входа, число retry,
исчерпанные повторы, ошибки матрицы, долю различий покрытия и задержку
появления сравнения после публикации. Само подключение к корпоративному
сборщику метрик/оповещений настраивается в окружении развёртывания.

Контрольная нагрузочная проверка выполняется на 100 заявках и 20 инженерах без
ожидания внешнего провайдера; релизный порог — p95 не более 2 секунд.
