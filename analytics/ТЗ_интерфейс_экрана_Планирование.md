# Техническое задание на интерфейс экрана Планирование и объяснение маршрутов

Версия: 1.1  
Дата: 17 сентября 2026 года

## 1. Название задачи

Переработать экран «Планирование» для просмотра актуального семидневного плана, запуска расчёта маршрутов и объяснения назначенных и неназначенных заявок.

## 2. Бизнес-описание

Сейчас экран показывает параметры горизонта и историю запусков, но не позволяет диспетчеру быстро ответить на три основных вопроса: какие заявки назначены на выбранный день, как они распределены между инженерами и почему часть заявок осталась неназначенной. Из-за этого результат оптимизации трудно проверить и использовать в ежедневной работе.

После доработки диспетчер и владелец проекта видят одну актуальную опубликованную версию плана. На экране доступны семь календарных дней, начиная с текущей даты проекта. Для выбранного дня заявки отображаются по колонкам инженеров в порядке маршрута, а последний столбец содержит все заявки, которые участвовали в дневном расчёте, но не были назначены на этот день. Карточка заявки даёт краткое объяснение результата, полное объяснение открывается в боковой панели.

Ручной запуск выполняется кнопкой «Рассчитать маршруты». Он использует существующий механизм полного расчёта от текущей даты и сразу публикует валидный результат по правилам действующих ТЗ. Экран не вводит черновики и отдельную публикацию.

## 3. Метрика успеха

Функциональность считается успешной, если после релиза выполняются следующие показатели:

- не менее 95 процентов успешных открытий доски отрисовывают актуальный план не дольше двух секунд без учёта времени самого расчёта;
- для 100 процентов заявок из сохранённого входа дневного solver существует ровно один исход на эту дату: назначена конкретному инженеру либо отображена в колонке «Неназначенные заявки»;
- для 100 процентов назначенных и неназначенных карточек сохранён и показан хотя бы один человекочитаемый код объяснения;
- число обращений к истории запусков или сторонним выгрузкам для проверки текущего плана сокращается; базовое значение фиксируется аналитикой до релиза, целевое сокращение через месяц составляет 50 процентов;
- не менее 90 процентов ручных запусков, которые завершились валидным результатом, автоматически отражаются на экране без ручной перезагрузки страницы.

Источники данных: серверные логи, таблицы версий плана и результатов дня, события интерфейса `planning_board_opened`, `planning_day_selected`, `planning_run_started`, `planning_run_finished`, `planning_job_details_opened`, а также технические метрики времени ответа API.

## 4. Техническое задание

### 4.1. Цель и границы задачи

В рамках задачи требуется:

1. заменить текущий экран «Планирование» новой доской маршрутов;
2. дать владельцу и диспетчеру возможность запустить полный расчёт маршрутов;
3. показать семь дат от текущего дня проекта;
4. показать полный результат дневного solver для выбранной даты;
5. объяснить назначение каждой заявки и причины неназначения;
6. поддержать состояния готовности данных, расчёта, успешного результата, частичного результата, ошибки и отсутствия плана;
7. подготовить серверный read model или эквивалентный API, который не заставляет интерфейс восстанавливать причины по текущим справочникам.

В задачу не входят:

- изменение алгоритмов OR-Tools, штрафов, каскада и правил динамического пересчёта;
- ручное перетаскивание заявок и переназначение между инженерами;
- изменение логики, состава полей или интерфейса существующего раздела «Параметры»;
- история запусков на основном экране;
- отдельные состояния «черновик» и «опубликован»;
- мобильная и планшетная версии;
- отображение дней после седьмого дня на этой странице.

### 4.2. Связь с действующими требованиями

Расчёт, публикация, защита текущих маршрутов, каскад по дням, реакция на создание и отмену заявки, недоступность инженера, аварийный приоритет и целевая функция работают по действующим отдельным ТЗ. Этот документ задаёт только запуск из интерфейса, состав отображаемых данных и правила объяснения результата.

Если между этим документом и алгоритмическим ТЗ возникает расхождение, алгоритмическое ТЗ определяет состав расчёта, а этот документ определяет представление уже сохранённого результата. Интерфейс не вычисляет назначение и не выводит причин, которых нет в сохранённом результате расчёта.

### 4.3. Термины

| Термин | Определение |
| --- | --- |
| Текущая дата проекта `D0` | Календарная дата в часовом поясе проекта. Она не определяется часовым поясом браузера. |
| Актуальная версия плана | Последняя успешно и атомарно опубликованная версия проекта. Черновых версий нет. |
| Результат дня | Сохранённый результат отдельного дневного запуска solver внутри актуальной версии плана. |
| Вход дня `DayInput` | Полный зафиксированный набор заявок, переданный в дневной solver для выбранной даты. |
| Назначенная заявка | Заявка из `DayInput`, которую дневной solver включил в маршрут инженера на эту дату. |
| Неназначенная заявка дня | Заявка из `DayInput`, которую дневной solver не назначил на эту дату. Она может быть назначена более поздним дневным запуском. |
| Не назначена в горизонте | Заявка, для которой после завершения всего каскада не найдено назначения до максимальной даты горизонта. |
| Отменённая заявка | Заявка со статусом `CANCELLED`. Она показывается как факт в ранее назначенном месте, но не входит в активную последовательность маршрута после пересчёта. |
| Объяснение | Набор сохранённых кодов и параметров, на основании которых сервер формирует краткий и полный человекочитаемый текст. |

### 4.4. Пользователи и права

Экран доступен владельцу проекта и диспетчеру. Обе роли могут:

- просматривать актуальный план всех инженеров проекта;
- выбирать любой из семи отображаемых дней;
- открывать полную информацию и объяснение по заявке;
- запускать ручной расчёт кнопкой «Рассчитать маршруты».

Инженер не имеет доступа к этому экрану и продолжает видеть только собственные назначения в своём кабинете. Все API проверяют роль и `project_id`; данные другого проекта не возвращаются.

### 4.5. Структура экрана

Экран строится сверху вниз в следующем порядке.

#### 4.5.1. Заголовок и действие

- Заголовок: «Планирование».
- Основная кнопка: «Рассчитать маршруты».
- Рядом показывается только компактный индикатор готовности исходных данных. В нормальном состоянии текст индикатора: «Данные готовы».
- Карточки «Дата запуска», «Начальный горизонт», «Максимальный горизонт», блок параметров и история запусков удаляются с основного экрана.
- Кнопка «Параметры» сохраняется рядом с кнопкой расчёта. Её существующие логика, права доступа, состав полей, переходы и результат сохранения не изменяются этой задачей.
- Отдельной кнопки «Опубликовать» нет.

Нажатие «Рассчитать маршруты» сразу создаёт ручной полный запуск без модального подтверждения. Расчёт начинается с `D0`, использует действующий каскад и после валидации атомарно публикует валидный результат.

Если обязательные исходные данные не готовы, индикатор меняется на «Данные не готовы», кнопка блокируется. По нажатию на индикатор открывается список конкретных проблем со ссылками на соответствующие разделы: нет типов работ, инженеров, смен, координат адресов, дорожной матрицы или других обязательных данных, определённых алгоритмическими ТЗ.

#### 4.5.2. Состояние ручного расчёта

После запуска:

- кнопка становится недоступной и получает текст «Расчёт выполняется»;
- под верхней строкой появляется тонкая полоса состояния с временем начала и текущей фазой, например «Подготовка данных», «Расчёт 18.09», «Проверка результата», «Публикация»;
- предыдущая актуальная версия плана остаётся видимой и помечается текстом «Показан предыдущий план до завершения расчёта»;
- повторный запуск из той же страницы невозможен, пока активен расчёт проекта;
- отмена запущенного расчёта в этой задаче не поддерживается.

После успешной публикации доска автоматически обновляется, выбранная дата сохраняется, если она всё ещё входит в диапазон `D0…D0+6`. При ошибке предыдущий план остаётся актуальным, кнопка снова доступна, а над доской показывается сообщение с краткой причиной и действием «Повторить».

#### 4.5.3. Переключатель семи дней

Под кнопкой расположены семь одинаковых кнопок дат:

- диапазон: `D0`, `D0+1`, …, `D0+6`;
- дата вычисляется в часовом поясе проекта;
- при первом открытии выбран `D0`;
- каждая кнопка показывает день недели, число и месяц, количество назначенных и неназначенных заявок дня;
- текущий день имеет метку «Сегодня»;
- выбранная дата выделяется синим фоном и не зависит от метки «Сегодня»;
- после наступления полуночи диапазон сдвигается при следующем обновлении страницы или получении новой версии;
- навигации к восьмому и последующим дням на этом экране нет.

Счётчики дат берутся из сохранённого результата дня. Отменённые заявки не входят в количество назначенных и неназначенных, но при их наличии на кнопке может отображаться отдельный нейтральный счётчик отмен.

#### 4.5.4. Контекст актуального результата

Над доской компактно показываются:

- дата и время последней успешной публикации в часовом поясе проекта;
- причина запуска: вручную, ночью, новая заявка, отмена заявки или изменение доступности инженера;
- инициатор для ручного запуска;
- номер версии плана;
- статус результата: `SUCCESS`, `PARTIAL` или `FEASIBLE_TIME_LIMIT` в человекочитаемом виде.

История прошлых версий на основном экране не показывается. Служебные идентификаторы пользователю не выводятся.

#### 4.5.5. Поиск и фильтры

Перед колонками доступны:

- поиск по адресу и типу работ;
- фильтр «Обычная / Авария»;
- фильтр по статусу заявки;
- фильтр «Все / Назначенные / Неназначенные».

Фильтры влияют только на видимые карточки выбранной даты и не меняют сохранённый план. Счётчики на кнопках дат остаются полными; рядом с заголовком доски при фильтрации показывается «Показано X из Y».

### 4.6. Доска маршрутов

#### 4.6.1. Колонки инженеров

Для выбранной даты создаётся отдельная колонка для каждого инженера, который:

- имеет смену на эту дату; или
- имеет назначенную, выполняемую, выполненную либо отменённую заявку, относящуюся к этой дате актуальной версии.

Сначала показываются инженеры с активными назначениями, затем инженеры без активных назначений; внутри группы сортировка выполняется по имени. Заголовок колонки содержит имя, время смены, количество активных заявок, суммарную длительность маршрута и пробег, если метрики сохранены.

Если у инженера нет активных заявок, в колонке показывается «Нет назначенных заявок» и его часы смены. Недоступный инженер, который сохраняет защищённую выполняемую заявку по правилам динамического пересчёта, остаётся на доске с меткой «Недоступен».

Колонки имеют фиксированную минимальную ширину и прокручиваются горизонтально. Заголовки колонок остаются видимыми при вертикальной прокрутке. Последняя колонка «Неназначенные заявки» закрепляется справа на десктопе, пока ширина окна позволяет избежать перекрытия содержимого.

#### 4.6.2. Полнота результата выбранного дня

Для каждой заявки из `DayInput` интерфейс обязан показать ровно один исход выбранного дневного запуска:

- `ASSIGNED` — одна карточка в колонке назначенного инженера;
- `UNASSIGNED_TODAY` — одна карточка в колонке «Неназначенные заявки».

Одна заявка не может одновременно находиться в колонке инженера и в «Неназначенных» для одной даты и одной версии. Заявка, не назначенная 17 сентября, но назначенная 18 сентября, показывается:

- 17 сентября — в «Неназначенных» с меткой «Перенесена на 18.09»;
- 18 сентября — в колонке назначенного инженера.

Такое повторение между разными датами является ожидаемым и отражает последовательные дневные запуски каскада.

Если дата не рассчитывалась в актуальной версии, доска показывает «Для этой даты нет результата расчёта», а не пустые колонки, которые можно принять за отсутствие заявок.

#### 4.6.3. Отменённые заявки

Отменённая заявка остаётся видимой на дате и у инженера, где она была назначена перед отменой, с приглушённым оформлением и статусом «Отменена». Она помещается после активной последовательности в группе «Отменённые» и не получает порядковый номер активного маршрута.

Карточка показывает время отмены и автора, если эти данные доступны. Отменённая заявка не входит в `DayInput` нового расчёта, счётчики активных назначений и метрики маршрута. Если заявка была отменена до любого назначения, она не появляется на доске планирования и остаётся доступна в реестре заявок.

#### 4.6.4. Содержание карточки назначенной заявки

Карточка содержит:

- порядковый номер в маршруте;
- плановое время начала и окончания;
- статус заявки;
- метку «Авария» для аварийной заявки;
- полный адрес;
- тип работ;
- длительность работ;
- крайний срок SLA и признак просрочки;
- требуемое оборудование в компактном виде;
- одну основную причину результата;
- действие «Почему назначена» или открытие карточки целиком.

Между соседними активными карточками показываются плановое время в пути и расстояние, если эти значения сохранены в маршруте. Карточки сортируются по сохранённой позиции маршрута, затем по плановому времени. Для текущего дня показываются также заявки в статусах «В работе» и «Выполнена».

#### 4.6.5. Колонка неназначенных заявок

Колонка содержит все `UNASSIGNED_TODAY` из сохранённого результата выбранного дня. Внутри неё создаются две группы:

1. «Перенесены» — заявка не назначена на выбранный день, но в этой же актуальной версии получила назначение на более позднюю дату. На карточке показывается дата будущего назначения.
2. «Не назначены в горизонте» — заявка осталась без назначения после завершения каскада. На карточке показывается итоговый статус и причины.

Сортировка внутри групп:

1. просроченные;
2. аварийные;
3. по ближайшему SLA;
4. по времени создания.

Карточка неназначенной заявки содержит адрес, тип и длительность работ, SLA, аварийность, краткую причину и действие «Почему не назначена».

### 4.7. Объяснение решений solver

#### 4.7.1. Общий принцип

Объяснения формирует backend на основании snapshot и результата конкретного дневного запуска. Интерфейс получает готовые коды, параметры и человекочитаемый текст. Нельзя повторно оценивать заявку по текущим справочникам: квалификации, смены, оборудование и дорожные данные могли измениться после публикации.

Объяснение разделяет три разных факта:

1. **Допустимость** — инженер удовлетворяет жёстким ограничениям заявки.
2. **Факторы целевой функции** — SLA, аварийность, пробег, использование исполнителя и другие сохранённые компоненты влияли на оптимизацию.
3. **Результат оптимизации** — solver выбрал этот допустимый вариант среди совместимых вариантов либо оставил заявку неназначенной.

Фраза «назначена ближайшему инженеру» допустима только при наличии сохранённого сравнения, которое это доказывает. В остальных случаях используется нейтральная формулировка: «Выбрано оптимизатором среди допустимых вариантов».

#### 4.7.2. Краткое объяснение назначенной заявки

На карточке показывается одна основная причина. Примеры:

- «Аварийная заявка с высоким приоритетом»;
- «Крайний срок сегодня»;
- «Просрочена на 2 дня»;
- «Вписана в смену и временное окно»;
- «Выбрано оптимизатором среди допустимых вариантов».

Не следует выводить как единственную причину «Есть квалификация»: это объясняет допустимость, но не доказывает, почему выбран именно этот инженер.

#### 4.7.3. Полное объяснение назначенной заявки

По нажатию открывается правая боковая панель. Она содержит:

- основные данные заявки;
- выбранного инженера, дату, позицию и плановое время;
- подтверждённые жёсткие ограничения: квалификации, оборудование, транспорт, смена, временное окно;
- факторы приоритета: SLA, просрочка, аварийный бонус;
- маршрутные факторы: добавленное время или расстояние, если они рассчитаны и сохранены;
- число допустимых инженеров;
- итоговую формулировку результата;
- технические компоненты objective в сворачиваемом разделе, доступном владельцу и диспетчеру.

Числовые штрафы и внутренние коды не показываются на самой карточке.

#### 4.7.4. Объяснение неназначенной заявки

Если нет ни одного допустимого инженера, панель перечисляет причины исключения по инженерам или агрегированно: нет квалификации, оборудования, нужного транспорта, смены либо допустимого временного окна.

Если допустимые инженеры есть, но заявка не вошла в маршрут, интерфейс показывает только подтверждённую причину:

- «Не помещается в доступный остаток смены»;
- «Невозможно соблюсти временное окно с учётом дороги»;
- «Оборудование уже распределено другим маршрутам»;
- «Solver выбрал оставить заявку неназначенной в рамках целевой функции»;
- «Расчёт завершён по лимиту времени, допустимое назначение не найдено»;
- «Горизонт исчерпан».

Запрещены неподтверждённые формулировки «слишком далеко», «менее выгодна» или «низкий приоритет», если соответствующее сравнение не сохранено.

#### 4.7.5. Минимальный справочник кодов причин

| Код | Результат | Текст по умолчанию | Обязательные параметры |
| --- | --- | --- | --- |
| `OPTIMIZER_SELECTED` | Назначена | Выбрано оптимизатором среди допустимых вариантов | `eligible_engineers_count` |
| `EMERGENCY_PRIORITY` | Назначена | Аварийная заявка с высоким приоритетом | `emergency_bonus` |
| `OVERDUE_PRIORITY` | Назначена | Просроченная заявка получила повышенный приоритет | `overdue_days` |
| `SLA_DUE_TODAY` | Назначена | Крайний срок сегодня | `sla_date` |
| `HARD_CONSTRAINTS_MATCHED` | Назначена | Заявка соответствует смене и требованиям инженера | перечень проверок |
| `NO_ELIGIBLE_ENGINEER` | Не назначена | Нет инженера, удовлетворяющего обязательным требованиям | агрегированные причины |
| `NO_QUALIFICATION` | Не назначена | Нет инженера с требуемой квалификацией | квалификации |
| `NO_EQUIPMENT` | Не назначена | Недостаточно доступного оборудования | тип и требуемое количество |
| `NO_SHIFT` | Не назначена | Нет доступной смены | дата |
| `NO_TRANSPORT` | Не назначена | Нет подходящего транспорта | требование |
| `TIME_WINDOW_CONFLICT` | Не назначена | Невозможно соблюсти временное окно | окно и ближайший допустимый интервал |
| `SHIFT_CAPACITY_EXCEEDED` | Не назначена | Работа не помещается в доступный остаток смены | требуемые минуты |
| `ROUTE_INFEASIBLE` | Не назначена | Не найден допустимый маршрут с учётом дороги | дата |
| `DROPPED_BY_OBJECTIVE` | Не назначена | Solver оставил заявку неназначенной в рамках целевой функции | итоговый penalty |
| `TIME_LIMIT_NO_ASSIGNMENT` | Не назначена | Расчёт завершён по лимиту времени | лимит и статус solver |
| `HORIZON_EXHAUSTED` | Не назначена | Заявка не назначена до конца горизонта | конечная дата горизонта |

Справочник расширяемый. Для неизвестного кода интерфейс показывает безопасный текст «Подробная причина недоступна» и отправляет событие мониторинга; сырой код пользователю не выводится.

### 4.8. Состояния экрана

#### Данные готовы, план существует

Показываются семь дат, контекст версии, фильтры и доска выбранного дня.

#### Данные не готовы

Кнопка расчёта блокируется. Индикатор открывает список конкретных проблем. Если ранее опубликованный план существует, он остаётся доступным с пометкой, что новый расчёт сейчас невозможен.

#### Расчёт выполняется

Старый план остаётся видимым. Кнопка блокируется, показывается фаза и время старта. После публикации данные обновляются автоматически.

#### План отсутствует

Если данные готовы, показывается пустое состояние «План ещё не рассчитан» и активная кнопка расчёта. Если данных нет, показывается список проблем.

#### Частичный результат

Валидная часть опубликована и отображается. Над доской показано: «Часть заявок не назначена». Все неназначенные находятся в последней колонке с причинами.

#### Результат по лимиту времени

План отображается, но над доской показывается: «Найден допустимый план, оптимальность не доказана». Карточки, для которых причина ограничена лимитом, получают соответствующий код.

#### Ошибка расчёта

Предыдущая версия остаётся видимой. Показываются краткая причина, время ошибки и «Повторить». Технический stack trace в UI не выводится.

#### Нет заявок на дату

Колонки инженеров с рабочими сменами остаются видимыми и показывают пустое состояние. Колонка неназначенных также показывает «Нет неназначенных заявок».

### 4.9. Обновление и конкурентные изменения

- Экран получает уведомление или периодически проверяет `current_plan_version_id`.
- При появлении новой версии данные обновляются целиком, чтобы карточки разных версий не смешивались.
- Выбранная дата и фильтры сохраняются при обновлении.
- Если пользователь открыл боковую панель заявки, а заявка изменилась в новой версии, панель обновляется и показывает метку «План обновлён».
- При смене `D0` открытая дата сохраняется, если входит в новый диапазон; иначе выбирается новый `D0`.
- Ручной, ночной и автоматический запуск одного проекта используют существующее правило одного активного расчёта. Интерфейс подключается к уже активному запуску, а не создаёт второй.

### 4.10. Данные и хранение

Для корректного интерфейса необходимо хранить либо сформировать эквивалентный неизменяемый read model актуальной версии:

#### `planning_day_results`

- `id`;
- `project_id`;
- `plan_version_id`;
- `planning_date`;
- `solver_status`;
- `day_input_hash`;
- `assigned_count`;
- `unassigned_count`;
- `cancelled_visible_count`;
- `created_at`.

Уникальность: `(plan_version_id, planning_date)`.

#### `planning_day_job_results`

- `day_result_id`;
- `job_id`;
- `outcome`: `ASSIGNED` или `UNASSIGNED_TODAY`;
- `engineer_id`, `route_position`, `planned_start_at`, `planned_end_at` для назначения;
- `later_assignment_date`, если эта заявка назначена более поздним днём той же версии;
- `final_horizon_outcome`;
- `primary_reason_code`;
- `reason_payload`;
- snapshot отображаемых полей заявки.

Уникальность: `(day_result_id, job_id)`. Ограничение базы или Validator не позволяет сохранить одновременно два исхода одной заявки.

#### `planning_explanations`

- ссылка на `planning_day_job_result`;
- `reason_code`;
- `category`: `ELIGIBILITY`, `PRIORITY`, `ROUTE`, `OUTCOME`;
- `severity`;
- `display_order`;
- структурированный `parameters`;
- версия шаблона текста.

#### `planning_cancelled_job_snapshots`

Хранит снимок отменённой заявки, её последнюю дату, инженера и позицию до отмены, автора и время отмены. Запись используется только для визуального следа и не подмешивается во вход solver.

Снимки должны быть связаны с `project_id` и `plan_version_id`. Объяснения и отображаемые значения не изменяются задним числом при редактировании справочников.

### 4.11. API

Названия маршрутов могут быть адаптированы к соглашениям проекта; контракт должен обеспечивать следующее поведение.

#### Получить сводку семи дней

`GET /api/projects/{project_id}/planning/board?from=D0&days=7`

Ответ содержит:

- `project_date`, `timezone`;
- текущий `plan_version` и статус активного запуска;
- готовность данных и список проблем;
- семь дней со счётчиками;
- данные выбранного сервером дня могут быть включены в первый ответ.

#### Получить выбранный день

`GET /api/projects/{project_id}/planning/board/{date}?plan_version_id={current}`

Ответ содержит колонки инженеров, активные назначения, отменённые снимки, неназначенные группы, объяснения для карточек и доступные фильтры. API возвращает `409 VERSION_CHANGED`, если запрошенная версия уже не актуальна; клиент затем перезагружает доску целиком.

#### Получить полное объяснение

`GET /api/projects/{project_id}/planning/day-results/{day_result_id}/jobs/{job_id}/explanation`

Ответ содержит snapshot заявки, выбранный исход, список проверок, факторов и причин. Результат относится к конкретной версии и дате.

#### Запустить ручной расчёт

`POST /api/projects/{project_id}/planning/runs`

Тело: `{ "trigger": "MANUAL" }`. Ответ: `202 Accepted`, идентификатор запуска и текущее состояние. Повторный запрос при активном расчёте возвращает существующий активный запуск либо `409 RUN_ALREADY_ACTIVE` с его идентификатором.

#### Получить состояние запуска

`GET /api/projects/{project_id}/planning/runs/{run_id}`

Ответ содержит статус, фазу, время старта, дату текущего дневного шага и безопасное описание ошибки. Допустима замена polling на серверные события.

### 4.12. Валидация результата для интерфейса

Перед публикацией Validator дополнительно проверяет:

1. для каждого `DayInput.job_id` существует один `planning_day_job_result`;
2. `ASSIGNED` содержит инженера, дату, позицию и время;
3. `UNASSIGNED_TODAY` содержит хотя бы один outcome reason;
4. заявка не дублируется в двух колонках одного дня;
5. порядок карточек совпадает с сохранённым маршрутом;
6. `later_assignment_date` ссылается на реальное назначение этой же версии;
7. сумма `assigned_count` и `unassigned_count` равна размеру `DayInput`;
8. отменённые снимки исключены из `DayInput` и активных метрик;
9. все человекочитаемые тексты можно построить из известной версии шаблонов.

Версия, не прошедшая эти проверки, не публикуется. Предыдущая версия остаётся актуальной.

### 4.13. Контрольные примеры

#### Пример 1. Заявка назначена сегодня

В `DayInput` 17 сентября входят A, B и C. Solver назначил A и B Ивану Петрову, C — Анне Смирновой. На вкладке 17 сентября отображаются три карточки в двух инженерных колонках; колонка неназначенных пуста. Для A основная причина — «Крайний срок сегодня», в панели дополнительно показаны совпадение квалификации, оборудование и итог optimizer.

#### Пример 2. Заявка перенесена на завтра

В `DayInput` 17 сентября входят A и X. Solver назначил A, а X оставил `UNASSIGNED_TODAY`. Каскад назначил X на 18 сентября. На вкладке 17 сентября X находится в группе «Перенесены» с меткой «Назначена 18.09». На вкладке 18 сентября X находится в маршруте инженера.

#### Пример 3. Заявка не назначена в горизонте

Для Y нет инженера с требуемой квалификацией. На каждой дате, где Y фактически входила в `DayInput`, она отображается в неназначенных с причиной дневного результата. После конца каскада её карточка содержит метку «Не назначена в горизонте» и итоговую причину `NO_QUALIFICATION`.

#### Пример 4. Отмена назначенной заявки

Заявка B была второй у Петрова 17 сентября, затем отменена. После динамического пересчёта активный маршрут строится без B. На доске B остаётся внизу колонки Петрова в группе «Отменённые», не имеет активного номера и не входит в пробег или счётчик назначенных.

#### Пример 5. Новый расчёт выполняется

На экране показана версия 24. Диспетчер нажимает «Рассчитать маршруты». Версия 24 остаётся видимой, кнопка блокируется, отображается фаза. После публикации версии 25 выбранная дата остаётся 19 сентября, все колонки заменяются атомарно данными версии 25.

### 4.14. Пограничные случаи

- Если инженеров больше, чем помещается по ширине, работает горизонтальная прокрутка; список заявок внутри колонки не получает отдельную горизонтальную прокрутку.
- Если имя инженера длинное, оно переносится максимум на две строки, полное имя доступно в подсказке.
- Если адрес длинный, в карточке показываются две строки с раскрытием полного значения в панели.
- Если нет сохранённого расстояния или времени в пути, соответствующий элемент не рисуется и не заменяется нулём.
- Если заявка имеет несколько причин, карточка показывает одну по приоритету, панель — все.
- Если код причины неизвестен текущей версии frontend, показывается безопасный fallback и регистрируется ошибка.
- Если заявка обновлена после snapshot, доска показывает snapshot плана, а панель дополнительно сообщает, что текущие данные заявки изменились.
- Если план опубликован на 30 дней, экран всё равно показывает только `D0…D0+6`.
- Если выбранный день имеет `PARTIAL`, это не скрывает назначенную валидную часть.
- Если `D0` сменился во время активного расчёта, поведение публикации определяется действующим правилом `STALE_SNAPSHOT`; UI продолжает показывать прежний план до нового результата.

### 4.15. Ограничения и производительность

- Поддерживается десктоп шириной от 1280 пикселей. Для меньшей ширины допускается горизонтальная прокрутка всей рабочей области; отдельный адаптивный дизайн не входит в задачу.
- Первый ответ сводки не должен содержать полные объяснения всех карточек. Полная панель загружается по требованию.
- Для дня до 20 инженеров и 100 заявок интерфейс должен сохранять плавную прокрутку; допускается виртуализация карточек.
- Смена фильтра не вызывает повторного solver и по возможности выполняется локально на данных выбранного дня.
- Все даты и время передаются с timezone или в UTC и отображаются в часовом поясе проекта.

### 4.16. Риски и меры

| Риск | Последствие | Мера |
| --- | --- | --- |
| UI восстанавливает причины из текущих справочников | Объяснение не соответствует опубликованному плану | Сохранять snapshot и explanation payload в версии плана |
| «Почему назначена» смешивает допустимость и оптимальность | Пользователь получает ложное объяснение | Разделить проверки, факторы и итог solver |
| Не сохраняется полный `DayInput` | Невозможно доказать полноту колонки неназначенных | Хранить `day_input_hash` и один исход на каждую заявку |
| Горизонтальный board становится нечитаемым | Диспетчер теряет контекст инженеров | Минимальная ширина колонок, sticky headers, закреплённая колонка неназначенных |
| Новая версия подмешивается к старой | На экране противоречивый маршрут | Загружать и заменять версию атомарно |
| Причина `DROPPED_BY_OBJECTIVE` выглядит как точный диагноз | Неверная причинность | Использовать нейтральный текст без неподтверждённых сравнений |
| Отменённая заявка искажает активный маршрут | Ошибочные счётчики и пробег | Хранить и отображать её отдельным неактивным снимком |

## 5. Предварительное техническое решение разработчика

Разработчику до первого груминга требуется подтвердить:

- место формирования read model дневного результата;
- способ хранения полного `DayInput` и объяснений;
- интеграцию с текущими `planning_runs`, `plan_versions`, маршрутами и неназначенными заявками;
- способ доставки обновления версии на экран: polling, SSE или WebSocket;
- лимиты ответа выбранного дня и необходимость виртуализации;
- формат версионированных шаблонов причин;
- миграции и backfill для последней существующей версии плана;
- поведение API при отсутствии старых explanation payload.

Предпочтительное решение: после Validator создавать неизменяемый read model каждой даты в той же транзакции, что и публикация `plan_version`. Это делает чтение быстрым и не позволяет UI смешать актуальные справочники с историческим snapshot.

## 6. UX и UI

### 6.1. Визуальный стиль

- Сохранить существующую тёмно-синюю боковую навигацию и светлый фон рабочей области.
- Использовать сдержанные тёмно-синие и светло-синие акценты проекта.
- Сделать доску плотнее текущего экрана: при ширине 1440–1600 пикселей одновременно видны 3–4 колонки и закреплённая колонка неназначенных.
- Основное действие — «Рассчитать маршруты». Кнопка «Параметры» остаётся вторичной и визуально не конкурирует с запуском расчёта.
- Красный цвет используется для просрочки и ошибок, янтарный — для аварийности и предупреждений, зелёный — для выполненных заявок и состояния готовности.

### 6.2. Интерактивность макета

Кликабельный макет находится в файле `service_portal/prototypes/planning-screen.html` и демонстрирует:

- переключение семи дней;
- поиск и фильтры;
- карточки назначенных, неназначенных и отменённых заявок;
- боковую панель объяснения;
- запуск расчёта и обновление версии;
- состояния «нет плана», «частичный результат», «ошибка» и «данные не готовы» через переключатель сценариев.

Макет задаёт структуру и поведение, но не является готовой реализацией API или solver.

### 6.3. Доступность

- Все интерактивные элементы доступны с клавиатуры и имеют видимый focus.
- Карточка открывается клавишами Enter и Space.
- Цвет не является единственным носителем статуса; статусы имеют текст.
- Заголовки колонок размечены как заголовки областей, боковая панель имеет `role=dialog` и управляет фокусом.
- Контраст основного текста и действий соответствует WCAG AA.

## 7. Тест-кейсы

## 8. Логирование и мониторинг разработчика

Логировать:

- старт ручного расчёта, инициатора и активный `run_id`;

Мониторинг на DEV и PROD:

- доля ошибок API;
- число опубликованных версий без полного explanation payload;

- доля автоматических обновлений UI после публикации;
- число неизвестных кодов причин.

## 9. План раскатки разработчика

1. Добавить таблицы или поля read model и справочник причин.
2. Выполнить миграции без переключения UI.
3. Начать сохранять новый формат параллельно существующему.
4. Проверить инварианты на DEV и тестовом проекте.
5. Выполнить backfill только для текущей версии, если данные позволяют; иначе показывать безопасное сообщение для старого плана.
6. Включить новый экран feature flag для владельцев и тестовых диспетчеров.
7. Сравнить счётчики с backend результатами минимум на трёх сценариях.
8. Включить экран всем проектам.
9. Удалить старый UI истории запусков после периода наблюдения; данные истории в БД не удалять. Существующий раздел «Параметры» сохранить без изменений.

Откат UI не должен откатывать опубликованные планы. Миграции должны быть обратно совместимыми на период поэтапного включения.

## 10. Документация

Обновить пользовательскую документацию диспетчера:

- как запустить ручной расчёт;
- как выбрать дату;
- как читать порядок маршрута;
- чем «перенесена» отличается от «не назначена в горизонте»;
- что означает объяснение назначения;
- почему предыдущий план остаётся видимым во время расчёта;

Техническая документация должна описывать контракт reason codes и инвариант полного `DayInput`.

## 11. Критерии приёмки

1. На экране есть заголовок «Планирование», вторичная кнопка «Параметры», основная кнопка «Рассчитать маршруты» и только один верхний индикатор готовности данных; старые информационные карточки параметров и история запусков отсутствуют.
2. Кнопка «Параметры» открывает существующий интерфейс с прежними правами и поведением; логика чтения, изменения и сохранения параметров не меняется.
3. Кнопка запускает ручной полный расчёт сразу, без подтверждения и без отдельной публикации.
4. Отображаются семь дат от `D0` в timezone проекта; по умолчанию выбран текущий день.
5. Для выбранной даты видны колонки инженеров и последняя колонка «Неназначенные заявки».
6. Каждая заявка из сохранённого `DayInput` показана ровно один раз для выбранного дня: в маршруте инженера либо в неназначенных.
7. Заявка, оставшаяся неназначенной на выбранный день и назначенная позже, показана в неназначенных с будущей датой, а на будущей вкладке — у инженера.
8. Заявка, не назначенная до конца горизонта, находится в отдельной группе и имеет конкретную причину.
9. Назначенная карточка содержит порядок, время, адрес, тип работ, длительность, статус, SLA и краткое объяснение.
10. Боковая панель отделяет допустимость, факторы objective и итог optimizer; неподтверждённые причинные утверждения не выводятся.
11. Отменённая заявка показана в прежней колонке со статусом «Отменена», исключена из активного маршрута, счётчиков и метрик.
12. Во время расчёта предыдущая версия остаётся видимой; повторный запуск заблокирован; после публикации доска обновляется атомарно.
13. При ошибке предыдущая версия остаётся актуальной и доступно действие повторного запуска.
14. При неготовых данных кнопка заблокирована, а пользователь видит конкретные проблемы.
15. Экран работает на десктопе от 1280 пикселей, поддерживает горизонтальную прокрутку и закреплённые заголовки.
16. Инженер не может открыть экран или получить его данные через API.
