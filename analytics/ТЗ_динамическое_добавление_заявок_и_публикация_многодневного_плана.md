# Техническое задание на динамическое добавление заявок и автоматическую публикацию многодневного плана

Версия: 1.3. Дата: 14 сентября 2026 года.

## 1. Назначение и статус документа

Документ задаёт бизнес-правила и технический контракт для автоматического пересчёта плана при появлении новой заявки, ночного планирования и ручного запуска. Результат расчёта на весь достигнутый горизонт публикуется сразу. Диспетчер видит, какие назначения изменились и почему заявки остались неназначенными; инженер видит только актуальную опубликованную версию своих назначений.

Это **отдельное ТЗ**. Файлы «ТЗ распределение заявок на один день», «ТЗ управляемый каскад многодневного планирования» и «ТЗ администрирование проектов и кабинеты пользователей» остаются без изменений. В реализации данного этапа этот документ имеет приоритет при прямом расхождении по запуску расчёта, защите текущего маршрута и публикации. В частности, он заменяет прежние правила «только ручной запуск», «будущие дни — черновики», «публикуется только текущий день» и «опубликованный текущий день целиком неизменяем». Остальные hard constraints, дневной solver, семидневный каскад, primary/reserve, FutureOpportunityBonus, проектная изоляция и жизненные статусы действуют по связанным ТЗ.

В этом документе «опубликован» означает доступность текущей версии плана в кабинетах. Опубликованное будущее назначение можно изменить следующим валидным расчётом. Для выполнения solver формирует внутренний временный результат, который не показывается как отдельное состояние «черновик» и не создаёт назначения до атомарной публикации.

## 2. Цели и границы

Цель — включать новые заявки в план автоматически с сохранением уже выполняемой работы и с контролируемым изменением опубликованных назначений. **Если крайний срок новой заявки сегодня или уже прошёл**, система проверяет возможность вставки на сегодня у каждого подходящего инженера, сравнивает только сегодняшние маршруты и выбирает одного инженера. После выбора один раз пересчитываются будущие даты. **Если крайний срок позже сегодня**, событие создания заявки не запускает расчёт текущего дня и не меняет ни одного сегодняшнего назначения: пересчитываются только доступные будущие даты. Ночной и ручной полные запуски остаются самостоятельными поводами расчёта по разделу 7.4.

Входят: события запуска, очередь по проекту, неизменяемый snapshot, защищённый префикс сегодняшних маршрутов, ограниченный дневной пересчёт OR-Tools, сравнение вариантов, многодневный каскад, автоматическая публикация полной версии, история и аудит, интерфейс результата, обработка ошибок и тесты.

Не входят: GPS и отдельный статус «В пути», ручное назначение или перенос инженера диспетчером, изменение статусов жизненного цикла solver, физическая логистика оборудования, пересчёт по каждому изменению справочников или графиков, гарантированное математически глобальное оптимальное решение без лимита времени.

## 3. Термины и инварианты

| Термин | Значение |
| --- | --- |
| Текущий день | Календарная дата `D0` в IANA timezone проекта на момент фиксации snapshot для расчёта. При смене даты до публикации snapshot признаётся устаревшим. |
| SLA | `sla_date` — крайняя дата выполнения, не обязательная дата визита. Выполнение раньше допускается. |
| Защищённый префикс | Назначения инженера на сегодня, которые нельзя менять по правилам раздела 6. |
| Изменяемый хвост | Ещё не начатые назначения после защищённого префикса того же инженера. |
| Вытесненная заявка | Ранее назначенная, ещё не начатая заявка, которую новый расчёт исключил из сегодняшнего маршрута. Её `jobs.status` остаётся `NEW`; `CANCELLED` не устанавливается. |
| Кандидат инженера | Вариант сегодняшнего маршрута одного подходящего инженера; будущий каскад не участвует в его оценке. |
| Публикация версии | Атомарная замена актуальных назначений проекта на весь рассчитанный период с сохранением прежней версии в истории. |
| Неназначена | Заявка не имеет актуального опубликованного назначения. Это результат планирования, а не новое значение `jobs.status`. |

Неизменны завершённые и выполняемые заявки, а также защищённая следующая остановка. Сегодняшняя ещё не начатая заявка не переходит от одного инженера к другому: solver может оставить её у прежнего инженера или вытеснить в остаток будущего каскада. В будущие дни назначения между инженерами могут изменяться. Один `job_id` имеет не более одного актуального опубликованного назначения во всех датах. Никакой частично рассчитанный или не прошедший Validator вариант не заменяет текущий план.

## 4. Поводы запуска и очередь

1. Создание одной заявки со статусом `NEW` — автоматический запуск после успешного сохранения заявки.
2. Массовый импорт — все успешно сохранённые новые заявки одного проекта объединяются в одно событие. Ошибочные строки файла в планирование не входят.
3. Ночной запуск — один раз за локальные сутки проекта в настраиваемое ночное время. Он пересчитывает текущую дату и доступный будущий горизонт по правилам защиты.
4. Ручной запуск диспетчером — тот же алгоритм и те же фиксации, без возможности обойти hard constraints.

В данном этапе изменение адреса, SLA, типа работ, статуса, смены, квалификации, транспорта или оборудования само по себе **не создаёт** автоматическое событие. Ручной и следующий ночной запуск читают актуальные данные. Для опасных изменений, которые сделали опубликованный план невалидным, интерфейс показывает предупреждение; отдельную политику автозапуска по таким изменениям описать следующим этапом.

Все события одного проекта проходят через одну долговременную очередь. Одновременно у проекта не более одного активного расчёта и одной операции публикации. Близкие события создания и импорта объединяются в короткое настраиваемое окно; по умолчанию 30 секунд после последнего события с верхним пределом ожидания 2 минуты. Запрос, пришедший во время активного расчёта, не подмешивается в его snapshot: он сохраняется в очереди и запускает следующий расчёт после завершения текущего. Повторное событие не должно создавать дубли назначения. При заблокированном проекте запуск не выполняется, событие получает явную причину.

Сохранение заявки не зависит от успеха solver: API создания возвращает сохранённую заявку и идентификатор события планирования. Автоматический расчёт асинхронен. Ночной запуск учитывает timezone проекта и переходы календарного времени. Событие создания или импорта классифицируется по `sla_date` каждой новой заявки относительно `D0`. Если все новые заявки имеют будущий срок, текущий день полностью исключён из расчёта этого события. Если в одном импорте есть и срочные, и будущие заявки, только срочные участвуют в сегодняшней ветке; будущие начинают участвовать не раньше `D0 + 1`. Ночной и ручной полные запуски могут рассчитывать сегодня по своим правилам; совпадение их по времени с созданием будущей заявки не превращает эту заявку в повод менять сегодняшний план.

## 5. Горизонт и отбор заявок

Базовые горизонты сохраняются: первый блок — 7 календарных дат, максимум — 30 календарных дат от локальной даты запуска; каждый день внутри блока — отдельный вызов дневного solver. Заявка попадает в расчёт, если она `NEW`, валидна, принадлежит проекту и её SLA лежит не позже конца максимального горизонта. Просроченные заявки участвуют. Заявка со сроком позже 30 дней остаётся без назначения до будущего запуска, когда срок войдёт в горизонт.

Правило `primary/reserve` сохраняется. В любом блоке primary — просроченные и со сроком до конца блока; reserve — со сроком позже блока, но внутри максимального горизонта. Reserve использует только свободную после primary ёмкость. Поэтому **новую заявку с будущим SLA нельзя начинать лишь с блока её срока**: она может быть reserve в более раннем блоке. Но для события её создания первая допустимая дата — **`D0 + 1`**, даже если сегодня есть свободная ёмкость и даже если ещё нет опубликованного плана. Ни сегодняшняя модель, ни сегодняшние назначения при таком событии не меняются. При ночном или ручном полном запуске первая дата определяется самостоятельными правилами разделов 7.1 и 7.4.

На каждом дне `RemainingJobs(d)` строится из полного snapshot за вычетом неизменных/уже назначенных на более ранние даты и permanent issues; `DroppedJobs(d)` переходят в `RemainingJobs(d+1)`. `DailyDropPenalty(j,d)` и `FutureOpportunityBonus(j,d)` пересчитываются относительно каждого дня, их сумма передаётся в дневную модель как `CascadeDropPenalty(j,d)` через `AddDisjunction`. Резерв не может вытеснить выполнимую primary заявку. Назначенная в новом дне заявка исчезает из остатка следующих дней.

Пересчитанные блоки сохраняются последовательно. Последующий блок можно переиспользовать только если совпали **полный состав остатка на входе, данные, влияющие на допустимость и стоимость, версия конфигурации и защищённые назначения**. Совпадения одного числа `Unassigned` недостаточно. Иначе каскад продолжается до пустого остатка, доказанной невозможности, лимита горизонта или ошибки. Изменённые будущие назначения публикуются вместе с остальным планом как новая версия.

## 6. Защита сегодняшнего маршрута

Для каждого инженера на момент snapshot назначения сортируются по `sequence`, а фактические статусы читаются из БД. `COMPLETED` фиксирует историю; `IN_PROGRESS` фиксирует инженера, заявку и начатую работу. Если есть заявка `IN_PROGRESS`, следующая ещё не завершённая заявка того же маршрута также фиксируется как цель поездки после текущей. Если `IN_PROGRESS` нет и смена уже идёт, фиксируется первая ещё не завершённая заявка: система консервативно считает инженера в пути к ней. Ни одна новая заявка не вставляется перед защищённой остановкой и не меняет её инженера, дату, порядок или плановый смысл.

После последней защищённой остановки все `NEW` назначения инженера становятся изменяемым хвостом. Их порядок и плановое время разрешено менять в пределах существующих жёстких окон, смен, длительности, дорожного времени, квалификаций и оборудования. Любое число таких заявок может быть вытеснено, если итоговый вариант лучше по общей шкале раздела 8. Вытесненные заявки не назначаются другому инженеру **сегодня**; они возвращаются в остаток каскада с завтрашнего дня.

Входная точка изменяемого хвоста — адрес последней защищённой заявки и оценка времени окончания работы по ней. Если защищённой заявки нет, используются последняя фактически завершённая точка инженера и текущее время; если за день ещё ничего не выполнено — стартовая точка и начало смены. Время вычисляется как максимум из текущего локального времени, известного фактического времени и планового окончания защищённой заявки; недостающие факты и прогнозная ошибка отмечаются в диагностике. Перед публикацией статусы и версия маршрута читаются повторно; при изменении префикса вариант признаётся устаревшим и пересчитывается.

До начала смены, если инженер ещё не приступал к маршруту, первая заявка не считается целью поездки и может изменяться ночным или ручным расчётом. После начала смены применяется консервативная защита выше.

## 7. Сценарии расчёта

### 7.1. Нет действующего плана

Отсутствие опубликованного плана **не отменяет ветвление по сроку новой заявки**. Первый ночной или ручной полный запуск начинает обычный каскад с `D0`. Событие создания или импорта, в котором все новые заявки имеют `sla_date > D0`, начинает каскад с `D0 + 1`: текущий день остаётся без назначений и не рассчитывается. Если событие содержит новую заявку с `sla_date ≤ D0`, текущий день входит в расчёт по правилам срочной ветки раздела 7.3; если выполнить её сегодня невозможно, она переходит в будущий остаток. Результат проверяется и публикуется одной версией, а заявки вне плана получают причины неназначения.

### 7.2. Новая заявка со сроком позже сегодня

Этот сценарий относится к событию **создания или импорта** заявки с `sla_date > D0`. Сегодняшний solver не вызывается; заявка не передаётся в сегодняшнюю модель даже как reserve. Никакая сегодняшняя заявка не получает нового инженера, порядка или времени, а новые сегодняшние назначения не создаются. Если плана ещё нет, сегодняшний день остаётся пустым. Первая изменяемая дата для такой новой заявки — `D0 + 1`, а не первый день блока её SLA: в более раннем **будущем** блоке она может использовать свободную reserve ёмкость.

Заявка и затронутые ещё не выполненные будущие заявки передаются в каскад с `D0 + 1`. После каждого дня формируется остаток. Если состав и остальные влияющие входы на границе совпали с предыдущей версией, следующие сохранённые блоки можно переиспользовать; иначе пересчёт продолжается до условий остановки. Валидный результат автоматически публикуется без изменения сегодняшних назначений.

### 7.3. Новая заявка со сроком сегодня или в прошлом

Эта ветка применяется **только при `sla_date ≤ D0`**. Система обязана **проверить возможность** выполнить заявку сегодня; это не обещание назначить её сегодня при нарушении ограничений. Backend один раз собирает одинаковый исходный snapshot и список подходящих инженеров: активный инженер проекта, доступная оставшаяся смена, нужные квалификации и транспорт, потенциально достаточное оборудование, допустимое окно и маршрутная стартовая точка. Окончательную выполнимость определяет solver и Validator, а не предварительный фильтр.

Для **каждого** подходящего инженера `e` создаётся отдельная сегодняшняя модель. В ней только маршрут `e`: защищённый префикс задаётся как неизменяемая граничная точка и время, все остальные сегодняшние инженеры и их маршруты остаются фиксированными вне модели. Вход модели содержит срочную новую заявку, все ещё не начатые заявки изменяемого хвоста `e`, время пути, окна, смену и остаток оборудования после резервирования для прочих неизменных маршрутов. **Только внутри этой проверочной модели срочная заявка обязательна** и должна быть назначена `e` сегодня: иначе solver мог бы выгодно пропустить её, хотя допустимая вставка существует. Это условие не применяется к заявке с будущим SLA и не требует публиковать невалидную вставку. Прежние заявки изменяемого хвоста остаются optional с действующим `CascadeDropPenalty(j, сегодня)` из ТЗ каскада; отдельный штраф «за выбор инженера» в OR-Tools не передаётся. Модель возвращает порядок, времена и множество вытесненных заявок. При отсутствии допустимого решения кандидат получает причину отказа. Для каждого найденного результата выполняется дневной Validator, в том числе проверка общего оборудования проекта.

Backend сравнивает **только валидные сегодняшние маршруты** по разделу 8. Если хотя бы один инженер может выполнить новую заявку сегодня, выбирается лучший среди таких инженеров. Вариант «не менять сегодня» не конкурирует с выполнимой сегодняшней вставкой. Если ни один подходящий инженер не получил валидный маршрут с новой заявкой сегодня, сегодняшний план сохраняется, а новая заявка переходит в расчёт с завтрашнего дня.

**Только после выбора** сегодняшнего маршрута запускается один будущий каскад: вытесненные заявки и прочий остаток передаются на завтра по прежним правилам. Если сегодня не нашлось выполнимой вставки, тот же единственный каскад получает и новую заявку. Будущий результат не используется для повторного ранжирования сегодняшних инженеров. Валидная часть плана проходит пакетный Validator и проверку актуальности, затем одной транзакцией публикуется новая версия текущего и будущих дней. Если каскад технически не завершился или план за время вычисления изменился, новая версия не публикуется; событие остаётся на повтор. Переход к другому сегодняшнему инженеру из-за неназначенных заявок будущего каскада не выполняется.

### 7.4. Ночной и ручной запуск

Оба запуска рассчитывают весь доступный период. Уже защищённый префикс текущего дня остаётся неизменным. Текущие незавершённые хвосты можно перестроить **внутри маршрута того же инженера**, без переноса текущих заявок между инженерами. Неназначенные на сегодня заявки и вытесненные из хвоста переходят в завтрашний остаток. Будущие даты пересчитываются обычным каскадом. Ручной запуск не является аварийным обходом ограничений.

## 8. Как выбрать инженера для сегодняшней заявки

### 8.1. Входные данные и граница сравнения

Раздел 8 применяется **только к событию с новой заявкой, у которой `sla_date ≤ D0`**. Для выбора инженера оценивается только локальная дата расчёта `D0`. Заявка с `sla_date > D0` этот раздел обходит: для неё сегодняшний solver не запускается. Backend не запускает и не оценивает будущий каскад для каждого срочного кандидата. `ObjectiveValue()` разных моделей OR-Tools напрямую не сравнивается, поскольку в них разные изменяемые маршруты. Дневной solver по-прежнему строит маршрут со штрафом `CascadeDropPenalty(j,D0)` из ТЗ каскада; `FutureOpportunityBonus` влияет на решение solver о пропуске прежних заявок, но **не является отдельным показателем выбора инженера**. Backend сравнивает готовые сегодняшние маршруты по единому правилу ниже.

Перед расчётом фиксируются `T0` — время snapshot, `D0` — локальная дата проекта, версия опубликованного плана, конфигурация и общий набор `J_today`: новая срочная заявка плюс все опубликованные на `D0`, ещё не завершённые заявки со статусом `NEW`. Защищённые заявки входят в набор как неизменные и дают одинаковый результат у всех кандидатов. Заявки со статусами `IN_PROGRESS` и `COMPLETED` учитываются Validator как фиксированные факты, но не ранжируются. У всех кандидатов одинаковые `J_today`, `T0`, конфигурация, дорожная матрица и сегодняшние маршруты остальных инженеров.

| Значение | Источник на `T0` |
| --- | --- |
| `sla_date`, статус, окно, длительность, маршрутная точка | Заявка и связанный тип работ. |
| Прежний инженер, порядок и плановое начало | Текущий `plan_version_assignments` для `D0`. |
| Защищённый префикс и старт изменяемого хвоста | Статусы, история действий и смена по разделу 6. |
| Квалификации, транспорт, смены, оборудование | Справочники и график проекта; Validator проверяет общий дневной ресурс. |
| `DailyDropPenalty(j,D0)` | Один расчёт backend по дневному ТЗ и общей конфигурации до запуска кандидатных solver. |
| Новый порядок, время, вытесненные заявки, дорога, ожидание | Результат дневного solver кандидата и общая дорожная матрица. |

Валидатор проверяет каждый сегодняшний вариант вместе с неизменными маршрутами остальных инженеров: hard constraints, защищённый префикс, оборудование и уникальность назначения. Вариант без допустимого решения или с нарушением не участвует в выборе. Пока хотя бы один допустимый вариант вставки существует, вариант «оставить новую заявку на завтра» не сравнивается с ним.

### 8.2. Точный порядок выбора

Для заявок `J_today` фиксируются пять SLA-групп по `sla_date − D0`: `OVERDUE` (меньше 0), `DUE_TODAY` (0), `DUE_1` (1), `DUE_2_3` (2–3), `DUE_LATER` (4 и более дней). Для кандидата `c` заявка из `J_today` считается `DroppedToday`, если после сегодняшнего solver она не назначена на `D0`. Если это ранее опубликованная заявка, она считается вытесненной даже при последующем назначении на завтра; будущий результат **не нужен** для сегодняшней оценки.

Побеждает **лексикографически минимальный** вектор. Для каждой SLA-группы по порядку в него входят `(DroppedCount_g, DroppedDailyPenalty_g)`, где `DroppedCount_g` — число `DroppedToday` в группе, а `DroppedDailyPenalty_g` — сумма сохранённых на `T0` значений `DailyDropPenalty(j,D0)` этих заявок. Сначала сравнивается число потерянных сегодня просроченных заявок, затем их общий дневной штраф, затем такая же пара для заявок со сроком сегодня, завтра, через 2–3 дня и позже. Одинаковые формулы и конфигурация используются у всех инженеров; штраф за пропуск из **разных** моделей OR-Tools не читается как готовый рейтинг.

При равенстве всех пяти пар далее сравниваются в этом порядке:

1. `OldOrderInversions` — число пар прежних сегодняшних заявок того же инженера, которые обе остались сегодня, но поменялись взаимным порядком. Вставка новой заявки между ними сама по себе инверсией не является.
2. `ChangedStartCount`, затем `ChangedStartMinutes` — число оставшихся сегодня прежних заявок со сдвигом планового начала и сумма абсолютных сдвигов в целых минутах.
3. `NewJobStartDelayMinutes` — число минут от `T0` до планового начала новой заявки; если назначение начинается сейчас, значение 0.
4. `TodayTravelMinutes`, затем `TodayWaitingMinutes` — суммы по всем сегодняшним маршрутам проекта на одной матрице и с одинаковым правилом учёта ожидания. Неизменные маршруты добавляют одинаковую константу всем кандидатам.

Сравнение останавливается на первом различающемся компоненте. Например, одна вытесненная заявка со сроком завтра хуже нуля вытесненных со сроком завтра независимо от экономии дороги. При полном равенстве выигрывает меньший внутренний `engineer_id`, затем лексикографически меньшая последовательность `(engineer_id, sequence, job_id)` сегодняшнего маршрута. `FutureOpportunityCount`, число неназначенных после 30 дней, изменения будущих назначений и стоимость будущих маршрутов **не входят** в вектор.

### 8.3. Порядок расчёта и пример

1. Создать один snapshot и список всех подходящих инженеров по разделу 7.3.
2. Только для заявки с `sla_date ≤ D0` отдельно рассчитать сегодняшнюю вставку для каждого инженера; обязательность новой заявки действует внутри каждой такой проверочной модели. Сохранить время, статус solver, результат Validator, `DroppedToday` и вектор из раздела 8.2. Неразрешимую модель отклонить с причиной.
3. Если допустимых вставок нет, сохранить сегодняшний план и включить новую заявку в каскад с завтрашнего дня. Если они есть, выбрать минимальный сегодняшний вектор. **Только для выбранного варианта** выполнить один будущий каскад с вытесненными и прочими заявками остатка.
4. Проверить весь полученный план пакетным Validator, повторно проверить актуальность snapshot и опубликовать одну версию. Валидные будущие неназначения показывать диспетчеру; они не запускают сравнение с другим сегодняшним инженером. При технической ошибке каскада прежняя версия сохраняется и событие повторяется.

Пример: X нужно выполнить сегодня. Инженер 12 назначает X и вытесняет A со сроком завтра; его маршрут добавляет 10 минут дороги. Инженер 25 назначает X, никого не вытесняя, но добавляет 28 минут дороги. У инженера 25 `DroppedCount_DUE_1 = 0`, у инженера 12 — 1, поэтому **выбирается инженер 25** без расчёта двух будущих каскадов. После выбора один каскад перестраивает будущие даты. Если оба инженера никого не вытесняют и одинаково сохраняют порядок и время старых заявок, сравнивается начало X, затем сегодняшняя дорога.

Все подходящие инженеры должны получить завершённую сегодняшнюю оценку в общем лимите времени. Если лимит исчерпан, первый успевший инженер не объявляется лучшим: прежний план сохраняется, а диспетчер видит `CANDIDATE_COMPARISON_TIMEOUT`. Поиск ограничен отдельными маршрутами и временем solver; будущие последствия выбора намеренно не оптимизируются на этом этапе.

## 9. Публикация и жизненный цикл

После успешного расчёта и Validator публикуется весь рассчитанный период. Если часть заявок объективно не назначена в пределах горизонта, валидные назначения всё равно публикуются; причины неназначения и риск просрочки показываются диспетчеру. Подтверждение перед каждой автоматической публикацией не требуется. Если дневной solver, пакетный Validator, сохранение или проверка актуальности завершились ошибкой, новая версия не публикуется и прежняя остаётся рабочей. Технически прерванный каскад не считается допустимой «валидной частью» для автопубликации.

Каждая публикация имеет монотонный `plan_version` в проекте, ссылки на исходный snapshot, batch, planning runs и причину запуска. Старые версии назначений сохраняются для аудита и не отображаются инженеру как текущие. Транзакция заменяет назначения всех изменённых дат, фиксирует неизменные даты, записывает список изменённых, вытесненных и вновь назначенных заявок и переключает указатель `current_plan_version`. Чтение кабинета видит целиком либо прежнюю, либо новую версию.

Жизненный `jobs.status` solver не меняет: `NEW` остаётся `NEW` и после назначения или вытеснения; `IN_PROGRESS` и `COMPLETED` задаются действиями инженера/диспетчера по прежним правилам. Нельзя переводить вытесненную заявку в `CANCELLED`. Завершённые факты не переписываются. Если заявка была опубликована на будущий день, её новое назначение может сменить дату и инженера; диспетчер видит историю обеих версий.

Инженер видит свои назначения на весь опубликованный горизонт. Кабинет получает актуальную версию при каждом открытии и периодически проверяет её изменение при активной сессии. Изменение показывается явно: новая заявка, снятая заявка, изменённые дата, порядок или время. Отдельное подтверждение инженера для вступления версии в силу не требуется; при отсутствии связи сервер хранит версию, а кабинет получает её при восстановлении соединения. Push, SMS и email в этом этапе не нужны.

## 10. Данные, API и права

### 10.1. Данные

Нужны отдельные сущности или эквивалентные поля: `planning_events` (проект, тип, job_ids, время, idempotency key, состояние), `planning_batches` (snapshot/hash, конфигурация, причина запуска, горизонт, статус), `candidate_evaluations` (engineer_id, исходный и конечный **сегодняшний** маршрут, сегодняшний вектор оценки, причины отказа, время), `plan_versions` (номер, batch_id, опубликовано в, автор события, текущая версия), `plan_version_assignments` и `plan_changes` (старое/новое назначение, причина). Все связи и уникальности содержат `project_id`; пользовательские формы не показывают внутренние коды и ID как обязательные поля.

Для каждого шага хранится версия исходных заявок, статусов и назначений, оборудования, смен, квалификаций, дорожной матрицы и конфигурации solver. История не удаляется при вытеснении или последующем изменении. Для одной заявки разрешено одно актуальное назначение на проект; для одного проекта — одна активная публикация и один активный расчёт.

### 10.2. API и интерфейс

| Действие | Доступ | Ответ |
| --- | --- | --- |
| Создать заявку или импортировать файл | Диспетчер | Сохранённые заявки, ошибки строк и идентификатор события планирования. |
| Запустить полный расчёт | Диспетчер | `202 Accepted`, идентификатор batch и ссылка на прогресс. |
| Получить прогресс | Диспетчер | Дата, блок, кандидат, доля оценённых инженеров, очередные события, ошибки. |
| Получить текущий план и отличия версий | Диспетчер | Все даты, маршруты, назначенные/неназначенные, изменённые назначения и причины. |
| Получить собственный маршрут | Инженер | Только свои назначения текущей опубликованной версии и её номер. |

Владелец сохраняет прежние права управления проектами и доступами; права диспетчера и инженера не расширяются. Сервер проверяет роль и проект на каждом чтении и записи. Для автоматических событий фиксируются инициатор `SYSTEM` и источник `JOB_CREATED`, `IMPORT`, `NIGHTLY` или `MANUAL`; для ручного запуска также `actor_user_id`. Ответ API создания заявки не обещает назначение до завершения асинхронного расчёта.

UI диспетчера показывает: состояние очереди и расчёта, дату последней публикации и версию, список изменений относительно прежнего плана, вытесненные заявки и новые даты их назначения, неназначенные заявки с причиной и признаком нарушения SLA. UI инженера ясно показывает изменение текущей версии и не выводит чужие маршруты.

## 11. Согласованность и сбои

Создание события выполняется в той же транзакции, что и сохранение заявки, либо через outbox с гарантированной повторной доставкой после commit. Повторная доставка события и повтор worker не создают новую активную версию из того же `input_hash`. Ночной и ручной запрос с уже работающим batch ставятся в очередь или получают указатель на активный batch по указанному idempotency key.

Перед публикацией система повторно читает локальную дату проекта, статусы, `current_plan_version`, hash значимых входов и защищённый префикс. Смена `D0` или другое несовпадение означает `STALE_SNAPSHOT`: результат остаётся в истории, но не публикуется, событие повторяется на новом snapshot и заново классифицируется по сроку заявки. Публикация и переключение актуальной версии происходят атомарно. Временный сбой дорожной матрицы или solver приводит к ограниченному повтору; по исчерпании попыток текущий план сохраняется и создаётся видимая ошибка. При отсутствии валидного маршрута для новой заявки публикация валидного старого плана возможна; новая заявка видна как неназначенная с причиной.

Оборудование считается общим дневным ресурсом. При отдельном расчёте маршрута одного инженера занятость остальных инженеров фиксируется; кандидат не может получить уже выделенные им единицы. Междневная физическая передача оборудования не моделируется. Дорожная матрица, время и все внешние вызовы версионируются в snapshot или идентифицируются стабильным hash для воспроизводимости.

## 12. Ограничения времени и производительности

Расчёт асинхронный; пользователь не ждёт его в запросе создания заявки. Конфигурация задаёт максимум параллельных кандидатных дневных моделей, `candidate_solver_time_limit_sec`, `single_cascade_time_limit_sec`, общий `event_time_limit_sec` и лимит обращения к дорожному сервису. По рабочей оценке проекта — около двух проектов, десятки инженеров, до 100 заявок в день и до 1000 строк импорта — требуется технический spike на худшем сценарии: отдельный дневной solve для каждого подходящего инженера и **один** каскад до 30 дней после выбора. Значения лимитов фиксируются после измерений на репрезентативных данных; запрещено скрыто сокращать список инженеров ради выполнения лимита.

Кэш дорожной матрицы и параллельный расчёт независимых **сегодняшних** кандидатов допустимы, если у всех одинаковый snapshot и версия конфигурации. Кандидатные ветки не пишут активные назначения. Критерий «лучший» применим лишь к полностью оценённым сегодняшним вариантам. Будущий каскад начинается после их сравнения; повторное использование неизменных будущих дат допускается по правилам раздела 5.

## 13. Критерии приёмки

1. Создание новой заявки сохраняет её до расчёта и создаёт ровно одно логическое событие; повторная доставка не создаёт второе назначение.
2. Для события создания заявки со сроком завтра или позже сегодняшний solver не вызывается, сегодняшние назначения не меняются и новая заявка не назначается сегодня даже как reserve. Это верно и при отсутствии опубликованного плана; первая дата расчёта — `D0 + 1`, хотя заявка может занять reserve ёмкость будущего блока раньше своего SLA.
3. Только новая заявка со сроком сегодня или в прошлом проверяется у всех подходящих инженеров на сегодня; в каждой проверочной модели она обязательна, но при отсутствии допустимого маршрута сегодняшний план сохраняется. По каждому кандидату сохраняется результат дневного solve, а будущий каскад запускается один раз после выбора.
4. При наличии `IN_PROGRESS` она и следующая заявка остаются у того же инженера на том же месте. Без `IN_PROGRESS` после начала смены защищена первая предстоящая. Завершённые заявки не изменяются.
5. Сегодняшняя ещё не начатая заявка может изменить порядок и плановое время у прежнего инженера в пределах hard constraints или быть вытесненной; другому инженеру сегодня она не передаётся.
6. Любое число вытесненных заявок возвращается в завтрашний остаток, не становится `CANCELLED` и не теряется на границе block.
7. Порядок сравнения срочных кандидатов воспроизводится по сохранённому вектору раздела 8 на одинаковых `J_today`, `T0`, `D0`; прямое сравнение их `ObjectiveValue()` и сравнение результатов будущих каскадов не используются. Обязательность новой заявки действует только внутри срочной кандидатной модели; будущая заявка в такую модель не передаётся.
8. Если новая заявка назначена сегодня, а старые вытеснены, вся новая версия публикуется атомарно; инженер видит только свою актуальную версию.
9. Если назначить все заявки до конца горизонта нельзя, валидная часть автоматически публикуется, остальные видны диспетчеру с конкретными причинами и SLA-риском.
10. Если solver, Validator, сохранение или сравнение всех кандидатов не завершились успешно, прежний опубликованный план остаётся актуальным; ошибка видна и подлежит повтору.
11. Изменение статуса инженером одновременно с расчётом не позволяет опубликовать устаревший защитный префикс.
12. Ночной и ручной запуск используют ту же защиту и сразу публикуют валидный план на рассчитанный горизонт. Все даты внутри block решаются отдельными дневными моделями.
13. Близкие события одного проекта объединяются; при смешанном импорте заявки со сроком после `D0` не участвуют в сегодняшней ветке вместе со срочными. Разные проекты изолированы; в одном проекте нет двух одновременных публикаций.

## 14. Контрольные сценарии

| Сценарий | Ожидаемый результат |
| --- | --- |
| Инженер выполняет A, затем в маршруте B и C; приходит X со сроком сегодня | A и B остаются защищёнными; X проверяется только после B у каждого подходящего инженера. |
| У инженера нет `IN_PROGRESS`, смена идёт, ближайшая B | B защищена как цель поездки; новая заявка может войти только после B. |
| После вставки X у первого инженера сегодня выпадает C, а у второго — D | Сравниваются SLA-группы и дневные штрафы C и D, затем сегодняшние перестановки и путь. Будущий каскад выполняется один раз для выбранного маршрута. |
| Оба инженера назначают X сегодня; первый вытесняет A со сроком завтра и экономит 18 минут дороги, второй никого не вытесняет | Выбран второй: `DroppedCount_DUE_1 = 0` против 1 важнее сегодняшнего времени пути. Куда попадёт A в будущем, до выбора не вычисляется. |
| Инженер 12 назначает X сегодня, но вытесняет другую заявку со сроком сегодня; инженер 25 назначает X без вытеснения | Выбран инженер 25: одна потерянная сегодня заявка `DUE_TODAY` хуже нуля, независимо от пути. |
| Один кандидат лучше сегодня, но после выбранного маршрута каскад оставил заявку неназначенной в пределах горизонта | Валидная часть публикуется, причина показывается диспетчеру. Другие сегодняшние инженеры задним числом не сравниваются. |
| Ни одному инженеру не удалось валидно назначить X сегодня | Сегодняшние маршруты сохраняются, X включается в один каскад с завтрашнего дня. |
| X создана сегодня, крайний срок завтра, опубликованный план уже есть | Сегодняшний solver не вызывается и сегодняшние маршруты не меняются; X входит в каскад с завтра. |
| X создана сегодня, крайний срок через три дня, опубликованного плана нет | Текущий день остаётся пустым; первый расчёт выполняется на завтра, X может быть назначена раньше крайнего срока. |
| Импорт содержит X со сроком сегодня и Y со сроком через два дня | В сегодняшней ветке проверяется только X; Y не получает сегодняшнего назначения и участвует в будущем каскаде. |
| X имеет SLA во втором блоке, а в первом есть свободная reserve ёмкость | X участвует в первом изменяемом будущем блоке и может быть назначена раньше срока. |
| Прежний блок передавал в следующий A, новый передаёт B | Следующий блок пересчитывается, хотя количество `Unassigned` одинаково. |
| Одна заявка не имеет совместимого инженера на всём горизонте | Остальной валидный план публикуется; заявка остаётся `NEW` без назначения с подтверждённой причиной. |
| Инженер начал работу во время расчёта | Публикация по старому snapshot блокируется; событие пересчитывается. |
| Импорт создал 1000 заявок | Создаётся одно групповое событие проекта после предварительной проверки файла. |

## 15. Риски и проверка перед разработкой

Главный выигрыш по производительности — вместо полного каскада для каждого инженера выполняются только дневные кандидатные модели и один каскад для победителя. До реализации измерить их на реальном или репрезентативном наборе: 100 заявок за день, 30-дневный горизонт, редкие квалификации, оборудование и 1000 импортированных строк. Главный компромисс — лучший сегодняшний маршрут может привести к худшему будущему плану, чем другой сегодняшний кандидат; этот риск принят выбранным правилом и должен быть виден в отчёте о публикации. Незаметно подменять сегодняшний критерий полным каскадом или сокращать список инженеров нельзя.

Прогноз времени освобождения инженера после защищённой остановки может быть ошибочным без GPS и фактического времени завершения. Поэтому публикуется только валидный на известных данных план, статус и версия повторно проверяются перед commit, а диспетчер видит источник оценки. Офлайн-инженер узнаёт об изменении при следующей синхронизации кабинета; для оперативного подтверждения доставки понадобится отдельный этап уведомлений.

Источники технического поведения OR-Tools: [штрафы за пропуск optional визитов](https://developers.google.com/optimization/routing/penalties), [стартовые маршруты не являются жёсткой фиксацией](https://developers.google.com/optimization/routing/routing_tasks), [справка RoutingModel о допустимых машинах и фиксации маршрута](https://or-tools.github.io/docs/python/classortools_1_1constraint__solver_1_1pywrapcp_1_1RoutingModel.html).
