# Техническое задание

Управляемый каскад многодневного планирования заявок

Этап Автоматическое распределение остатка заявок на последующие дни с ограниченным горизонтом

Нормативная основа ТЗ распределения заявок на один день и ТЗ администрирования проектов и кабинетов пользователей

Статус Согласованная редакция для оценки и разработки

12 сентября 2026 года

Версия 1.1

## 1 Название задачи

Реализовать управляемый каскад многодневного планирования, который последовательно применяет существующий алгоритм дневного распределения к текущей и следующим датам, переносит временно неназначенные заявки дальше по горизонту и завершает работу по формальным условиям остановки.

## 2 Бизнес цель

После расчёта одного дня часть заявок может остаться вне маршрутов из-за ограниченной длительности смен, временных окон, графиков, квалификаций, транспорта, оборудования или географии. Диспетчер не должен вручную запускать одинаковый расчёт на каждую следующую дату и отслеживать, какие заявки уже были распределены.

Система должна сформировать единый черновой план на несколько дней, сохраняя приоритет SLA и учитывая будущую доступность редких сочетаний инженеров и ресурсов. Результат должен показать назначения по дням, оставшиеся проблемы и причины, по которым отдельные заявки не удалось распределить.

## 3 Метрики успеха

| Метрика | Критерий | Источник |
| --- | --- | --- |
| Валидность | 100 процентов сохранённых дневных результатов проходят независимый Validator | planning_runs и логи Validator |
| Нарушения hard constraints | Ноль назначений с нарушением смены, окна, квалификации, транспорта, оборудования или проектной изоляции | Пакетный Validator |
| Уникальность назначения | Одна заявка присутствует не более чем в одном дне текущего batch | planning_batch_jobs |
| Завершение процесса | Каждый batch достигает терминального состояния и не образует бесконечного цикла | planning_batches |
| Приоритет SLA | Менее срочная или резервная заявка не вытесняет выполнимую заявку более высокой SLA-группы | Контрольные тесты |
| Производительность | Первый семидневный блок целево до 5 минут, полный 30-дневный каскад до 15 минут | Технические метрики |
| Прозрачность | Для каждой нераспределённой заявки доступна подтверждаемая причина или нейтральный код optimizer | UI и API |

## 4 Область реализации

### 4.1 Входит в этап

- Ручной запуск многодневного batch диспетчером или владельцем проекта.

- Формирование согласованного снимка входных данных на момент запуска.

- Первоначальный семидневный горизонт и автоматическое расширение блоками до 30 дней.

- Последовательный вызов существующего дневного solver для допустимых дат.

- Оценка будущих возможностей заявки по парам «инженер и день».

- Разделение постоянных и временных причин неназначения.

- Сохранение дочерних planning_run, черновиков, агрегированных метрик и истории batch.

- Остановка пользователем с сохранением валидных завершённых дней.

- Интерфейс прогресса и просмотра всех рассчитанных дней и проблемных заявок.

- Проверка актуальности текущего дневного черновика перед публикацией.

### 4.2 Не входит в этап

- Автоматический ночной или событийный запуск.

- Динамическая перестройка выполняемого маршрута после новой заявки.

- Публикация планов на будущие даты.

- Ручное назначение или переназначение инженера диспетчером.

- Ручной признак срочности и поле «не планировать до».

- Возрастной бонус за количество предыдущих попыток расчёта.

- Жёсткое резервирование редких инженеров или оборудования.

- Единая математическая модель, одновременно оптимизирующая все дни.

- Внутридневная передача оборудования между инженерами.

## 6 Термины

| Термин | Определение |
| --- | --- |
| planning_batch | Неизменяемая версия одного многодневного запуска для проекта и текущей локальной даты |
| requested_start_date | Текущая календарная дата в timezone проекта, с которой пользователь запускает процесс |
| effective_start_date | Первая дата, для которой batch может создавать новый дневной черновик |
| initial horizon | Первые 7 календарных дней от effective_start_date включительно |
| maximum horizon | Не более 30 календарных дней от effective_start_date включительно |
| block | Очередной семидневный календарный интервал каскада |
| primary backlog | Просроченные заявки и заявки, SLA которых попадает в текущий block |
| reserve backlog | Заявки с SLA после текущего block, но не позднее maximum horizon |
| draft assignment | Назначение будущего или текущего дня, созданное расчётом и ещё не опубликованное |
| future opportunity | Совместимая пара «дата и инженер» в оставшейся части maximum horizon |
| permanent issue | Причина, которая не исчезнет при простом переходе к следующему дню в текущем batch |
| temporary unassigned | Неназначение в одном planning_run, после которого заявка остаётся в backlog |
| current batch | Единственный актуальный черновой многодневный результат проекта |

## 8 Событие запуска

- Batch запускается только вручную владельцем или диспетчером.

- requested_start_date должна совпадать с текущей датой в IANA timezone проекта. Прошедшая и будущая дата отклоняются.

- Для одного проекта одновременно допускается один активный batch.

- Перед созданием batch сервер проверяет блокировку проекта, права пользователя и наличие активной конфигурации дневного solver.

- Если актуальный current batch имеет тот же input_hash и configuration version, сервер возвращает существующий результат вместо повторного вычисления.

- Новый валидный терминальный batch становится current batch проекта. Предыдущий черновой batch получает SUPERSEDED и остаётся в истории.

### 8.1 Определение первой рассчитываемой даты

| Состояние текущего дня | effective_start_date | Поведение |
| --- | --- | --- |
| Нет опубликованного плана | Текущая дата | Сначала рассчитывается текущий день, затем остаток переносится дальше |
| Есть опубликованный план без начатых работ | Следующий календарный день | Опубликованные назначения фиксируются и не пересчитываются |
| Есть IN_PROGRESS или COMPLETED назначения | Следующий календарный день | Выполняемый маршрут не изменяется |
| На следующую дату нет ни одной валидной смены | Дата сохраняется в горизонте, но solver для неё не запускается | Каскад переходит к следующей календарной дате |

## 9 Горизонт и календарь

- Initial horizon равен 7 календарным дням от effective_start_date включительно.

- Если после блока остался eligible backlog и существуют будущие возможности, горизонт автоматически расширяется следующим семидневным блоком.

- Maximum horizon равен 30 календарным дням от effective_start_date включительно.

- Дата без валидных смен учитывается в календарной длине горизонта, получает состояние SKIPPED_NO_SHIFT и не вызывает дневной solver.

- Если backlog стал пустым, последующие блоки не создаются.

- При расширении ранее рассчитанные дни текущего batch не пересчитываются.

- Графики за пределами maximum horizon не читаются и не используются как основание для обещания назначения.

## 10 Отбор заявок

### 10.1 Условия включения

В planning_batch включается заявка, которая одновременно удовлетворяет условиям ниже.

- Относится к выбранному project_id.

- Имеет жизненный статус NEW.

- Не входит в действующее опубликованное назначение.

- Имеет sla_date не позднее maximum_horizon_end.

- Существовала в согласованном snapshot на момент запуска.

Заявки с SLA позже maximum_horizon_end не входят в batch, не получают reason code и не учитываются в знаменателе метрик batch. Они остаются NEW и попадут в будущий запуск.

### 10.2 Выполнение раньше SLA

- sla_date является крайним сроком, а не обязательной датой визита.

- Заявка может быть назначена на любую допустимую дату от effective_start_date до sla_date.

- Одно временное окно заявки повторяется на каждом допустимом дне.

- После SLA заявка продолжает участвовать и может быть назначена на любой следующий день горизонта.

- Просрочка считается в календарных днях timezone проекта.

### 10.3 Primary и reserve backlog

На каждом block заявки делятся на две группы. Primary backlog содержит просроченные заявки и заявки с SLA до конца текущего block. Reserve backlog содержит заявки с более поздним SLA, но в пределах maximum horizon.

- Primary backlog всегда имеет приоритет перед reserve backlog.

- Reserve backlog может использовать только ёмкость, которая остаётся после назначения всех выполнимых primary заявок текущего block.

- Реализация может использовать гарантированно разделённые диапазоны penalty или последовательные фазы solve. Обязательное свойство: сумма выгод от reserve заявок не должна вытеснять одну выполнимую primary заявку.

- При max_jobs_per_run отбор сначала заполняется primary backlog, затем reserve backlog в детерминированном порядке.

## 11 Приоритет заявок

Приоритет является иерархическим. Вторичная цель не может ухудшить достигнутое значение более высокой цели.

1 Соблюдение hard constraints дневного solver.

2 Минимизация числа выполнимых заявок более срочной SLA-группы, оставшихся неназначенными.

3 Внутри одной SLA-группы приоритет заявок с меньшим числом future opportunities.

4 Максимизация общего числа назначенных заявок.

5 Минимизация дорожного времени и остальных затрат дневного маршрута.

### 11.1 SLA группы

| Порядок | Группа | Правило внутри группы |
| --- | --- | --- |
| 1 | OVERDUE | Большая календарная просрочка выше меньшей |
| 2 | DUE_TODAY | Сначала меньшая future opportunity count |
| 3 | DUE_IN_1_DAY | Сначала меньшая future opportunity count |
| 4 | DUE_IN_2_3_DAYS | Сначала меньшая future opportunity count |
| 5 | DUE_LATER_IN_CURRENT_BLOCK | Сначала меньшая future opportunity count |
| 6 | RESERVE | Не вытесняет выполнимые заявки групп 1–5 |

Количество предыдущих неназначений и дата создания не повышают бизнес-приоритет. created_at и внутренний id используются только как стабильный технический tie-break.

### 11.2 Future opportunity

Для заявки j и текущей даты d вычисляется FutureOpportunityCount как число пар «инженер e и дата t» от d до maximum_horizon_end, для которых выполнена базовая совместимость.

- Инженер активен и относится к проекту.

- На дату существует корректная смена достаточной длины.

- Инженер имеет все обязательные квалификации.

- Инженер соответствует требованию транспорта.

- Обязательные типы оборудования имеют available_units больше нуля.

- Окно и длительность не делают выполнение заведомо невозможным.

FutureOpportunityCount является оценкой потенциальной совместимости. Он не доказывает маршрутную выполнимость и не резервирует конкретного инженера. При равной SLA-группе меньший счёт получает больший secondary penalty за пропуск.

#### 11.2.1 Передача значения в OR Tools

FutureOpportunityCount не передаётся в OR-Tools отдельным полем, переменной или hard constraint. Значение рассчитывается backend до построения RoutingModel и преобразуется в FutureOpportunityBonus. Затем бонус прибавляется к дневному штрафу за пропуск заявки.

DailyDropPenalty(j, d) = SLABase(j, d) + OverdueBonus(j, d) + SkillScarcityBonus(j, d) + EquipmentInventoryBonus(j, d) + WindowTightnessBonus(j)

- SLABase и OverdueBonus пересчитываются относительно конкретной planning_date d.

- SkillScarcityBonus отражает число совместимых инженеров только на рассчитываемый день d.

- EquipmentInventoryBonus и WindowTightnessBonus рассчитываются по правилам дневного ТЗ.

- FutureOpportunityBonus является отдельным многодневным компонентом и отражает возможности от дня d до конца maximum horizon.

| FutureOpportunityCount | FutureOpportunityRank | FutureOpportunityBonus по умолчанию |
| --- | --- | --- |
| 0 | Не применяется | Заявка не передаётся в solver и получает подтверждённую причину несовместимости на горизонте |
| 1 | 3 критический дефицит | +750 |
| 2–3 | 2 высокий дефицит | +500 |
| 4–7 | 1 ограниченный выбор | +250 |
| 8 и более | 0 обычный выбор | 0 |

CascadeDropPenalty(j, d) = DailyDropPenalty(j, d) + FutureOpportunityBonus(j, d)

Для каждой optional заявки RoutingModelBuilder обязан вызвать routing.AddDisjunction([node_index], CascadeDropPenalty). Чем выше итоговый penalty, тем дороже solver исключить заявку из маршрута и тем вероятнее её назначение при наличии допустимого маршрута.

- FutureOpportunityBonus применяется только как вторичный приоритет внутри одной SLA-группы.

- Бонусы 750, 500 и 250 являются значениями конфигурации первой версии и сохраняются в snapshot batch.

- Максимальный бонус и способ разделения диапазонов должны исключать переход менее срочной заявки в более высокую SLA-группу.

- Для reserve backlog сначала действует отдельное правило primary before reserve; один FutureOpportunityBonus не даёт reserve заявке права вытеснить primary.

- В planning_batch_jobs или связанном snapshot сохраняются компоненты DailyDropPenalty, исходный count, rank, FutureOpportunityBonus и итоговый CascadeDropPenalty для объяснения результата.

### 11.3 Детерминированность

- Все заявки, инженеры, даты и матричные ключи сортируются стабильным порядком.

- При равных бизнес-показателях применяется sla_date, затем created_at, затем внутренний id.

- Версия solver, параметры поиска и seed сохраняются в snapshot.

- Повторный пользовательский запрос с тем же input_hash возвращает current batch и не запускает новый поиск.

- На STATIC_TEST одинаковый вход обязан давать одинаковые назначения, порядок и причины.

На продуктивном time-limited solver побитовая повторяемость между разными версиями библиотек или аппаратными средами не гарантируется. Стабильность пользовательского результата обеспечивается повторным использованием batch с одинаковым input_hash.

## 12 Основной алгоритм

Внутри одного block дневной solver запускается отдельно для каждой календарной даты по возрастанию. Один block не является одной моделью OR-Tools на семь дней.

### 12.1 Модель выполнения block

- Block является упорядоченным набором не более чем из семи календарных дат.

- Для каждой даты d создаётся отдельный дочерний planning_run и новый экземпляр RoutingIndexManager и RoutingModel.

- Дневной solver решает только одну дату и не переносит заявки на завтра самостоятельно. Переход к следующей дате выполняет CascadeOrchestrator.

- В одном семидневном block выполняется до семи независимых вызовов solver: по одному на дату с валидными сменами и непустым набором кандидатов.

- Дата d + 1 начинает рассчитываться только после проверки и атомарного сохранения валидного результата даты d.

- RoutingModel, Assignment и временные структуры предыдущего дня не переиспользуются. Из предыдущего дня берутся только сохранённые итоги: какие заявки уже назначены и какие остались.

- Если на дату нет валидных смен, planning_batch_day получает SKIPPED_NO_SHIFT, solver не вызывается, а остаток без изменений переходит к следующей дате.

### 12.2 Полный состав batch и остаток на дату

При запуске один раз сохраняется неизменяемый полный состав B: все заявки, прошедшие правила eligibility на snapshot. Новые или изменённые после snapshot заявки в выполняющийся batch не добавляются.

Для даты d активный остаток определяется так:

RemainingJobs(d) = B − PermanentIssues − AssignedBefore(d) − TerminallyUnassignedBefore(d)

- AssignedBefore(d) содержит заявки с валидным черновым назначением на любую более раннюю дату этого batch.

- TerminallyUnassignedBefore(d) содержит заявки, для которых уже доказано отсутствие возможностей на всей оставшейся части maximum horizon.

- Из RemainingJobs(d) формируется SolverCandidates(d): заявки, имеющие хотя бы одну базово совместимую пару «инженер и смена» на дату d и прошедшие предварительные дневные проверки.

- Заявки без возможности именно на дату d получают временную диагностическую причину, не передаются в solver этого дня и остаются в остатке для следующей даты.

- SolverCandidates(d) делятся на primary и reserve по правилам раздела 10.3. Ограничение max_jobs_per_run применяется отдельно в установленном детерминированном порядке.

### 12.3 Контракт входа дневного solver

CascadeOrchestrator перед каждым вызовом формирует новый SolverInput(d). Он обязан содержать:

- planning_batch_id, planning_run_id и конкретную planning_date d;

- snapshot заявок из SolverCandidates(d) с внутренними job_id;

- активных инженеров и их валидные смены только на дату d;

- квалификации, транспорт, типы работ, длительности и available_units оборудования из snapshot batch;

- временные окна заявок, технические координаты и дорожную матрицу, необходимую для узлов этого дня;

- версию конфигурации, seed, time limit и остальные параметры дневного solver;

- для каждой optional заявки рассчитанный CascadeDropPenalty(j, d), передаваемый в AddDisjunction.

Перед построением модели для всех заявок остатка повторно рассчитывается FutureOpportunityCount на интервале от d до maximum_horizon_end. DailyDropPenalty считается относительно d, поэтому на следующей дате оба компонента и CascadeDropPenalty рассчитываются заново.

Черновые назначения предыдущих дней не передаются в новый RoutingModel как узлы или фиксированные маршруты: соответствующие job_id уже исключены из RemainingJobs(d).

### 12.4 Сохранение результата дня

Дневной solver возвращает маршруты и две группы заявок: AssignedJobs(d), включённые в маршруты, и DroppedJobs(d), исключённые через disjunction. Результат обрабатывается в следующем порядке:

1 Сохранить технический ответ solver во временном контексте planning_run: status, objective, маршруты, порядок узлов, dropped nodes и метрики.

2 Выполнить дневной Validator и междневную проверку уникальности заявок.

3 При успешной проверке одной транзакцией сохранить planning_run со статусом SUCCESS, маршруты, черновые назначения и результат planning_batch_day.

4 Для AssignedJobs(d) установить в planning_batch_jobs состояние DRAFT_ASSIGNED, assigned_date = d и planning_run_id текущего дня.

5 Для DroppedJobs(d) сохранить последнюю попытку и диагностические причины, но оставить состояние BACKLOG. Эти заявки должны участвовать в следующей дате.

6 Для заявок, не переданных в solver из-за временной недоступности на d, сохранить диагностическую причину дня и также оставить состояние BACKLOG.

7 Только после commit обновить processed_through_date и перейти к следующей календарной дате.

Если Validator или транзакция сохранения завершились ошибкой, остаток не изменяется и следующая дата не запускается. Batch завершается по правилу DAY_RUN_FAILED из раздела 13.

### 12.5 Формирование входа следующего дня

После успешного сохранения дня новый остаток вычисляется по формуле:

RemainingJobs(d + 1) = RemainingJobs(d) − AssignedJobs(d)

- DroppedJobs(d) входят в RemainingJobs(d + 1).

- Заявки, временно недоступные на d и не переданные в solver, входят в RemainingJobs(d + 1).

- AssignedJobs(d) больше не передаются ни в один последующий solver текущего batch.

- Для даты d + 1 создаётся новый planning_run, загружаются смены d + 1, заново формируется дорожная матрица и пересчитываются дневные и многодневные penalty.

Пример: на 12 сентября в остатке было 100 заявок, solver назначил 72. На 13 сентября CascadeOrchestrator создаёт новый planning_run для оставшихся 28 заявок. Если 24 из них доступны 13 сентября, они передаются в новый RoutingModel; четыре временно недоступные заявки остаются в остатке на 14 сентября.

### 12.6 Завершение block и открытие следующего

- Цикл разделов 12.2–12.5 повторяется последовательно для каждой даты текущего block.

- После последней даты block ранее рассчитанные дни фиксируются и не пересчитываются.

- Если активный остаток пуст и нет terminally unassigned eligible заявок, batch завершается SUCCESS.

- Если остались заявки, для которых нет возможностей на оставшемся maximum horizon, они получают итоговую причину, а batch завершается PARTIAL по правилам раздела 13.

- Если остаток есть, future opportunities существуют и maximum horizon не достигнут, создаётся следующий семидневный block. Его первая дата следует за последней датой предыдущего block, после чего запускается тот же подневный цикл.

- При восстановлении фоновой задачи CascadeOrchestrator продолжает с первой незавершённой даты после processed_through_date. Дни со статусами SUCCESS, SKIPPED_NO_SHIFT и PINNED_PUBLISHED повторно не запускаются.

### 12.7 Сквозная последовательность

1 Проверить права, timezone, текущую дату, конфигурацию и отсутствие активного batch.

2 Создать planning_batch в состоянии CREATED и установить блокировку проекта.

3 Определить effective_start_date и сформировать неизменяемый snapshot.

4 Сохранить полный состав B и выполнить классификацию permanent issues на maximum horizon.

5 Открыть initial block длиной семь календарных дней.

6 Взять первую незавершённую дату block и сформировать RemainingJobs(d).

7 Пропустить дату без смен либо сформировать SolverCandidates(d), primary и reserve.

8 Пересчитать FutureOpportunityCount, DailyDropPenalty и CascadeDropPenalty относительно d.

9 Создать новый planning_run и новый RoutingModel, передать SolverInput(d) и выполнить один дневной solve.

10 Проверить и атомарно сохранить результат дня.

11 Исключить AssignedJobs(d) из остатка; dropped и временно отложенные заявки сохранить для d + 1.

12 Проверить stop request, ошибки, пустой остаток, future opportunities и предел горизонта.

13 Если продолжение разрешено, перейти к следующей дате и повторить шаги 6–12 с новым planning_run.

14 После конца block при необходимости открыть следующий block и продолжить тот же цикл.

15 Рассчитать итоговые метрики и completion_reason; валидный терминальный batch сделать текущим черновиком проекта.

## 13 Условия продолжения и остановки

| Условие | Статус batch | completion_reason | Поведение |
| --- | --- | --- | --- |
| Eligible backlog пуст | SUCCESS | ALL_ELIGIBLE_ASSIGNED | Следующие блоки не рассчитываются |
| Изначально нет eligible заявок | SUCCESS | NO_ELIGIBLE_JOBS | Создаётся пустой валидный batch |
| День без смен | RUNNING | Не применяется | День SKIPPED_NO_SHIFT, каскад продолжается |
| В день назначено ноль, но есть future opportunities | RUNNING | Не применяется | Каскад переходит дальше |
| У остатка нет future opportunities | PARTIAL | NO_FUTURE_OPPORTUNITIES | Остановить каскад |
| Достигнут 30-дневный максимум | PARTIAL | HORIZON_LIMIT | Остаток получает NOT_ASSIGNED_WITHIN_HORIZON |
| Пользователь остановил расчёт | PARTIAL | STOPPED_BY_USER | Сохранить завершённые валидные дни |
| Один дневной run завершился критической ошибкой | PARTIAL или FAILED | DAY_RUN_FAILED | PARTIAL при наличии валидных дней, иначе FAILED |
| Ошибка snapshot или хранилища до первого результата | FAILED | SYSTEM_ERROR | Рабочий current batch не заменяется |

## 14 Причины неназначения

### 14.1 Permanent issues

| Код | Условие | Действие |
| --- | --- | --- |
| INVALID_INPUT | Нарушено обязательное правило данных заявки | Исключить из дневных запусков и показать диспетчеру |
| GEOCODING_FAILED | Нет нормализованного адреса или технических координат | Исключить до исправления адреса |
| MISSING_SERVICE_DURATION | Нет положительной длительности работы | Исключить до исправления типа работ |
| NO_COMPATIBLE_ENGINEER_IN_HORIZON | Ни одна пара «инженер и день» не проходит квалификацию и транспорт | Не повторять по дням |
| NO_SHIFT_IN_HORIZON | Для проекта нет валидных смен на всём maximum horizon | Не запускать дневной solver |
| DURATION_EXCEEDS_ALL_SHIFTS | Работа не помещается ни в одну потенциально совместимую смену | Не повторять по дням |
| EQUIPMENT_UNAVAILABLE_IN_HORIZON | У обязательного типа available_units равно нулю | Не повторять по дням |
| INVALID_TIME_WINDOW_FOR_HORIZON | Окно и длительность исключают выполнение в любой совместимой смене | Не повторять по дням |

### 14.2 Временные причины

| Код | Поведение |
| --- | --- |
| NO_AVAILABLE_ENGINEER_TODAY | Оставить заявку в backlog следующей даты |
| NOT_SELECTED_BY_OPTIMIZER | Оставить заявку в backlog без возрастного бонуса |
| DATASET_LIMIT | Оставить заявку в backlog и повторно включить в детерминированный отбор |
| TRAVEL_DATA_NOT_READY | Сохранить причину дня; при доступности будущей матрицы продолжить |
| DAILY_TIME_WINDOW_CONFLICT | Не считать постоянной без проверки всего горизонта |
| DAILY_EQUIPMENT_CAPACITY | Оставить в backlog, поскольку available_units восстанавливается на следующем дне |
| NOT_ASSIGNED_WITHIN_HORIZON | Итоговая причина batch, заявка остаётся NEW |

Диагностический модуль не должен утверждать недоказанную причинность. Если solver просто не выбрал optional node, основным кодом остаётся NOT_SELECTED_BY_OPTIMIZER, а подтверждённые ограничения сохраняются как diagnostic_flags.

## 15 Жизненный статус и черновые назначения

- Результаты DRAFT_ASSIGNED и UNASSIGNED относятся только к planning_batch или planning_run.

- jobs.status остаётся NEW до разрешённого перехода в опубликованном маршруте.

- Одна заявка не может иметь более одного draft assignment в current batch.

- Draft assignment не виден инженеру и не считается опубликованным обязательством.

- Новый current batch заменяет все неопубликованные будущие черновики предыдущего batch.

- Изменение или отмена заявки после snapshot не изменяет выполняющийся batch; результат помечается потенциально устаревшим проверкой input hash.

## 16 Состояния и версии

### 16.1 Состояния batch

| Состояние | Описание |
| --- | --- |
| CREATED | Запись создана, входы ещё не подготовлены |
| PREPARING | Формируется snapshot, eligibility и future opportunities |
| RUNNING | Выполняются дневные planning_run |
| STOP_REQUESTED | Принят запрос остановки, завершается безопасная точка |
| SUCCESS | Все eligible заявки получили draft assignment либо eligible набор пуст |
| PARTIAL | Есть валидные дни, но остался backlog или расчёт остановлен |
| FAILED | Не получен ни один пригодный дневной результат |
| SUPERSEDED | Черновик заменён более новым current batch |

### 16.2 Состояния дня

| Состояние | Описание |
| --- | --- |
| PENDING | Дата включена в открытый block |
| SKIPPED_NO_SHIFT | На дату нет валидных смен |
| PINNED_PUBLISHED | Текущий день уже опубликован и не пересчитывается |
| RUNNING | Дочерний planning_run выполняется |
| SUCCESS | Дневной run прошёл Validator |
| FAILED | Дневной run не дал пригодного результата |

## 17 Snapshot и актуальность

Batch использует неизменяемый логический snapshot. Изменения данных после запуска не подмешиваются в выполняющийся расчёт и не запускают автоматический пересчёт.

- Snapshot включает заявки, типы работ, длительности, квалификации, инженеров, транспорт, графики, оборудование, timezone, конфигурацию solver и ссылки на дорожные данные.

- input_hash строится по нормализованным полям, способным изменить результат.

- Изменение адреса, SLA, окна, типа работ, графика, квалификации, транспорта, оборудования или активного состояния изменяет hash.

- Перед публикацией текущего дня сервер выполняет быструю повторную проверку hash и статусов заявок.

- Если hash и статусы совпадают, черновик разрешено публиковать без нового solve.

- Если данные изменились, batch получает признак STALE_FOR_PUBLICATION, публикация блокируется и пользователю предлагается новый запуск.

## 18 Остановка пользователем

- Остановить batch может владелец или диспетчер того же проекта.

- Запрос переводит batch в STOP_REQUESTED и является идемпотентным.

- Текущий дневной solver завершается по ближайшему безопасному условию или собственному time limit; новые дни не запускаются.

- Успешные дочерние planning_run и их черновики сохраняются.

- Batch завершается PARTIAL с completion_reason STOPPED_BY_USER.

- Если текущий день имеет успешный валидный planning_run, его можно опубликовать после явного предупреждения о частичном многодневном результате.

## 19 Публикация

- В рамках этого этапа публикуется только текущая календарная дата проекта.

- Будущие дни доступны владельцу и диспетчеру только как черновики.

- Публикация выполняется по существующим правилам daily_plan, plan_version и assignments.

- Публиковать можно только SUCCESS planning_run, прошедший дневной и пакетный Validator и проверку актуальности.

- Если batch имеет PARTIAL, перед публикацией требуется отдельное подтверждение пользователя.

- Если в текущем дне есть неназначенные заявки, сохраняется действующее подтверждение публикации неполного дневного плана.

- Опубликованный или начатый текущий план не изменяется последующими batch.

## 21 API

### 21.1 Запуск

POST /api/projects/{project_id}/planning/batches

{ "requested_start_date": "2026-09-12" }

- Запрос асинхронный и возвращает 202 Accepted с planning_batch_id, status и status_url.

- requested_start_date обязана равняться текущей дате проекта.

- Заголовок Idempotency-Key обязателен для защиты от двойного нажатия.

- 409 PLANNING_BATCH_IN_PROGRESS возвращается при активном batch проекта.

- Если существует current batch с тем же input_hash, ответ может вернуть reuse = true и существующий id.

### 21.2 Состояние и результат

GET /api/projects/{project_id}/planning/batches/{id}

- Возвращает состояние, progress, текущую дату обработки, открытый block, время, метрики, days и остаток.

- Пока batch выполняется, уже завершённые дни доступны для просмотра.

- Результат другого проекта возвращает 404, а не раскрывает существование объекта.

### 21.3 Остановка

POST /api/projects/{project_id}/planning/batches/{id}/stop

- Повторный запрос безопасен.

- Для терминального batch возвращается текущее состояние без ошибки.

### 21.4 История

GET /api/projects/{project_id}/planning/batches?status=&from=&to=&limit=&offset=

- Сортировка created_at DESC.

- История содержит SUPERSEDED и FAILED результаты, но current_flag установлен только у одного пригодного batch.

### 21.5 Проверка публикации

POST /api/projects/{project_id}/planning/batches/{id}/validate-current-day

- Пересчитывает input_hash и проверяет статусы заявок без запуска solver.

- Возвращает valid_for_publication, changed_entities_count и безопасный перечень категорий изменений.

## 22 Интерфейс диспетчера

### 22.1 Запуск и прогресс

- На экране планирования показывается текущая дата проекта без возможности выбрать другую дату.

- Основное действие называется «Рассчитать планы на следующие дни».

- До запуска показываются initial horizon 7 дней и maximum horizon 30 дней.

- Во время выполнения показываются статус, текущая дата, номер блока, обработанные дни, assigned и remaining.

- Кнопка «Остановить расчёт» доступна владельцу и диспетчеру и не требует повторного подтверждения.

- Экран получает прогресс периодическим GET-запросом; постоянное открытое соединение не требуется.

### 22.2 Результат

После завершения экран содержит три представления.

| Представление | Содержание |
| --- | --- |
| По дням | Дата, состояние, инженеры, маршруты, времена, оборудование, assigned и unassigned |
| Остаток и проблемы | Заявка, SLA, последняя рассмотренная дата, primary reason, diagnostics и future opportunity count |
| Итоги | Горизонт, обработанные дни, назначено, просрочено, permanent issues, остаток и время расчёта |

- Все рассчитанные будущие дни показываются подробно владельцу и диспетчеру.

- Инженер не видит ни черновики, ни planning_batch.

- Внутренние ID, коды, широта и долгота в интерфейсе не отображаются.

- Если batch устарел, над результатом показывается предупреждение и действие нового запуска.

- Публикация доступна только для текущего дня и только после validate-current-day.

- Для PARTIAL показывается причина завершения и отдельное подтверждение перед публикацией текущего дня.

## 23 Пакетный Validator

После каждого успешного дневного run и перед переводом batch в терминальное состояние выполняются дополнительные проверки.

- Все jobs, engineers, planning_runs и справочники относятся к project_id batch.

- Одна заявка назначена не более одного раза во всём batch.

- Дата назначения находится между effective_start_date и maximum_horizon_end.

- Заявка отсутствует одновременно в draft assignment и permanent issues.

- Каждый дневной SUCCESS run прошёл собственный Validator.

- Дни расположены по возрастанию и принадлежат открытым block.

- Reserve заявка не вытеснила выполнимую primary заявку в контрольных диагностических случаях.

- Итоговые assigned, unassigned, permanent и excluded счётчики взаимно согласованы.

- Для SUCCESS eligible backlog пуст.

- Для PARTIAL задан completion_reason.

Ошибка пакетного Validator переводит batch в FAILED, не делает его current и блокирует публикацию дочерних run.

## 24 Транзакции и параллельность

- Создание batch и установка проектной блокировки выполняются одной транзакцией.

- Уникальное ограничение запрещает два активных batch для одного project_id.

- Каждый дневной результат сохраняется отдельной атомарной транзакцией после Validator.

- 30-дневный batch не удерживает одну транзакцию базы данных на всё время выполнения.

- Смена current batch выполняется одной транзакцией только после терминального валидного результата.

- FAILED batch без пригодного дневного результата не заменяет предыдущий current batch.

- Запуск отдельного дневного planning_run на дату, уже обрабатываемую активным batch, возвращает 409 PLANNING_DATE_LOCKED_BY_BATCH.

## 25 Производительность

| Показатель | Требование |
| --- | --- |

| Первый блок | Целевое время до 5 минут |

## 27 Логи аудит и метрики

- Аудит содержит запуск, остановку, завершение, замену current batch и публикацию текущего дня.

- Пароли, координаты, полные матрицы и чувствительные данные не записываются в обычные application logs.

- Для batch сохраняются duration, number_of_blocks, processed_days, skipped_days, successful_days и failed_days.

- Для заявок агрегируются primary, reserve, permanent, assigned и not_assigned_within_horizon.

- Для оптимизации сохраняются solver wall time, status, objective, dropped nodes, matrix size и validator result по дням.

- Интерфейс диспетчера показывает только итог текущего batch; отдельное сравнение вариантов алгоритма не требуется.

## 28 Тест кейсы

| Сценарий | Ожидаемый результат |
| --- | --- |
| Нет опубликованного плана сегодня | Текущий день рассчитывается первым |
| Сегодняшний план опубликован | Он фиксируется, effective_start_date становится следующим днём |
| Работы сегодня начаты | Текущий маршрут не изменяется, каскад начинается со следующего дня |
| Пустой backlog после первого дня | SUCCESS, следующие дни не запускаются |
| Нет смен два дня подряд | Дни SKIPPED_NO_SHIFT, каскад продолжает будущие даты |
| Ноль назначений сегодня, совместимость завтра | Batch продолжает расчёт |
| Ноль future opportunities | PARTIAL с NO_FUTURE_OPPORTUNITIES |
| Остаток после семи дней | Открывается следующий семидневный block |
| Остаток после 30 дней | PARTIAL HORIZON_LIMIT и NOT_ASSIGNED_WITHIN_HORIZON |
| Заявка SLA позже 30 дней | Не входит в batch и не считается unassigned |
| Reserve и выполнимая primary конкурируют | Primary назначается первой |
| Редкая и обычная заявки одной SLA-группы | Меньшая FutureOpportunityCount получает больший приоритет |
| Передача FutureOpportunity в solver | Backend прибавляет бонус к DailyDropPenalty и передаёт CascadeDropPenalty в AddDisjunction |
| FutureOpportunityCount равен нулю | Заявка не создаётся как optional node и получает подтверждённую причину на горизонте |
| Редкая менее срочная и обычная более срочная | SLA-группа важнее дефицитности |
| Оборудование available_units равно нулю | Permanent issue EQUIPMENT_UNAVAILABLE_IN_HORIZON |
| Оборудование занято сегодня, доступно завтра | Временная причина и перенос |
| Длительность больше всех смен | DURATION_EXCEEDS_ALL_SHIFTS без повторов по дням |
| Остановка пользователем | Завершённые дни сохранены, PARTIAL STOPPED_BY_USER |
| Остановка после успешного текущего дня | Текущий день можно опубликовать после предупреждения |
| Изменение входов во время расчёта | Текущий snapshot не меняется |
| Изменение входов до публикации | validate-current-day блокирует публикацию |
| Входы не изменились | Черновик разрешено публиковать без нового solve |
| Повторный запрос с тем же hash | Возвращается существующий current batch |
| Двойной запуск | Второй запрос получает 409 |
| Ошибка одного дня после успешных дней | PARTIAL DAY_RUN_FAILED, успешные дни сохранены |
| Ошибка до первого дневного результата | FAILED, предыдущий current batch остаётся актуальным |
| Заявка назначена в два дня | Пакетный Validator отклоняет batch |
| Проверка проектной изоляции | Чужие данные не входят в snapshot и API возвращает 404 |
| Один block из семи рабочих дат | Создаётся до семи разных planning_run и новый RoutingModel на каждую дату; одного общего вызова solver нет |
| Заявка назначена сегодня | После commit она исключена из RemainingJobs и отсутствует во входе solver завтра |
| Заявка dropped сегодня | Она остаётся BACKLOG и входит в отбор SolverCandidates следующей даты |
| Заявка временно недоступна сегодня | Solver сегодня её не получает; заявка остаётся BACKLOG и проверяется завтра |
| Переход к следующему block | Первый день нового block получает только остаток после всех сохранённых дней предыдущего block |
| Перезапуск фоновой задачи после сбоя | Завершённые дни не пересчитываются; обработка продолжается после processed_through_date |

## 29 Критерии приёмки

- Владелец и диспетчер могут вручную запустить, наблюдать и остановить batch.

- Сервер принимает только текущую дату проекта и корректно определяет effective_start_date.

- Initial и maximum horizon соответствуют 7 и 30 календарным дням.

- Дни без смен пропускаются без ложной ошибки.

- Заявки с SLA за пределами maximum horizon не участвуют.

- Primary backlog не вытесняется reserve backlog.

- Дефицитность влияет только внутри одной SLA-группы и считается по парам «инженер и день».

- Назначенные заявки удаляются из остатка и не попадают в другие дни batch.

- Постоянные причины не прокручиваются через каждый дневной solver.

- Все пути завершаются SUCCESS, PARTIAL или FAILED в пределах time limit.

- Остановка сохраняет валидные дни и не повреждает предыдущий current batch.

- Перед публикацией выполняется проверка актуальности.

- Публиковать можно только текущую дату; будущие черновики инженеру не видны.

- Пакетный Validator не допускает нарушений hard constraints и повторного назначения.

- Все тесты раздела 28 выполнены, а ссылка на тест-ран добавлена в задачу разработки.

- Каждая рассчитываемая дата имеет отдельный planning_run и отдельный вызов нового RoutingModel.

- Следующая дата не запускается до успешного Validator и commit предыдущей даты.

- Вход следующей даты равен сохранённому остатку: назначенные исключены, dropped и временно отложенные сохранены.

- Переход между block не меняет правило подневного запуска и не пересчитывает завершённые даты.

## 30 Риски и меры

| Риск | Влияние | Мера |
| --- | --- | --- |
| Локально выгодный день ухудшает следующий | Рост просрочки | FutureOpportunityCount и приоритет дефицитных заявок внутри SLA-группы |
| Число future opportunities не учитывает географию | Ложная оценка доступности | Считать показатель только secondary фактором; маршрут подтверждает дневной solver |
| Reserve заявки вытесняют primary суммарным penalty | Нарушение бизнес-приоритета | Разделённые диапазоны penalty или последовательные фазы с тестом инварианта |
| Долгий 30-дневный расчёт | Плохой UX и тайм-аут | Асинхронный API, прогресс, остановка и общий лимит 15 минут |
| Изменения данных во время расчёта | Устаревший черновик | Неизменяемый snapshot и validate-current-day |
| Постоянно невыполнимая заявка | Бесконечный цикл | Permanent classification и формальные условия остановки |
| Разные результаты time-limited solver | Недоверие диспетчера | Stable ordering, фиксированный seed и reuse по input_hash |
| Расхождения старого дневного ТЗ с моделью данных | Ошибочная реализация | Использовать актуальные правила admin ТЗ для ID, длительности, оборудования и координат |
| Будущий черновик воспринимается как обещание | Ошибки коммуникации | Явная маркировка «Черновик» и запрет будущей публикации |

## 31 Предварительное техническое решение разработчик

Предлагается отдельный MultiDayPlanningService поверх существующего PlanningService. Он отвечает за snapshot, horizon, blocks, future opportunities, последовательный запуск дней, batch Validator и состояния. Дневной PlanningService остаётся владельцем RoutingModel, дорожной матрицы, оборудования, дневных причин и маршрутов.

- Batch запускается фоновой задачей, поскольку допустимое время достигает 15 минут.

- ProjectPlanningLock запрещает пересекающиеся batch и дневные run.

- BatchDataProvider формирует snapshot и input_hash.

- HorizonClassifier определяет eligibility, primary, reserve и permanent issues.

- FutureOpportunityService вычисляет совместимые пары на оставшемся горизонте и возвращает count, rank и bonus.

- CascadePenaltyCalculator складывает DailyDropPenalty и FutureOpportunityBonus, проверяет границы SLA-группы и передаёт итог в RoutingModelBuilder.

- CascadeOrchestrator владеет последовательным циклом дат: создаёт planning_batch_day и новый planning_run для каждой даты, формирует RemainingJobs и SolverInput, вызывает PlanningService ровно один раз для этой даты и переходит дальше только после commit результата.

- BatchValidator проверяет междневные инварианты.

- CurrentBatchService атомарно переключает актуальную версию.

- StopToken проверяется между стадиями подготовки и перед каждым новым днём.

До основной разработки требуется spike на двух вопросах: гарантированное разделение primary и reserve penalty без переполнения int64 и фактическое время расчёта 7 и 30 дней на репрезентативных данных. Spike не меняет согласованную бизнес-иерархию.
