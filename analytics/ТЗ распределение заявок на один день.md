# Техническое задание на дневное планирование выездных инженеров

*Первый этап: распределение доступных заявок на один выбранный день*

Документ определяет бизнес-правила, модель данных, API, ограничения оптимизации, обработку ошибок и критерии приёмки backend-модуля дневного планирования. Результат запуска — сохранённая версия плана, в которой заявки распределены между доступными инженерами либо зафиксированы как неназначенные в рамках конкретного расчёта.

Следующие этапы проекта — обработка новой заявки, итерационное многодневное планирование, пользовательские интерфейсы и административная часть — не входят в реализацию этой задачи, но текущая модель учитывает будущую проектную изоляцию и жизненный цикл заявок.

## 1. Название задачи

Реализовать автоматическое распределение доступных заявок между выездными инженерами на один выбранный день с учётом SLA, квалификаций, смен, временных окон, транспорта, оборудования и дорожного времени.

## 2. Бизнес-описание

Сейчас дневной план формируется без единого автоматического механизма. Ручное распределение затрудняет одновременный учёт SLA, квалификаций, смен, временных окон клиентов, продолжительности работ, транспортных ограничений, географии и ограниченного оборудования. Это увеличивает время диспетчера и повышает риск назначения невыполнимых маршрутов или пропуска приоритетных заявок.

Необходимо реализовать backend-модуль, который по запросу строит допустимый план на одну выбранную календарную дату. Для каждой участвующей заявки модуль определяет факт выполнения в этот день, инженера, место заявки в маршруте и допустимое время начала работы. Оборудование распределяется между инженерами на весь день и не передаётся между ними внутри дня.

Если выполнить все заявки невозможно, заявка остаётся со своим исходным жизненным статусом, а факт неназначения сохраняется только внутри конкретного planning_run. Повторный запуск создаёт новую версию плана и не изменяет историю предыдущих запусков.

## 3. Метрика успеха

| Метрика | Критерий | Источник | Период |
| --- | --- | --- | --- |
| Валидность плана | 100% результатов со статусом SUCCESS проходят независимый Validator | БД и структурированные логи | Каждый запуск |
| Нарушения hard constraints | 0 назначений с нарушением квалификации, транспорта, смены, окна, последовательности или оборудования | Validator и тест-ран | Каждый релиз |
| Получение допустимого результата | Для согласованного тестового набора solver возвращает допустимое решение в пределах настроенного solver_time_limit_sec | Solver diagnostics | Технический spike и регрессия |
| Доля SLA-critical заявок | Сохраняется доля назначенных OVERDUE и DUE_TODAY; целевое значение определяется после пилота | planning_runs | Первые 2 недели пилота |
| Доля назначенных заявок | Сохраняется assigned_jobs_count / eligible_jobs_count; используется как базовая линия для настройки penalty | planning_runs | Первые 2 недели пилота |

Значение 30 секунд является конфигурируемым стартовым ограничением времени поиска, а не гарантией математического оптимума. Если на фактическом объёме расчёт окажется существенно медленнее, производительность и модель оптимизации анализируются отдельной задачей.

## 4. Техническое задание

### 4.1. Цель и границы этапа

Цель — построить наиболее эффективный допустимый план для одного проекта и одной planning_date, минимизируя сумму штрафов за неназначенные заявки и дорожного времени назначенных маршрутов.

```text
Objective = Σ DropPenalty(j), j ∈ Unassigned + Σ TravelTime(arc)
```

В задачу входят подготовка входных данных, расчёт совместимости и penalty, получение дорожной матрицы, построение RoutingModel, назначение заявок, дневное распределение оборудования, Validator, сохранение версии расчёта, API запуска и получения результатов.

Не входят: CRUD и UI исходных данных, изменение выполняемого маршрута после поступления новой заявки, динамическое и многодневное планирование, автоматический перенос на следующий день, передача оборудования в течение дня, физическая логистика оборудования, ML-прогнозы и отдельный CP-SAT solver.

### 4.2. Словарь терминов

| Термин | Определение |
| --- | --- |
| planning_date | Выбранная календарная дата планирования в IANA timezone проекта. Новый расчёт для прошедшей даты не запускается. |
| planning_run | Неизменяемая версия одного запуска расчёта для проекта и planning_date. |
| Eligible job | Заявка NEW, прошедшая обязательную нормализацию и включённая в набор solver. |
| BaseCompatible[j,e] | Совместимость заявки и инженера по проекту, рабочей дате, квалификациям и транспорту без учёта оборудования и маршрута. |
| Drop Penalty | Стоимость исключения optional job из решения. Более высокий penalty повышает приоритет заявки. |
| Assigned | Заявка включена в маршрут инженера в рамках planning_run. |
| Unassigned | Заявка не включена в маршрут конкретного planning_run. Жизненный статус jobs.status не меняется. |
| Hard constraint | Ограничение, которое ни при каких условиях не может быть нарушено сохранённым SUCCESS-планом. |
| Travel profile | Режим расчёта дорожного времени: CAR использует driving, NONE использует walking. |

### 4.3. Событие запуска и дата планирования

- Расчёт запускается вручную синхронным POST-запросом.
- Клиент передаёт planning_date. Допускается текущая или будущая дата в timezone проекта.
- Timezone проекта хранится в формате IANA, например Asia/Yekaterinburg, и не зависит от timezone сервера.
- Для одной пары project_id + planning_date одновременно допускается один активный run в состояниях CREATED, PREPARING или RUNNING.
- Повторный запрос при активном run возвращает 409 PLANNING_RUN_IN_PROGRESS.
- Каждый новый запуск создаёт отдельный planning_run; старые результаты не перезаписываются.

### 4.4. Заявки и жизненные статусы

Жизненные статусы jobs.status: NEW, IN_PROGRESS, COMPLETED, CANCELLED. Первый этап передаёт в solver только активные заявки со статусом NEW выбранного проекта. SLA не ограничивает попадание заявки: участвуют просроченные, сегодняшние и будущие заявки.

IN_PROGRESS резервируется для следующего этапа и в текущий solver не передаётся. Результаты ASSIGNED и UNASSIGNED_TODAY хранятся в таблицах результата planning_run и не записываются в jobs.status.

### 4.6. Нормализация входных данных

1. Загрузить данные только выбранного project_id в одной согласованной транзакционной версии.
2. Отобрать активные jobs.status = NEW.
3. Определить duration: jobs.service_duration_min, иначе work_types.default_service_duration_min. Если оба отсутствуют или значение не положительное — исключить заявку с MISSING_SERVICE_DURATION.
4. Проверить sla_date, work_type_id, адрес/координаты и временное окно. Некорректные обязательные данные дают INVALID_INPUT.
5. Если координат нет, выполнить геокодирование по адресу. При ошибке исключить заявку с GEOCODING_FAILED.
6. Определить required_qualifications, required_equipment и required_transport из типа работ.
7. Рассчитать BaseCompatible и DropPenalty.
8. Применить max_jobs_per_run. При превышении выбрать заявки по DropPenalty DESC, sla_date ASC, created_at ASC, id ASC. Остальные сохранить как неназначенные с DATASET_LIMIT.

### 4.7. Временные окна, смены и время

Временное окно ограничивает начало работы, а не её завершение:

```text
window_start ≤ planned_start ≤ window_end
```

Работа может закончиться после window_end, но всегда должна полностью помещаться в смену инженера:

```text
shift_start ≤ planned_start; planned_finish = planned_start + duration; planned_finish ≤ shift_end
```

| Входные границы | Нормализованное окно |
| --- | --- |
| Обе отсутствуют | 00:00–23:59:59 локального дня проекта |
| Только start | start–23:59:59 |
| Только end | 00:00–end |
| Обе заполнены | start–end; если start > end, INVALID_TIME_WINDOW |

Нормализованное окно пересекается со сменой конкретного инженера. Ночные смены и окна, переходящие через полночь, не поддерживаются в MVP.

Инженер может ожидать открытия окна. Waiting не включается в Objective. Solver может выбрать любое допустимое время начала и выезда без дополнительного правила минимизации ожидания; поэтому два запуска с одинаковыми данными могут вернуть разные, но равно допустимые времена.

```text
planned_arrival = planned_finish(previous) + travel_time(previous, current)
waiting_before_job = max(0, planned_start − planned_arrival)
```

Для первой заявки previous — начальная точка инженера и выбранное solver время начала маршрута. Все сохраняемые времена должны содержать локальную дату и timezone или храниться как timestamptz.

### 4.8. SLA и Drop Penalty

```text
DaysToSLA = sla_date − planning_date
OverdueDays = max(0, planning_date − sla_date)
```

| Условие | SLA status | Базовый penalty |
| --- | --- | --- |
| DaysToSLA < 0 | OVERDUE | 10 000 + 1 000 × OverdueDays |
| DaysToSLA = 0 | DUE_TODAY | 9 000 |
| DaysToSLA = 1 | FUTURE | 4 000 |
| DaysToSLA = 2–3 | FUTURE | 2 000 |
| DaysToSLA > 3 | FUTURE | 500 |

```text
DropPenalty = SLABase + OverdueBonus + SkillScarcityBonus + EquipmentInventoryBonus + WindowTightnessBonus
```

| Дополнительный фактор | Значение по умолчанию |
| --- | --- |
| Только 1 BaseCompatible инженер | +500 |
| Только 2 BaseCompatible инженера | +250 |
| Доступна 1 единица требуемого типа оборудования | +500 за тип |
| Доступны 2 единицы требуемого типа оборудования | +250 за тип |
| Окно начала ≤ 30 минут | +300 |
| Окно начала ≤ 60 минут | +150 |
| Окно начала ≤ 120 минут | +50 |
| Travel | 1 балл за минуту |

Все коэффициенты конфигурируются на уровне проекта и сохраняются в config_snapshot. SLA остаётся soft priority: solver может пропустить SLA-critical заявку, если другое решение имеет меньший суммарный Objective.

### 4.9. Совместимость заявки и инженера

BaseCompatible[j,e] = true только при одновременном выполнении условий: инженер относится к проекту и активен; имеет корректную смену на planning_date; обладает всеми требуемыми квалификациями; удовлетворяет required_transport. Оборудование, вместимость смены и возможность вставки в маршрут в BaseCompatible не входят.

Если работа требует CAR, инженер с transport_type = NONE несовместим. Если работа не требует CAR, инженер NONE допускается и для него используется профиль walking.

### 4.10. Геокодирование и Travel Matrix

Для минимально работающего решения используются два взаимозаменяемых провайдера: STATIC_TEST для DEV и автоматических тестов и YANDEX_SYNC для демонстрационного или пилотного запуска на небольшом объёме. Solver зависит только от интерфейса TravelMatrixProvider.

- Если координаты уже заполнены, повторное геокодирование не выполняется.
- Если адрес изменён, сохранённые координаты считаются устаревшими. Реализация хранит address_hash/geocoded_at либо очищает координаты при изменении адреса.
- Синхронные запросы Yandex разбиваются на блоки так, чтобы origins × destinations не превышало 100 элементов.
- Матрицы строятся отдельно для driving и walking только при наличии инженеров соответствующего профиля.
- Ключ кеша включает нормализованные координаты начала и конца, mode и traffic_reference_time bucket.
- В YANDEX_SYNC данные Yandex и производные дорожные значения хранятся не более 30 дней; обязательна TTL-очистка.
- STATIC_TEST принимает подготовленную матрицу и не выполняет внешних запросов.

traffic_reference_time является единым для всего run. Для будущей даты используется самое раннее shift_start. Для текущей даты используется более позднее из текущего времени и самого раннего shift_start. Для walking значение не влияет на Yandex.

Матрица содержит Engineer start → Job и Job → Job. Возвращение после последней заявки не рассчитывается. Если элемент Yandex имеет status = FAIL, соответствующая дуга запрещается и не заменяется нулём. Заявка исключается с TRAVEL_DATA_NOT_READY только если для неё не остаётся допустимого способа включения в маршрут. Системная недоступность провайдера, не позволяющая построить расчёт, завершает run со статусом FAILED.

### 4.11. Модель OR Tools

| Понятие | Модель |
| --- | --- |
| Vehicle | Engineer |
| Node | Eligible job |
| Start node | Индивидуальная начальная точка инженера |
| End node | Dummy end; переход от последней заявки имеет travel и time = 0 |
| Optional node | Каждая заявка через AddDisjunction(node, DropPenalty) |

Для каждой заявки в RoutingModel разрешаются только vehicles из BaseCompatible[j]. Если множество пусто, заявку целесообразно не добавлять в solver и сразу сохранить NO_COMPATIBLE_ENGINEER.

Time Dimension использует vehicle-specific transit callbacks:

```text
TimeTransit(A,B,e) = ServiceDuration(A) + TravelTime(A,B, profile(e))
ArcCost(A,B,e) = TravelTime(A,B, profile(e)) × travel_cost_per_minute
```

Service duration обеспечивает физическую последовательность, но отдельно не увеличивает Objective. Slack Time Dimension разрешает ожидание. Начальный CumulVar каждого инженера ограничивается его сменой и не фиксируется в shift_start.

### 4.12. Оборудование внутри RoutingModel

Оборудование назначается инженеру на весь planning_date и не передаётся внутри дня. Для каждой пары Engineer e × EquipmentType r создаётся boolean UsesEquipment[e,r].

```text
Σe UsesEquipment[e,r] ≤ AvailableUnits[r]
```

Для каждой допустимой пары job j × engineer e формируется Assigned[j,e] как индикатор VehicleVar(j) = e. Для dropped node значение VehicleVar равно −1, поэтому все Assigned[j,e] равны 0.

```text
Assigned[j,e] ≤ UsesEquipment[e,r], если job j требует equipment r
UsesEquipment[e,r] ≤ Σ Assigned[j,e] для jobs, требующих r
```

Обратное ограничение запрещает резервировать оборудование инженеру, если ни одна его назначенная заявка не требует этот тип. Один инженер может использовать закреплённую единицу оборудования в нескольких заявках в течение дня.

### 4.13. Search Parameters и ограничение объёма

| Параметр | Значение по умолчанию |
| --- | --- |
| first_solution_strategy | PARALLEL_CHEAPEST_INSERTION |
| local_search_metaheuristic | GUIDED_LOCAL_SEARCH |
| solver_time_limit_sec | 30, конфигурируется |
| max_jobs_per_run | 1000, защитный конфигурируемый порог |

Если лимит времени достигнут и найдено допустимое решение, оно сохраняется как SUCCESS с solver_status = FEASIBLE_TIME_LIMIT. Если допустимого решения нет, run завершается FAILED. Математическая оптимальность для MVP не требуется.

Если заявок больше max_jobs_per_run, solver получает заявки с наибольшим рассчитанным penalty. Для равных значений используется sla_date, created_at и id. Не вошедшие заявки сохраняются с reason_code DATASET_LIMIT. На ожидаемом тестовом объёме срабатывание этого правила не предполагается.

| Состояние | status, solver_status, started_at, finished_at |
| Objective | objective, drop_cost, travel_cost |
| Счётчики | input_jobs_count, eligible_jobs_count, assigned_jobs_count, unassigned_jobs_count, sla_critical_total, sla_critical_assigned |
| Snapshot | config_snapshot jsonb, input_snapshot jsonb, normalized_input_hash, travel_matrix_ref/hash nullable, traffic_reference_time |
| Диагностика | solver_version, solver_time_ms, error_code, error_message, validation_errors jsonb |
| Аудит | created_at |

Статусы: CREATED, PREPARING, RUNNING, SUCCESS, FAILED, FAILED_VALIDATION. Результат со статусом FAILED_VALIDATION не может считаться актуальным.

#### planning_routes и planning_route_jobs

planning_routes: id, planning_run_id, engineer_id, planned_start, planned_finish, total_travel_min, total_service_min, total_waiting_min. Пустой маршрут инженера не сохраняется.

planning_route_jobs: id, planning_route_id, job_id, sequence, planned_arrival, planned_start, planned_finish, travel_from_previous_min, waiting_before_job_min, drop_penalty_snapshot. Unique planning_route_id + sequence и unique planning_run_id + job_id обеспечиваются ограничениями БД.

#### planning_equipment_assignments и planning_unassigned_jobs

planning_equipment_assignments: id, planning_run_id, engineer_id, equipment_type_id. Запись создаётся только для фактически требуемого оборудования; unique для run + engineer + equipment_type.

planning_unassigned_jobs: id, planning_run_id, job_id, drop_penalty, primary_reason_code, diagnostic_flags jsonb. Заявка не может одновременно находиться в planning_route_jobs и planning_unassigned_jobs одного run.

### 4.15. Snapshot и воспроизводимость

При запуске в одной согласованной версии данных сохраняются заявки, инженеры, смены, квалификации, типы работ, дневная доступность оборудования, configuration version, planning_date и timezone. Дополнительно сохраняются нормализованный хеш входа, версия OR-Tools, search parameters, traffic_reference_time и ссылка/хеш использованной матрицы.

Требование означает аудируемость входов и результата, но не побитовое повторение маршрута. При ограничении времени solver может вернуть другой равно допустимый план. Для STATIC_TEST полная история сохраняется без лицензионного TTL. Для YANDEX_SYNC безопасное поведение по умолчанию — удалить не позднее чем через 30 дней кеш, полученные через геокодер координаты и planning_run вместе с полями, производными от дорожных данных. Более длительное хранение допускается только после отдельной проверки условий лицензии.

### 4.16. Reason codes

| Код | Условие |
| --- | --- |
| INVALID_INPUT | Отсутствуют или некорректны обязательные входные данные |
| MISSING_SERVICE_DURATION | Нет положительной длительности у заявки и типа работ |
| INVALID_TIME_WINDOW | Окно не может быть нормализовано |
| GEOCODING_FAILED | Не удалось получить координаты |
| TRAVEL_DATA_NOT_READY | Для заявки не осталось допустимых дорожных дуг |
| NO_AVAILABLE_ENGINEER | На planning_date нет доступных инженеров проекта |
| NO_COMPATIBLE_ENGINEER | Нет инженера с требуемой сменой, квалификациями и транспортом |
| DATASET_LIMIT | Заявка не вошла в solver из-за max_jobs_per_run |
| NOT_SELECTED_BY_OPTIMIZER | Корректная заявка была optional, но не выбрана solver |

Reason codes вычисляются детерминированным диагностическим модулем. Код не должен утверждать недоказанную причинность. Ограничения оборудования, окна и смены могут сохраняться как diagnostic_flags, только если это подтверждается простой изолированной проверкой; они не заменяют primary_reason_code и не требуют дополнительных solver-запусков.

### 4.17. Validator

После solver независимо проверяются: принадлежность всех данных проекту; отсутствие повторного назначения; полный набор квалификаций; транспорт; начало внутри окна; завершение внутри смены; последовательность service + travel; наличие оборудования; дневная ёмкость оборудования; отсутствие пересечения Assigned и Unassigned; корректность sequence и агрегированных метрик.

Любая ошибка переводит run в FAILED_VALIDATION. Маршруты такого run сохраняются для диагностики, но API помечает результат неактуальным и не выдаёт его как рабочий план.

### 4.18. API

#### Запуск

```text
POST /api/projects/{project_id}/planning/runs
{ "planning_date": "2026-09-09" }
```

Запрос выполняется синхронно. При успешном завершении возвращается 201 Created с planning_run_id, status, solver_status и краткими metrics. HTTP timeout клиента и сервера должен превышать solver_time_limit_sec с запасом на подготовку и сохранение.

Основные ошибки: 403 — нет права запуска; 409 PLANNING_RUN_IN_PROGRESS; 422 — некорректная или прошедшая planning_date; 500/503 — критическая ошибка с сохранённым planning_run_id, если он был создан.

#### Получение результата

```text
GET /api/projects/{project_id}/planning/runs/{id}
```

Возвращаются run, metrics, routes с route jobs и equipment, а также unassigned_jobs. Запрос к run другого проекта возвращает 404.

#### История

```text
GET /api/projects/{project_id}/planning/runs?planning_date=&status=&limit=&offset=
```

Сортировка created_at DESC. limit имеет серверный максимум. Последний SUCCESS-run для даты может использоваться следующим этапом UI как актуальный.

### 4.19. Поведение при пустых и ошибочных данных

- Нет заявок: SUCCESS с пустыми routes и unassigned_jobs.
- Нет доступных инженеров при корректной загрузке: SUCCESS, все валидные заявки получают NO_AVAILABLE_ENGINEER.
- Одна некорректная заявка не блокирует остальные; она сохраняется в unassigned_jobs.
- Ошибка отдельной дорожной дуги запрещает дугу, но не останавливает run.
- Невозможно загрузить исходные данные, нет обязательной конфигурации, недоступен solver или TravelMatrixProvider не может подготовить расчёт: FAILED.
- Необработанная техническая ошибка: FAILED с error_code и безопасным error_message.

### 4.20. Основной flow

```text
Manual start → Create run → Snapshot → Normalize → Compatibility → SLA/Penalty
→ Travel Matrix → RoutingModel + Equipment → Solve → Assigned/Unassigned
→ Reason resolver → Validator → Save result → Response
```

### 4.21. Edge cases

- Окно уже смены: используется пересечение; если оно пусто для всех BaseCompatible инженеров, заявка остаётся неназначенной.
- Duration длиннее любой доступной смены: заявка корректна, но solver её не назначает.
- available_units = 0: заявки с таким оборудованием могут участвовать как optional, но не могут быть назначены.
- Несколько требуемых квалификаций и типов оборудования применяются одновременно по правилу AND.
- Несколько инженеров могут иметь одинаковую стартовую точку; матрица может переиспользовать одинаковые координаты.
- Одинаковые координаты двух заявок дают нулевое или предоставленное провайдером travel time; service duration сохраняет последовательность.
- Изменение заявки после старта run не влияет на snapshot и результат этого run.
- По истечении 30 дней данные YANDEX_SYNC нельзя использовать в новом run; фоновая очистка удаляет кеш, координаты геокодера и связанные результаты run, если более длительное хранение не подтверждено лицензией.

### 4.22. Риски

| Риск | Снижение риска |
| --- | --- |
| Непредсказуемое время поиска с equipment constraints | Обязательный spike на репрезентативных объёмах и конфигурируемый time limit |
| Стоимость и лицензия Yandex | STATIC_TEST на DEV; YANDEX_SYNC только для малых наборов; TTL ≤ 30 дней; мониторинг элементов матрицы |
| Нестабильное качество penalty | Хранить метрики, snapshots и версию конфигурации; калибровать после пилота |
| Разные допустимые времена при одинаковом Objective | Считать это допустимым MVP-поведением и не обещать побитовую повторяемость |
| Рост объёма выше max_jobs_per_run | Детерминированный отбор по penalty; отдельная задача на кластеризацию и многодневное планирование |

## 5. Предварительное техническое решение [разработчик]

Предлагается отдельный PlanningService, который оркестрирует PlanningDataProvider, JobNormalizer, CompatibilityService, PenaltyCalculator, TravelMatrixProvider, RoutingModelBuilder, Solver, UnassignedReasonResolver, PlanningValidator и PlanningRunRepository. Конкретные классы и методы разработчик определяет в рамках принятой архитектуры приложения.

- Транзакционно создать planning_run и зафиксировать входной snapshot.
- Использовать ограничение БД или распределённый lock для одного активного run на project_id + planning_date.
- Скрыть STATIC_TEST и YANDEX_SYNC за единым TravelMatrixProvider.
- Хранить конфигурацию с версиями и добавлять её snapshot в каждый run.
- Сохранять routes, jobs, equipment и unassigned атомарно после Validator.
- Проверить custom BoolVar UsesEquipment + VehicleVar на spike до основной реализации.

Разработчик до первого груминга должен подтвердить поддержку выбранной версии OR-Tools, способ построения Assigned[j,e], формат транзакционного snapshot, реализацию TTL-кеша, ограничения БД и инфраструктуру синхронного HTTP-запроса.

## 6. UX / UI

UI не входит в текущую задачу. Backend должен возвращать достаточные данные для будущего интерфейса диспетчера: статус запуска, метрики, маршруты, порядок и времена заявок, оборудование и неназначенные заявки с reason codes. Новые UI-компоненты в рамках этапа не создаются.

## 7. Тест-кейсы

Ссылка на тест-ран добавляется QA после создания задачи в системе управления разработкой. До начала разработки необходимо согласовать тестовые данные, доступ к STATIC_TEST matrix и ожидаемые результаты контрольных сценариев.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Базовый расчёт | Допустимые заявки распределяются по маршрутам; Validator успешен. |
| Проектная изоляция | В run не попадают данные другого project_id. |
| Произвольная дата | Текущая и будущая даты принимаются; прошедшая дата отклоняется. |
| Квалификации | Заявка назначается только инженеру со всеми квалификациями. |
| Транспорт | required_transport = CAR не назначается инженеру NONE; NONE использует walking. |
| Полное окно | planned_start находится между start и end; finish может быть позже end, но не shift_end. |
| Односторонние окна | Только start и только end нормализуются согласно правилам. |
| Некорректное окно | start > end даёт INVALID_TIME_WINDOW. |
| Duration fallback | Используется значение заявки, затем default типа; отсутствие обоих даёт MISSING_SERVICE_DURATION. |
| Смена | Работа не начинается до shift_start и не заканчивается после shift_end. |
| Waiting | Ожидание разрешено и корректно сохраняется; оно не входит в Objective. |
| SLA и penalty | Проверены все SLA buckets, дни просрочки и дополнительные бонусы. |
| Optional jobs | При нехватке ресурсов часть заявок получает NOT_SELECTED_BY_OPTIMIZER. |
| Оборудование 1 | Одна единица типа не закрепляется за двумя инженерами. |
| Повторное использование | Один инженер выполняет несколько заявок с одним закреплённым типом. |
| Несколько типов | Job назначается только инженеру со всеми требуемыми типами. |
| Недоступная дуга | Yandex FAIL запрещает дугу и не превращается в travel = 0. |
| Частично некорректные данные | Некорректная заявка не блокирует остальные. |
| Нет заявок | Создаётся SUCCESS с пустым результатом. |
| Нет инженеров | Все заявки получают NO_AVAILABLE_ENGINEER, run успешен. |
| Конкурентный запуск | Второй активный run на проект и дату получает 409. |
| История и snapshot | Изменение источника и config не меняет старый run; история YANDEX_SYNC удаляется по лицензионному TTL. |
| Dataset limit | Отбор детерминирован; исключённые заявки получают DATASET_LIMIT. |
| Validator | Любое искусственно внесённое нарушение даёт FAILED_VALIDATION. |
| Time limit | Лучшее допустимое решение сохраняется с FEASIBLE_TIME_LIMIT. |

## 8. Логирование и мониторинг [разработчик]

### 8.1. Логирование

Все события логируются структурированно с planning_run_id и project_id. Не логировать адреса и полные snapshots в обычный application log.

- Старт и завершение run, status и error_code.
- Количество входных, eligible, assigned и unassigned заявок; количество инженеров и типов оборудования.
- Время загрузки, нормализации, матрицы, solver, Validator и сохранения.
- Objective, drop_cost, travel_cost, solver_status и validation_status.
- Количество элементов и запросов Yandex, cache hit ratio, ответы 429/5xx и число FAIL-дуг.
- Количество equipment variables и assignment/equipment constraints.

### 8.2. Мониторинг

- p50/p95/p99 полного времени planning run и отдельных этапов.
- Доля SUCCESS, FAILED и FAILED_VALIDATION.
- Доля запусков без допустимого решения и доля time-limit результатов.
- Assigned ratio и SLA-critical completion по проектам.
- Объём и стоимость элементов Yandex Matrix, cache hit ratio и срок TTL.

Дашборд и алерты должны работать на DEV до выхода задачи. Алерт обязателен для FAILED_VALIDATION, резкого роста внешних запросов и повторяющихся 429/5xx Yandex.

## 9. План раскатки [разработчик]

1. Создать таблицы проектов, исходных справочников и planning_* либо добавить project_id и ограничения в существующие таблицы.
2. Добавить одну активную конфигурацию по умолчанию для тестового проекта.
3. Настроить STATIC_TEST на DEV и тестовую матрицу. При использовании YANDEX_SYNC добавить секрет API key и лимиты внешних запросов.
4. Включить feature flag planning_one_day_enabled для выбранного проекта.
5. Выполнить spike на фактическом ожидаемом объёме и зафиксировать baseline.
6. Провести smoke run, проверить Validator, snapshots, TTL и метрики.
7. После успешного тест-рана включить функцию на пилотном проекте.

Пересчёт старых данных не требуется. Миграции должны быть обратимо применимыми до начала записи planning runs. Основные риски обновления: неверная проектная изоляция, отсутствие активной конфигурации, HTTP timeout и превышение лимита Yandex.
